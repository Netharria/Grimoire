# Spec 1.5: PluralKit

Status: **implemented 2026-11-16.** Approved 2026-11-16: the owner took the suggested answer to every open question
(section 10); OQ-1 and OQ-2 come with the owner's context. Section 3.12 lists where the code differs from the approved
text. Tests: unit 735 (1 skipped, KI-93), integration 1446 (39 skipped: KI-101's and KI-111's tests now run). Build
warnings: 119, unchanged. Stryker hasn't been run for this section yet.

Implements the plan's section 1.5: `IPluralKitIO`, the capability through which ported code asks PluralKit about a
message, with one place where PluralKit's HTTP answers become values. It replaces the rate limiter that refuses calls
with a token bucket that queues them (SH-2, Q24, defect 3, KI-111), adds the deleted-member branch (Q37), has the
lookup return a typed link instead of PluralKit's strings (LOG-4), gives the message logs one `ProxyAuthor` in place
of three nullable fields (LOG-3), and makes a missing `pluralkitApiEndpoint` turn PluralKit off instead of breaking the
delete log (KI-101).

PluralKit's published API facts this spec relies on (pluralkit.me/api, read 2026-11-16):

- `GET /v2/messages/{id}` takes either the proxy's id or the original's. Lookups by the original's id work for 30
  minutes after it was sent.
- The message endpoint has its own rate limit scope (`message`): **10 requests a second**. The docs don't say whether
  the limit is per IP or per token. A 429 has a JSON body with `retry_after` in milliseconds.
- An unknown message is **404 with code 20006** ("Message not found.").
- `system` and `member` are null "if the member associated with this message was deleted" (the basis for Q37).
- A request without a User-Agent gets a 400. The docs don't say whether the message endpoint needs a token.

## 1. Scope

**In scope**

- **`IPluralKitIO`**, its live implementation over the named `HttpClient`, a disabled implementation, and the
  `PluralKit<RT>` effect module. It adds one field to `GrimoireEnv` and one `Has<>` to each runtime, as 1.4 did.
- **One error edge** (`PluralKitErrors.Classify`, section 3.4): the only place an HTTP status, a PluralKit error body
  or an exception becomes a value.
- **The token bucket with a small queue (Q24, SH-2)** (section 3.5). It replaces the fixed window of 2 a second with
  no queue. Fixes defect 3 and KI-111.
- **The retry moves out of Polly** into `PluralKit<RT>`, as in 1.3 and 1.4: transient failures only, a short
  schedule, each attempt taking its own token (section 3.6). The PluralKit client loses
  `AddStandardResilienceHandler`.
- **The typed result (LOG-4)** (section 3.2): a pure `PluralKitMessage.Classify` turns PluralKit's wire record into a
  `ProxyLookup`, with a `ProxiedMessageLink` already built. The handler's eight-clause `&&` chain goes.
- **The deleted-member branch (Q37)**: PluralKit confirms the deleted message was replaced by a proxy, but sends no
  system or member. The original's delete isn't logged, and no link is saved.
- **`ProxyAuthor` (LOG-3)** (section 3.7): one nullable record replaces `OriginalUserId`, `SystemId` and `MemberId`
  in the delete and edit handlers' projections and in `AddMessageAuthorFields`. `OrPrivate` goes.
- **Configuration (KI-101)** (section 3.8): one `PluralKitOptions`, parsed once at startup. PluralKit is on only when
  every key it needs is set and the endpoint is an absolute URL. Otherwise it's off, with one warning naming the
  missing keys, and the `HttpClient` registration can't throw.
- **A bridge for `DeleteMessageEvent`** (section 3.9). The handler stays on EF until 3.10, so `IPluralkitService`
  becomes a small bridge that runs the effect and hands back a `ProxyLookup`. This is the only feature code 1.5
  touches, as 1.4 touched only `GuildLogPublisher` and the LOG-2 sites.
- **SH-7 for this path**: the 60-second window reads `ITimeIO`, not `DateTimeOffset.UtcNow`.
- **A fake PluralKit** for unit tests (`FakePluralKitIO`), and the integration fake (`FakePluralKit`) answering as
  PluralKit does (404 with code 20006, 429 with `retry_after`, null system and member).

**Out of scope**

- **Porting `DeleteMessageEvent` and `UpdateMessageEvent`** to `Eff` and Dapper: section 3.10. That includes the
  `ProxiedMessageLink` insert, which becomes `ON CONFLICT DO NOTHING` there and loses the two constraint catches.
- **KI-104** (the bulk delete dump names proxies by the webhook id): 3.10.
- **KI-112** (a locked thread doesn't stop proxies): 3.5.
- **A circuit breaker.** Polly's goes with the resilience handler (OQ-3).
- **Spans and metrics**: 1.6. 1.5 names the operation and exposes the queue's statistics for it (section 7).
- **Dispatch webhooks** (PluralKit's push alternative to polling). Not needed at our volume.

**IDs covered:** SH-2, Q24, defect 3, Q37, LOG-3, LOG-4, KI-101, KI-111, I-3 (kept: a failure still never costs the
delete log), I-15 (the small wire record, kept), SH-7 (this path), Q1 (the PluralKit half: an outage is
`Unavailable` at one edge).

## 2. Flow

### 2.1 A lookup

```
feature effect        PluralKit<RT>.Lookup(deleted, createdAt)                    effect, built not run
   │
   ├─ Clock<RT>.UtcNow ──► PluralKitWindow.ShouldAsk(createdAt, now)               pure: under 60 s old?
   │     no ──► ProxyLookup.NotAsked
   ▼
   retry while transient, on IPluralKitIO.ReadRetry, all under a 15 s cap (section 3.6)
   │
   ▼
LivePluralKitIO.GetMessage(id)                                                     live capability (the shell)
   │  limiter.AcquireAsync ──► waits in the queue (≤ about 10 s), or "queue full"
   │  GET messages/{id}
   │  200 ──► JSON ──► PluralKitMessage                                            wire record, all strings
   │  404 with code 20006 ──► None
   │  anything else ──► PluralKitErrors.Classify ──► Unavailable | Errors.Cancelled | defect
   ▼
Option<PluralKitMessage> ──► PluralKitMessage.Classify(deleted)                    pure (LOG-4, Q37)
   ──► NotProxied | ReplacedByProxy(link) | ReplacedByProxyOfDeletedMember(proxy) | IsTheProxy
```

The disabled capability (PluralKit not configured) answers `NotAsked` without a call.

### 2.2 The delete handler, through the bridge (until 3.10)

```
DeleteMessageEvent
   ├─ module on, not the bot, row stored                                           unchanged
   ├─ IPluralkitService.Lookup(id, createdAt)  ──► runs PluralKit<GrimoireRuntime>.Lookup
   │     fails ──► logged (section 3.4's level), treated as NotProxied             I-3 kept
   ├─ ReplacedByProxy(link)                ──► save the link, log nothing          unchanged

```

## 3. Types

In `Grimoire/Functional/` unless a path says otherwise. The PluralKit files go in a new `PluralKit/` folder next to
`Discord/`. The pure parts (`ProxyLookup`, `PluralKitMessage.Classify`, `PluralKitWindow`, `PluralKitOptions`) are in
`Grimoire/Features/Shared/PluralKit/`, beside the wire record.

### 3.1 The capability

```csharp
/// <summary>
///     PluralKit's message lookup (spec 1.5). Every HTTP answer becomes a value in one place (PluralKitErrors).
///     PluralKit&lt;RT&gt; adds the window, the retry and the cap, so it is the API features use.
/// </summary>
public interface IPluralKitIO
{
    /// <summary>False when PluralKit isn't configured. Then GetMessage is never called.</summary>
    bool IsEnabled { get; }

    /// <summary>
    ///     The message as PluralKit knows it, by the proxy's id or the original's. None for 404/20006. Waits for a
    ///     token from the bucket first.
    /// </summary>
    IO<Option<PluralKitMessage>> GetMessage(MessageId message);

    /// <summary>Live: PluralKitRetry.Reads. Fake: no delay.</summary>
    Schedule ReadRetry { get; }
}

public static class PluralKit<RT> where RT : Has<Eff<RT>, IPluralKitIO>, Has<Eff<RT>, ITimeIO>
{
    /// <summary>
    ///     What PluralKit says about a message that was just deleted. Asks only when PluralKit is on and the message
    ///     is under 60 s old. A read, so it's retried while transient, inside a 15 s cap.
    /// </summary>
    public static Eff<RT, ProxyLookup> Lookup(MessageId deleted, DateTimeOffset createdAt);
}
```

`IsEnabled` is a property rather than a separate capability so that the fake can switch it, and so that the window
check and the "off" case are in the effect that unit tests run.

### 3.2 The result (LOG-4, Q37)

```csharp
/// <summary>What PluralKit says about a deleted message, from the delete handler's point of view.</summary>
public abstract record ProxyLookup
{
    /// <summary>Not asked: PluralKit is off, or the message is over 60 s old.</summary>
    public sealed record NotAsked : ProxyLookup;

    /// <summary>PluralKit doesn't know it (404/20006).</summary>
    public sealed record NotProxied : ProxyLookup;

    /// <summary>PluralKit deleted this original and posted a proxy. Link them; log nothing.</summary>
    public sealed record ReplacedByProxy(ProxiedMessageLink Link) : ProxyLookup;

    /// <summary>
    ///     As above, but PluralKit sent no system or member: the member was deleted (Q37). Log nothing, save no link,
    ///     since ProxiedMessageLink keeps both ids required.
    /// </summary>
    public sealed record ReplacedByProxyOfDeletedMember(MessageId Proxy) : ProxyLookup;

    /// <summary>The deleted message is the proxy itself. Logged as usual; the stored link names the author.</summary>
    public sealed record IsTheProxy : ProxyLookup;
}
```

`PluralKitMessage` (the wire record, all `string?`, I-15) gains one pure method:

```csharp
/// <summary>Parses PluralKit's answer once, at the edge (LOG-4). Fails with Unavailable when it can't be read.</summary>
public Fin<ProxyLookup> Classify(MessageId deleted);
```

| PluralKit's answer | Result |
|---|---|
| `id` or `original` missing or not a snowflake | `Unavailable("PluralKit's answer can't be read.")` (section 3.4) |
| `id` equals `deleted` | `IsTheProxy` |
| `original` isn't `deleted` (PluralKit answered for another message) | `Unavailable`, as above |
| `system` and `member` both present, ids non-blank | `ReplacedByProxy(link)`, built with `PluralKitSystemId.Create` and `PluralKitMemberId.Create` |
| `system` or `member` null or missing | `ReplacedByProxyOfDeletedMember(proxy)` (Q37) |
| an id present but blank | `Unavailable`, as above: the docs never send a blank id |

`None` from the capability (404/20006) is `NotProxied`.

The "PluralKit answered for another message" row is new. Today a mismatched `original` saves a link for the wrong
pair. It can't happen with PluralKit as documented, but checking costs one comparison.

### 3.3 The window

```csharp
public static class PluralKitWindow
{
    /// <summary>
    ///     PluralKit deletes an original within a second or two of the proxy. A delete of an older message isn't
    ///     PluralKit's, so it isn't asked about. Well inside the 30 minutes PluralKit answers for originals.
    /// </summary>
    public static readonly TimeSpan Age = TimeSpan.FromSeconds(60);

    public static bool ShouldAsk(DateTimeOffset createdAt, DateTimeOffset now) => now - createdAt <= Age;
}
```

Unchanged behaviour, but it reads `Clock<RT>` (SH-7) and is unit-tested at the boundary (exactly 60 s is asked).

### 3.4 The error edge (Q1)

```csharp
internal static class PluralKitErrors
{
    /// <summary>The one place a PluralKit answer or exception becomes a value. Pure, tested row by row.</summary>
    public static Error Classify(PluralKitFailure failure, MessageId message, CancellationToken token);

    /// <summary>A 5xx, a 429, a timeout or a lost connection. Not a full queue, not a refusal, not a bad answer.</summary>
    public static bool IsTransient(Error error);
}
```

As in 1.4, `PluralKitFailure` reads the response or exception into data first (status, PluralKit's JSON `code`,
`retry_after`, the exception kind), so the decision is a pure function.

| Failure | Becomes | Transient | Logged by the bridge as |
|---|---|---|---|
| the run's token cancelled | `Errors.Cancelled` | no | Information |
| 404 with code 20006 | not an error: `None` | — | — |
| 404 without code 20006 | `Unavailable("PluralKit answered 404 for the messages endpoint; check pluralkitApiEndpoint.")` | no | Warning |
| 5xx | `Unavailable` | yes | Information |
| 429 (another client shares the limit, or PluralKit lowered it) | `Unavailable`, keeping `retry_after` for the log | yes | Warning: our bucket should prevent it |
| `HttpClient` timeout, `HttpRequestException`, `IOException`, `SocketException` | `Unavailable` | yes | Information |
| the queue is full (more than about 10 s of lookups waiting) | `Unavailable("PluralKit lookups are queued past the limit.")` | no | Warning |
| 401, 403 (a bad token, or PluralKit blocked us) | `Unavailable`, naming the status | no | Warning, plus one Warning alert (OQ-4) |
| 400 (for example a missing User-Agent) | `Unavailable`, quoting PluralKit's top-level `message` | no | Warning, plus one Warning alert (OQ-4) |
| a 200 whose JSON doesn't parse, or `Classify` can't read it | `Unavailable("PluralKit's answer can't be read.")` | no | Warning |
| anything else | defect | — | Error |

- **Why `Unavailable` and not `Invalid` or `Forbidden`.** C1's `Invalid` and `Forbidden` are refusals shown to a
  user. Nothing here is the user's doing, and the lookup is optional: the caller treats every failure the same way,
  as "not proxied" (I-3). The case only decides the log level and whether to retry.
- **No message content** goes in an error or a log line; PluralKit's `message` field is an error text, never the
  proxied content.
- **Today's behaviour kept:** every failure still logs the delete as an ordinary one. What changes is that a queued
  lookup no longer fails at all, so the failure branch now runs only on a real outage, as SH-2 intended.

### 3.5 The token bucket (Q24, SH-2)

```csharp
new TokenBucketRateLimiter(new TokenBucketRateLimiterOptions
{
    TokenLimit = 2, TokensPerPeriod = 1, ReplenishmentPeriod = TimeSpan.FromMilliseconds(200),
    QueueLimit = 50, QueueProcessingOrder = QueueProcessingOrder.OldestFirst, AutoReplenishment = true
});
```

(As built: the approved text had a bucket of 5 refilled 5 a second, which can let 10 through in one second. See
section 3.12.)

- **5 a second (OQ-1).** Half of PluralKit's published 10 for reads, because the docs don't say whether the limit is
  per IP or per token, and the limit can change. The old numbers (2 a second, and 4 per 2 seconds before that) were
  PluralKit's published limit when the Polly limiter was set up; it has since been raised.
- **A queue of 50**, so the longest wait is about 10 s at 5 a second: Q24's bound. A lookup past that gets "queue
  full" at once (section 3.4) and the delete is logged as an ordinary one, as today.
- **One limiter, owned by `LivePluralKitIO`** (a singleton). The live capability acquires before each attempt, so a
  retry waits its turn too. The acquire takes the run's token, so shutdown cancels a waiting lookup.
- **Does the wait hold up other events?** It shouldn't: DSharpPlus 5 runs each event's handlers on their own task.
  The integration test for KI-111 checks this indirectly (five deletes, all linked, inside the cap). If a wait does
  block dispatch, that's a DSP- entry and OQ-1 is revisited.

### 3.6 Retry and the cap

```csharp
public static class PluralKitRetry
{
    /// <summary>Two retries at about 0.5 and 1 s with jitter.</summary>
    public static Schedule Reads { get; }

    /// <summary>The whole lookup, queue waits included. Past it: Unavailable, and the delete is logged as usual.</summary>
    public static readonly TimeSpan Cap = TimeSpan.FromSeconds(15);
}
```

- **The `HttpClient` timeout is 5 s** per attempt (today: the standard handler's 10 s attempt, 30 s total).
- **Why a retry at all**: a single 502 today turns PluralKit's own delete into a false "deleted by member" log. One
  or two quick retries remove most of those.
- **Why a cap**: the queue (≤10 s) plus three 5-second attempts could reach 27 s. A delete log that late is still
  right, but it ties up a handler for no gain. 15 s covers a full queue plus one slow attempt.
- **What goes:** `AddStandardResilienceHandler` on the PluralKit client (its retry, attempt timeout, total timeout
  and circuit breaker) and the `HttpRateLimiterStrategyOptions` wrapper. The other named client keeps its handler.
  `Polly` stays referenced for `DiscordRetryPolicy`.

### 3.7 `ProxyAuthor` (LOG-3)

In `Grimoire/Features/Logging/MessageLogging/`:

```csharp
/// <summary>The account and PluralKit ids behind a proxy, from its stored ProxiedMessageLink.</summary>
public sealed record ProxyAuthor(UserId OriginalUserId, PluralKitSystemId SystemId, PluralKitMemberId MemberId);
```

- `DeleteMessageEvent.Response` and `UpdateMessageEvent`'s projection get `ProxyAuthor? Proxy`, projected as
  `m.ProxiedMessageLink == null ? null : new ProxyAuthor(...)`, replacing the three nullables.
- `AddMessageAuthorFields(UserId author, ProxyAuthor? proxy)`: "Author" alone, or "Original Author", "System Id" and
  "Member Id". `OrPrivate` is deleted: the link's ids are required and non-blank, so its "Private" arm can't run
  (Q37 keeps them required).
- The avatar lookup uses `proxy?.OriginalUserId ?? author`, as today.
- LOG-3's other parts (the positional `Response`, `AttachmentDto` → `AttachmentUrl[]`) are left to 3.10, which
  rewrites the projection for Dapper anyway.

### 3.8 Configuration (KI-101)

```csharp
/// <summary>PluralKit's settings, read once at startup.</summary>
public sealed record PluralKitOptions(Uri Endpoint, string UserAgent, string Token)
{
    /// <summary>
    ///     Right when every key is set and the endpoint is an absolute http(s) URL. Otherwise the keys that are
    ///     missing or wrong, for the one startup warning.
    /// </summary>
    public static Either<Seq<string>, PluralKitOptions> From(IConfiguration configuration);
}
```

- **Required:** `pluralkitApiEndpoint`, `pluralkitUserAgent` and `pluralkitToken` (OQ-2). A blank value counts as
  missing. The endpoint gets a trailing `/` if it lacks one, so `messages/{id}` resolves under `/v2/` and not beside
  it.
- **Off:** `IPluralKitIO` is `DisabledPluralKitIO` (`IsEnabled = false`), and the named client isn't registered. One
  warning at startup: "PluralKit integration is off: pluralkitApiEndpoint is missing." (it names each key). This
  replaces today's "UserAgent or Pluralkit Token Not Present" text; XC-06's test matches the new text.
- **On:** the client is registered from the parsed options, so `ThrowIfNullOrEmpty` and `new Uri(...)` in the
  registration go, and the `PluralkitService` constructor's own config read goes.
- Parsing is pure (`From` reads only the given configuration) and unit-tested per key.

### 3.12 As built (2026-11-16)

Where the code differs from the approved text above, and why:

- **The bucket's shape.** A bucket of 5 refilled 5 at a time lets 10 lookups into one second when the refill lands
  mid-second, which is PluralKit's whole limit (`LivePluralKitTests` measured 10). It's built as **one token every
  200 ms with a burst of 2**: still 5 a second on average, never more than 7 in any second, and a queue of 50 is
  still about 10 s. OQ-1's numbers (5 a second, about 10 s of queue) hold.
- **The fallback is an effect, not the bridge.** `DeletedMessageLookup<RT>.Run` (`Features/Shared/PluralKit/`) does
  section 3.4's logging, the alert and Q37's Debug line, and answers `NotProxied` for any failure but cancellation.
  So it's unit-tested against the fakes, and 3.10 calls it directly. The bridge (`PluralkitService.Lookup`) only runs
  it, with the application's stopping token.
- **A defect from PluralKit** (any other status, or an unexpected exception) is logged at Error with a Warning
  alert, then answered `NotProxied` like the rest, so it never costs the delete log (I-3).
- **No `PluralKitFailure` record.** The live capability reads the status and body itself, so the decision is two
  pure functions: `PluralKitErrors.FromResponse(status, body)` and `Classify(exception, token)`. The problem is a
  `PluralKitProblem` on the `PluralKitCallException` that every error keeps.
- **`IPluralKitIO` has a `Cap`**, so a unit test can shorten it. language-ext's `Timeout` ends a run that's too slow
  as `Errors.Cancelled`, not `Errors.TimedOut`, so `PluralKit<RT>` tells the cap from shutdown by the run's own token:
  cancelled means shutdown, anything else is `TooSlow`.
- **The settings are read when the capability is first resolved**, not when `AddGrimoire` registers it. Tests add
  configuration after `AddGrimoire`, and a value read at registration would miss it. The `HttpClient` is configured
  from the same parsed settings, so it never throws. The User-Agent and Authorization headers are added without
  validation, so an unusual user agent can't throw either.
- **`FakePluralKit` matches `messages/{id}` under any base path** (the live tests use `/v2/`), records arrival times
  for the bucket test, and can delay answers.
- **`FinShouldExtensions` gained `ShouldBeSome`** for `Option`.

## 4. Edge cases

| Case | What happens | Error case |
|---|---|---|
| PluralKit not configured, or a key blank | Off. One startup warning naming the keys. No lookup, no client | — |
| Only the endpoint missing (KI-101) | Off, as above. The delete is logged | — |
| The endpoint lacks `/v2/` or the trailing `/` | `/` is added. A wrong path answers 404 without 20006: Warning per lookup (OQ-4: and one alert) | `Unavailable`, not transient |
| A message over 60 s old is deleted | Not asked; logged as usual | — |
| PluralKit doesn't know the message (a plain delete) | `NotProxied`; logged as usual | — |
| PluralKit deletes an original it proxied | `ReplacedByProxy`; linked, not logged | — |
| …and the member behind it was deleted (Q37) | `ReplacedByProxyOfDeletedMember`; not logged, no link, Debug line | — |
| The proxy itself is deleted within 60 s | `IsTheProxy`; logged as usual, the stored link names the author | — |
| Five proxies in one second (KI-111) | Two at once, three queued, all answered within about a second; all linked, none logged | — |

| A 502, then success | Retried; the link is saved | — |
| PluralKit down (5xx or timeouts) | Three attempts, then logged as an ordinary delete, Information. At most 15 s | `Unavailable`, transient |
| A 429 | Retried on the schedule; Warning, since the bucket should prevent it | `Unavailable`, transient |

| Shutdown while a lookup waits in the queue | Cancelled; the handler's run ends as cancelled | `Errors.Cancelled` |
| The link's original row doesn't exist (purged, never logged) | Unchanged until 3.10: the FK catch logs and moves on | — |
| A proxy edited (the edit log) | No lookup; the stored link gives `ProxyAuthor` | — |

## 5. UX suggestions

- **Suggested:** none for moderators. The visible change is that proxies sent in a burst no longer show up as
  "Message deleted" by the member (KI-111), and a deleted member's proxies don't either (Q37). Both are fixes.
- **Suggested:** the startup warning names the missing keys ("PluralKit integration is off: pluralkitToken and
  pluralkitApiEndpoint are missing.") instead of today's fixed text, so whoever deploys knows what to set.
- **Behaviour a user might notice:** in a large burst, a delete log can now arrive up to about 10 s late (the queue),
  where today it arrived at once but could be wrong. That's Q24's trade.

None. 1.5 adds no statement. The link insert moves to Dapper with `ON CONFLICT DO NOTHING` in 3.10.

## 7. Telemetry

None in 1.5: OpenTelemetry comes in 1.6. 1.5 prepares for it:

- **The operation name** `PluralKit.GetMessage` is 1.6's span name. Tags: the outcome (`NotProxied`,
  `ReplacedByProxy`, …, or the error case), the HTTP status, PluralKit's code, the attempt number and the queue wait.
  Never the message content, and not the system or member id (defect 9: they identify a person).
- **The queue:** `LivePluralKitIO` exposes the limiter's `GetStatistics()` (queued count, available tokens, total
  failed leases) for the plan's "PluralKit queue" gauge, and "queue full" refusals become a counter.
- **The retry** in `PluralKit<RT>` is where 1.6 counts retries (`grimoire.pluralkit.retries`).

What a failure looks like in 1.6: the delete event's root span with outcome success, a child span
`pluralkit PluralKit.GetMessage` with three attempts, status 502 on each and a queue wait of 0, and the delete log
posted as an ordinary one.

## 10. Decisions (owner, 2026-11-16)

| # | Question | Decision |
|---|---|---|
| OQ-1 | **The bucket's numbers.** PluralKit publishes 10 a second for reads, without saying per what. SH-2 proposed 2 a second with a queue of 20. | **5 a second, a queue of 50** (about 10 s, Q24's bound). The owner: the published limit was 2 a second (and 4 per 2 seconds before that) when the Polly limiter was set up, which is why the code differs; it is now 10 a second for reads, and capping at half is a safe margin. |
| OQ-2 | **Is the token required?** PluralKit's docs don't say the message endpoint needs one. | **Required.** The owner believes the endpoint needs it. PluralKit stays off without it, as today. |
| OQ-3 | **A circuit breaker.** Polly's goes with the resilience handler. Without one, during a PluralKit outage each quick delete waits up to 15 s before it's logged. | **No breaker.** The cap bounds the wait, deletes are rare per second, and nothing piles up. Add one (an `Atom` of recent failures, C6) only if an outage shows a problem. |
| OQ-4 | **Alert on a refusal or a bad endpoint?** A 401, 403, 400 or a bare 404 won't fix itself, and today it's an Information line on every delete. | **One Warning alert** (the daily report's buffer, so it doesn't repeat), plus the Warning log per lookup. Transient failures and "queue full" only log. |
| OQ-5 | **Bridge or port now?** The rest of `DeleteMessageEvent` (EF, the audit log, the embed) belongs to 3.10. | **Bridge** (section 3.9), as 1.4 did for the guild log. 3.10 ports the handler and deletes the bridge. |
| OQ-6 | **A deleted member's original (Q37): a Debug line, or nothing?** | **Debug**, with the message id, so a missing delete log can be explained from the logs. |
