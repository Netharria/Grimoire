# Spec 2.0: One migration chain

Status: **implemented and committed 2026-11-19 (94d2809).** Approved 2026-11-19: the owner took the suggested answer to all
four open questions (section 10). Tests: unit 812 (1 skipped), integration 1455 (39 skipped, unchanged). Build warnings:
134, unchanged (same codes per project as before). Section 11 lists the results and where the code differs from this
text.

Implements the plan's section 2.0 and settled conflict C12: both schemas, `public` and `Settings`, are migrated by one
migrations-only context, as one ordered chain. Then a data copy always runs before the drop or rewrite that depends on
it, and the order no longer rests on startup code calling two contexts in the right sequence.

**What is already true, found while writing this spec.** Both contexts already record their migrations in the same
table, `public."__EFMigrationsHistory"`. `SettingsDbContext` sets `HasDefaultSchema("Settings")`, but nothing sets a
history table, so EF writes the unqualified name and the search path resolves it to `public`. This was checked by
running the Settings chain on a scratch database, and `StartupMigrationTests` already notes it. So 2.0 doesn't merge
two histories. It merges two **chains**: today each context only knows its own migrations, and the order between them
(the whole Grimoire chain first, then the whole Settings chain) exists only in `DiscordStartService`. The plan's C12 and
2.0 wording is corrected to say this (section 9).

## 1. Scope

**In scope**

- **A migrations-only context**, `GrimoireMigrationsDbContext`, in a new project `Grimoire.Migrations` (OQ-1). Its
  model is the union of the two runtime models, built by the same code that builds them (section 3.2), so the three
  can't drift apart.
- **The migrations move.** All 21 Grimoire migrations and all 5 Settings migrations move into `Grimoire.Migrations`
  with their ids unchanged (OQ-4). Only their `[DbContext]` attribute and namespace change. `main`'s 10 deployed
  migrations keep their ids and their `Up` and `Down` code exactly, so production's history rows still match them.
- **One model snapshot**, the union of today's two, checked by `dotnet ef migrations has-pending-model-changes`.
- **Startup migrates once**, through the new context, with P-3's 30-minute command timeout.
  `SettingsServiceRegistration.MigrateSettingsDb` is deleted.
- **The runtime contexts lose their migrations.** `GrimoireDbContext` and `SettingsDbContext` keep running queries
  until their features are ported (Phase 5), but have no `Migrations` folder and no snapshot, and nothing migrates
  them.
- **Proof of equivalence** (section 8): the merged chain produces the same SQL, the same schema, and, on a copy of
  production, the same data as today's two chains run in startup order.
- **Tests and tooling:** both integration fixtures and `StartupMigrationTests` migrate through the new context. The
  solution files, CLAUDE.md's commands and the 2.1 copy runbook are updated.

**Decisions this implements:** C12, and through it P-7's trap (a later drop of the legacy tables can't run before
Settings `Initial`'s copy, because both are in one ordered chain).

**Out of scope**

- **Editing any migration's content.** That is 2.2 (Settings), 2.3 (Grimoire) and later. 2.0 moves code; it changes no
  SQL. The equivalence checks depend on that.
- **Squashing the post-`main` migrations** (OQ-2). 2.0 keeps every step; whether to squash before the deploy is
  decided after 2.3.
- **Removing the runtime contexts.** That is Phase 5, which then moves all EF code into `Grimoire.Migrations` (plan,
  owner 2026-11-19).
- **The legacy tables' drop (P-7).** It stays in a later release (Q10); 2.0 only makes its order safe.

## 2. Flow

### 2.1 Startup, after 2.0

1. `DiscordStartService.StartAsync` calls `MigrationRunner.ApplyPendingAsync` (effect: database).
2. It creates a `GrimoireMigrationsDbContext` over the host's `NpgsqlDataSource`, with no retrying execution strategy
   (a failed migration is rolled back and the host exits; retrying it in a loop helps nothing).
3. `GetPendingMigrationsAsync` (effect): the chain's migrations whose ids aren't in `__EFMigrationsHistory`, in id
   order. On production today that is the 16 post-`main` migrations, interleaved by id.
4. If any are pending: set the command timeout to 30 minutes, `MigrateAsync` (effect), and log once at Warning:
   "Applied pending migrations in N ms". Otherwise do nothing.
5. On a failure the exception propagates, the host stops, and the bot doesn't come online (unchanged from today,
   XC-24).

### 2.2 The order of the chain

EF applies migrations in id order, and every id starts with its timestamp. With the ids unchanged, the merged
post-`main` chain is:

| # | Migration | From |
|---|---|---|
| 1 | `20251025193658_LeaderboardView` | Grimoire |
| 2 | `20260524033203_ModelRedesign` | Grimoire |
| 3 | `20260524035623_Initial` (copies the legacy settings out of `public`) | Settings |
| 4 | `20260524202942_DropOrphanedCustomCommandGuildFKs` | Grimoire |
| 5 | `20260524223710_FixMessageHistoryContentProperty` | Grimoire |
| 6 | `20260919222329_AddAlertOccurrences` | Grimoire |
| 7 | `20260919233857_AddDiagnosticsIgnoredItems` | Settings |
| 8 | `20260920001445_AddMuteRoleToMutes` | Settings |
| 9 | `20261025042202_DropOrphanedLegacyForeignKeys` | Grimoire |
| 10 | `20261025042846_SyncIndexesWithModel` | Grimoire |
| 11 | `20261025043315_AddReactionModel` | Grimoire |
| 12 | `20261025044354_RequirePardonModerator` | Grimoire |
| 13 | `20261108170839_RenameAttachmentFileNameToAttachmentUrl` | Grimoire |
| 14 | `20261109022034_DropRedundantIndexes` | Grimoire |
| 15 | `20261109022050_DropRedundantIndexes` | Settings |
| 16 | `20261110232856_AddClosedAtToLocksAndMutes` | Settings |

This differs from today's startup order: Settings `Initial` now runs third instead of twelfth. That is safe only if
nothing in rows 4 to 14 changes what `Initial` reads. Three of them touch the legacy settings tables, and only with
`DropForeignKey` (rows 4 and 9: 58 in all), `DropIndex`, `CreateIndex` and one `DropUniqueConstraint` (row 10). The
others don't touch them. `Initial`'s `SELECT`s depend on none of that. Section 8's data check on the copy of
production proves it rather than trusting the reading.

### 2.3 The change itself

All of it is mechanical, in this order, so each step can be checked:

1. Create `Grimoire.Migrations` (section 3.1) and move the model-building code into reusable methods (section 3.2).
   Build. `has-pending-model-changes` on both runtime contexts must still report nothing: the move changed no model.
2. Move the 26 migrations and their `.Designer.cs` files. Change `[DbContext(typeof(...))]` to the new context, and
   the namespace to `Grimoire.Migrations.Migrations`. The two `DropRedundantIndexes` classes would collide, so the
   Settings one becomes `DropRedundantSettingsIndexes`. The class name isn't stored anywhere; the `[Migration]` id is.
3. Write the merged snapshot: the Grimoire snapshot's entities plus the Settings snapshot's, each Settings table with
   `ToTable(name, "Settings")`. Then `has-pending-model-changes` on the new context must report nothing.
4. Switch startup and the tests to the new context, delete the old `Migrations` folders and `MigrateSettingsDb`.
5. Run section 8's checks.

## 3. Types

### 3.1 The project

`Grimoire.Migrations` references `Grimoire.Data` and `Grimoire.Settings`, and holds the EF `Design` and `Tools`
packages, which the two runtime projects then drop. `Grimoire` (the host) and `Grimoire.IntegrationTests` reference
it. It links `StronglyTypedIdConventions.cs` like `Grimoire.Settings` does, since the conventions class is `internal`
to each assembly that compiles it.

### 3.2 One model, three contexts

```csharp
// Grimoire.Data: the body of today's OnModelCreating and ConfigureConventions, unchanged, made callable.
public static class GrimoireModel
{
    public static void Configure(ModelBuilder modelBuilder);           // entities + ApplyConfigurationsFromAssembly
}

// Grimoire.Settings: the same for Settings. HasDefaultSchema("Settings") becomes an explicit schema on each of its
// entities, so the merged context's default schema stays public. The table mapping is identical; Settings has no
// sequences, which are the other thing a default schema decides.
public static class SettingsModel
{
    public const string Schema = "Settings";
    public static void Configure(ModelBuilder modelBuilder);
}

// Grimoire.Migrations: migrations only. Never queried.
public sealed class GrimoireMigrationsDbContext(DbContextOptions<GrimoireMigrationsDbContext> options)
    : DbContext(options)
{
    protected override void ConfigureConventions(ModelConfigurationBuilder builder)
        => builder.ConfigureStronglyTypedIds();
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        GrimoireModel.Configure(modelBuilder);
        SettingsModel.Configure(modelBuilder);
    }
}

public static class MigrationRunner
{
    public static readonly TimeSpan CommandTimeout = TimeSpan.FromMinutes(30);   // moved from SettingsServiceRegistration
    public static Task ApplyPendingAsync(NpgsqlDataSource dataSource, ILogger logger, CancellationToken token);
}
```

`GrimoireDbContext.OnModelCreating` becomes `GrimoireModel.Configure(modelBuilder)`, and `SettingsDbContext`'s becomes
`SettingsModel.Configure(modelBuilder)`. The runtime contexts keep their `DbSet`s. Every entity type a `DbSet`
discovers today is registered explicitly in `Configure`, so the merged context, which has no `DbSet`s, sees the same
types.

No new error cases: a migration failure is an exception at startup, before any `Eff` runs, as today.

## 4. Edge cases

| Case | What happens |
|---|---|
| Production, at `main`'s `SpamFilterOverrides` | Its 10 history rows match the chain's first 10 ids. The 16 post-`main` migrations are pending and run in section 2.2's order. |
| A dev or test database that already ran today's chains | Every id is in the history, so nothing is pending. (Dev databases are rebuilt after 2.2 and 2.3 anyway, Q6.) |
| A database partway through today's chains | The pending set is whatever is missing, in id order. Only possible on a dev database, and it would then run a Settings migration before a Grimoire one in a different order from today. Rebuild it instead; no shipped database is in this state (production is at `main`). |
| An empty database | All 26 migrations run in id order. Settings `Initial`'s copy finds no legacy tables (`IF EXISTS`) and copies nothing, as today. |
| A migration fails | It rolls back, the host exits, and the bot doesn't come online. Unlike today, there's no "Grimoire succeeded, Settings not attempted" split: the chain stops at the failed migration, whichever schema it touches. Fix and restart; the rest apply. |
| Someone runs `dotnet ef migrations add` against a runtime context | It would recreate a `Migrations` folder in `Grimoire.Data` or `Grimoire.Settings`. A test fails if either runtime context has any migrations (section 8), and CLAUDE.md's command names the new context. |
| `dotnet ef database update --context GrimoireDbContext` | "No migrations were found." Nothing happens. |
| The runtime models drift from the merged one (a configuration change in one place) | They can't drift silently: all three run the same `Configure` methods, and a test diffs each runtime model against the merged one (section 8). |
| The legacy-table drop in a later release (P-7) | It gets a later id than `Initial`, so it can't run before the copy. P-7's trap is closed. |

## 5. UX suggestions

None: nothing a user sees changes. One log change, which only the owner sees: startup writes one line, "Applied
pending migrations in N ms", where today it writes a second one for the settings chain.

## 6. SQL

None new. 2.0 moves code and changes no statement, so the generated SQL must equal today's (section 8, check 1).

## 7. Telemetry

None. Migrations run at startup, before the boundaries that open spans, and 1.6 added no telemetry for them. The
Warning log line with its duration stays, as one line instead of two.

## 8. Tests

**Equivalence checks** (run once, results in the commit message and the section's notes):

1. **The SQL is the same.** `dotnet ef migrations script 20250705185227_SpamFilterOverrides` on the new context, against
   today's two scripts (2.1's C-1) merged in id order. The diff must be empty except for the order of whole
   migrations. This is the strongest check: it compares exactly what would run on production.
2. **The schema is the same.** On two empty databases, run today's two chains in startup order on one, and the merged
   chain on the other. `pg_dump --schema-only` of both must be identical.
3. **The data is the same.** On two clones of the local production restore (2.1's runbook), run the old order and the
   new one. `pg_dump --data-only` of both schemas must be identical. This proves section 2.2's reading that moving
   Settings `Initial` earlier changes nothing it copies.
4. **The model is the same.** `has-pending-model-changes` reports nothing on the new context.

**Unit test** (`Grimoire.UnitTests`, no database: EF builds models without a connection):

- `MigrationModelTests.EachRuntimeModel_IsTheMergedModelsSlice`. The EF model differ, run from each runtime context's
  relational model to the merged one, produces only `CreateTable` operations (and `EnsureSchema`) for the *other*
  schema's tables, and nothing for its own.
- `MigrationModelTests.TheRuntimeContexts_HaveNoMigrations`. `GetMigrations()` is empty for both runtime contexts.

**Integration tests kept and changed:**

| Test | Change |
|---|---|
| `GrimoireCoreFactory` and `SettingsTestsFactory` | Migrate once through `GrimoireMigrationsDbContext` instead of through each runtime context. Two fixtures and two containers stay (OQ-3). |
| `StartupMigrationTests.OnAnEmptyDatabase_AllMigrationsAreApplied_AndTheBotWorks` (XC-20) | Checks the merged context has nothing pending, and one migration log line. |
| `StartupMigrationTests.OnADatabaseOneMigrationBehind_TheLastMigrationIsApplied` (XC-21) | One migration behind on the chain, not on each schema. |
| `StartupMigrationTests.AddClosedAt_…` | Migrates the merged chain to the step before `AddClosedAtToLocksAndMutes`. TD-1 replaces this migration in 2.2, which then deletes or rewrites the test. |
| New: `StartupMigrationTests.SettingsInitial_RunsBeforeEveryLaterGrimoireMigration` | Asserts the chain's order (section 2.2) by id, so a renamed id that moved `Initial` would fail. |

**Old tests mapped:** no logic tests move; this is infrastructure. XC-24 and XC-25 (a failing Grimoire or Settings
migration) become one case, "a failing migration stops the chain", in `09-cross-cutting.md`.

**Mutation testing:** not applicable. The new unit tests guard models, not logic, and Stryker only mutates logic.

## 10. Decisions (owner, 2026-11-19)

| # | Question | Decision (the suggested answer) |
|---|---|---|
| OQ-1 | **Where does the migrations context live?** (a) A new `Grimoire.Migrations` project referencing both. (b) Inside `Grimoire.Data`, which then references `Grimoire.Settings`. | **(a).** It keeps migrations-only code out of the runtime projects, which Phase 5 then leaves untouched, and avoids a `Data → Settings` dependency that only migrations need. |
| OQ-2 | **Squash the 16 post-`main` migrations into one?** One migration would make the first deploy all-or-nothing (one transaction), but it reverses Q6's "no squash" and loses the steps 2.2 and 2.3 are about to edit. | **Not in 2.0.** Keep the steps so 2.2 and 2.3 can edit them, and decide after 2.3. 2.0's implementation checks one fact for that decision: whether EF 10's `MigrateAsync` runs all pending migrations in one transaction or one each (today's XC-24 suggests one each). |
| OQ-3 | **One test fixture or two?** The plan's row said one. Today `"Test collection"` (94 classes) and `"Settings collection"` (14) each have their own Postgres container and run in parallel. | **Keep two.** Both migrate through the merged chain, which gives the single ordering C12 is after. Merging them would make the 14 settings classes wait in line behind the harness tests, for no gain in correctness. |
| OQ-4 | **Keep the migration ids, or renumber?** Keeping them interleaves Settings `Initial` after `ModelRedesign` (section 2.2). Renumbering the Settings migrations to sort after every Grimoire one would copy today's startup order exactly. | **Keep them.** Renumbering would make every dev database re-run migrations it already has. Section 8's data check proves the interleaved order gives the same result. If it doesn't, renumbering is the fix, and it's allowed (nothing past `main` is deployed). |

## 11. Results and differences from the spec

**Equivalence (section 8), all four pass:**

1. **SQL.** The merged chain's script and today's two scripts, cut into per-migration blocks (each is one transaction):
   the same 26 ids, every block byte-identical, the merged script in id order, the same history table.
2. **Schema.** An empty database migrated through EF's runner (`dotnet ef database update`), the old way (Grimoire then
   Settings) and the new way: `pg_dump --schema-only` identical (34,623 bytes). The old full Grimoire script can't run
   through `psql` (one of `main`'s migrations ends a raw SQL statement without `;`, which EF's runner doesn't need), so
   both sides used the runner.
3. **Data.** Two clones of the local production restore, migrated from `main` by the old two scripts and by the merged
   one: schemas identical, and data identical except 507 timestamps that `ModelRedesign` stamps with `now()`, masked
   for the comparison. Section 2.2's reading holds: moving Settings `Initial` earlier changes nothing it copies.
4. **Model.** No pending changes on the new context; and each runtime model, checked against its old snapshot from
   git, has no changes either.

**OQ-2's fact:** EF 10 runs **each migration in its own transaction**. On a scratch database stopped before
`AddReactionModel`, a pardon without a moderator made `RequirePardonModerator` fail, and `AddReactionModel` stayed
applied. A failed first deploy therefore leaves the database partly migrated, and a fixed rerun continues from there.

**Where the code differs from the text:**

- **No renames, and the namespaces stay.** The Grimoire migrations keep `Grimoire.Migrations`, the Settings ones keep
  `Grimoire.Settings.Migrations`, so the two `DropRedundantIndexes` classes don't collide and each file changes only its
  `[DbContext]` line. The Settings migrations are in `Grimoire.Migrations/Migrations/Settings/`.
- **`MigrationRunner` takes the context factory** (`IDbContextFactory<GrimoireMigrationsDbContext>`, registered by
  `AddMigrations()`), not the data source: EF's tools find a context through the host's dependency injection.
- **Two runtime model details had to be copied for the merged model** (`Grimoire.Data/Conventions/EntitySetConventions.cs`,
  linked into Settings):
  - Almost every table is named after its `DbSet` property, which the merged context doesn't have. `AddEntitySetsOf`
    and `NameTablesAfterEntitySetsOf` register those types and names, at convention level so a configuration's
    `ToTable` still wins, and skip the view-mapped `LeaderboardView`, as EF does.
  - **EF makes key and index names unique across the whole model, ignoring schemas.** Three Settings tables share a
    name with a legacy `public` table (`Mutes`, `Rewards`, `SpamFilterOverrides`), so in the merged model one side got
    `PK_Mutes1`, `IX_Mutes_EndTime1` and so on, names the database doesn't have. `MigrationModelTests` caught it.
    `FixConstraintNames` names every key, index and foreign key explicitly with the name it already has, on both
    sides. A first version used EF's *default* names and overwrote the two explicit `IX_Sin_…` index names. The unit
    test couldn't see that, because both sides ran the same code, but the old-snapshot check did. From now on,
    `has-pending-model-changes` on the merged snapshot guards such shared changes.
- **The unit tests** are in `Grimoire.UnitTests/Database/MigrationModelTests.cs`: one slice test per runtime model,
  plus the no-migrations check. A failure lists the operations that differ.
- **The order test** is named `SettingsInitial_RunsStraightAfterModelRedesign`.
- **Design-time packages** (`Microsoft.EntityFrameworkCore.Design`, `.Tools`) moved from the runtime projects to
  `Grimoire.Migrations`.
