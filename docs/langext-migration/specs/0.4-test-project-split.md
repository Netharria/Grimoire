# Spec 0.4: split unit and integration tests, and fix Stryker

Status: **implemented 2026-11-14.** Tests before and after: 1814 (39 skipped). The unit project has 430 tests (1 skipped), the integration project 1384 (38 skipped), with no failures. Stryker baseline in section 5.

## 1. Scope

- **What moves:** the tests move to two projects, `Grimoire.UnitTests` and `Grimoire.IntegrationTests`. They're moved, not rewritten.
- **Projects that go:** `Grimoire.Tests`, `Grimoire.Settings.Tests` and `Grimoire.Domain.Test.Unit`. Their tests move.
- **Stryker:** set it up so it finishes, and runs only against the unit project.
- **Out of scope:**
  - moving logic tests out of the fake-Discord harness, which happens per feature in Phase 3;
  - new tests;
  - the move from Grimoire `Result` to language-ext (1.1).

## 2. Why Stryker never finished (findings, 2026-11-14)

1. **Wrong test runner.** Stryker 5.0.0 defaults to `vstest`. The repo runs on Microsoft Testing Platform (`global.json`
   `test.runner`, xunit v3 4.0.1).
   - With `vstest` on `Grimoire.Domain.Test.Unit`, Stryker finds the 139 tests, but coverage capture fails and no
     mutant is killed (score 0%). The run finishes only because that project is tiny.
   - With `--test-runner mtp`, the same project finishes in **9 s**: 87 killed, 17 survived, 67 not covered, 56 compile
     errors, score 50.9%. The trial reports are in the session scratchpad, not the repo.
2. **Mutating against the whole harness.** Since 2026-10-25, `Grimoire.Tests` holds about 877 fake-Discord tests. Each
   one starts a bot host and a Postgres container. The April/May runs that finished came before the harness existed.
   Every November run left an empty output folder. Stryker runs the tests once per mutant group, and runs them
   in parallel (16 cores here). So even with a working runner, that project is hours per pass.
   - The owner's logs show the November runs **never left the initial test run** (no mutation started) in 8 hours,
     so it's a hang, not slowness. See section 2a.
3. **Stryker on a test project only ever ran on the project it references.** Pointed at `Grimoire.Tests`, it mutated
   `Grimoire` with every DB and harness test as its test set.

## 2a. The hang, confirmed 2026-11-14

Reproduced with `dotnet stryker -p Grimoire.csproj` on `Grimoire.Tests` (the default `vstest` runner). The initial run
started 1361 tests, ran for about 8 s, and then sat idle at 2% CPU. A `dotnet-stack` dump of the test host shows a
lock-order deadlock between two threads:

- **Thread A**, xunit finishing a test: `JsonReporterMessageHandler` → `ConsoleRunnerLogger.LogImportantMessage`, which
  **holds** xunit's console-logger lock → `Console.Out.WriteLine` → **waits** for the console stream lock.
- **Thread B**, a DSharpPlus event-handler error logged by the test bot: Serilog `ConsoleSink` → `Console.Out`
  (`SyncTextWriter`, **holding** the console lock) → `[assembly: CaptureConsole]`'s `ConsoleCaptureTestOutputWriter` →
  `TestOutputHelper` → the message bus → `ConsoleRunnerLogger`, which **waits** for xunit's lock.

The JSON console reporter only runs when xunit v3 is launched in the `@@` mode that vstest and Stryker use. Plain
`dotnet test` on Microsoft Testing Platform doesn't use it, which is why normal runs finish. `Grimoire.Settings.Tests`
has neither `CaptureConsole` nor Serilog, so it isn't affected.

Fix, in step 2 below: the test bot's Serilog writes to `TestContext.Current.TestOutputHelper` through a small sink,
next to `TestLogSink`, instead of `WriteTo.Console`. `[assembly: CaptureConsole]` is removed. Failure output still shows
the bot's log lines, and nothing in a test writes to the real console while xunit holds its lock. Integration tests
never run under Stryker anyway, but this also keeps vstest-based runners (IDEs) from hanging.

Fix: Stryker uses `mtp`, and runs only `Grimoire.UnitTests`. Integration tests never run under Stryker. Mutation
scores then measure the unit tests, which is where Phase 3 moves the logic.

- **Both projects reference** `Grimoire`, `Grimoire.Domain` and `Grimoire.Settings`.
- **`InternalsVisibleTo`:**
  - `Grimoire.Domain`, `Grimoire.Settings` and `Grimoire` replace the three old test names with the two new ones.

  `using Grimoire.IntegrationTests.FakeDiscord;` lines. Files are moved with

### Shared helpers

`ResultShouldExtensions` is used on both sides, and the two existing copies differ: the Grimoire one adds
`ShouldBeSetOrUnchanged`. Keep the Grimoire copy as one file in `Grimoire.UnitTests`, in namespace `Grimoire.TestShared` (a global using in both projects). The integration project includes
it with `<Compile Include=… Link=…>`, not a third project. Section 1.1 replaces it with `Fin` assertions anyway.
`AlertTestHelpers.cs` is shared the same way: five integration tests use its `ManualTimeProvider`. `DiagnosticsTestData`
is used only by unit tests.

## 4. Steps

1. Create the two projects, with the packages above, and add them to `Grimoire.sln`.
2. Move the files with `git mv`, and fix namespaces and `global using`s. Replace the test bot's `WriteTo.Console` with
   a test-output sink, and drop `[assembly: CaptureConsole]` (section 2a).
3. Point `InternalsVisibleTo` at the new names, and remove the three old projects from the solution and disk.
4. Build. Then run each project. The test counts must add up: unit tests plus integration tests equal the count before
   the move, with the same skips.
5. Stryker config (section 5). Run it on the unit project to check it finishes, and record the baseline score.
6. Update the docs (section 8).

## 5. Stryker setup

`stryker-config.json` at the repo root points at **`Grimoire.Mutation.sln`**. That's a second solution holding the four
production projects and `Grimoire.UnitTests` only. In solution mode Stryker ignores `test-projects` and runs every test
project in the solution: against `Grimoire.sln` it captured coverage over both assemblies, about 11 minutes per pass
and one pass per production project. It doesn't accept `.slnf` filters ("Given path is not a solution file"). **A new
production project must be added to both solutions.**

```json
{
  "stryker-config": {
    "solution": "Grimoire.Mutation.sln",
    "test-projects": [ "Grimoire.UnitTests/Grimoire.UnitTests.csproj" ],
    "test-runner": "mtp",
    "mutate": [ "!**/Migrations/**", "!**/Configuration/**", "!**/*.Designer.cs" ],
    "reporters": [ "html", "progress", "cleartext" ],
    "thresholds": { "high": 80, "low": 60, "break": 0 }
  }
}
```

- **Solution mode** mutates every production project (Domain, Settings, Grimoire, Data), using the unit tests only.
  The Data project then reports mostly "no coverage", which is correct: its tests are integration tests.
- **Day-to-day runs** use `dotnet stryker --since:main` (only the changed code), plus
  `--mutate "Grimoire.Domain/**"` style filters to focus on one area.
- **Score target:** `break: 0` for now, so a low score never fails a run. Phase 3 can raise it per area once logic has
  moved to unit tests.
- **MTP runner warning:** Stryker 5 calls the MTP runner "preview". If a run misreports, the first check is
  `-V trace -L` and the report's per-mutant test list.
- **`StrykerOutput/`** goes into `.gitignore`, and the 18 old run folders are deleted (they are local only).

**Baseline, 2026-11-14** (whole solution, 40 s):

| Mutants | Count |
|---|---|
| Created | 9529 |
| Excluded by the `mutate` filter (mostly migrations) | 3877 |
| Compile errors (Stryker's safe mode, mostly CS0165 unassigned locals) | 1510 |
| Not covered by a unit test | 2727 |
| Ignored (block already covered, excluded from coverage) | 728 |
| Tested | 687: 529 killed, 158 survived |

That gives a **score of 15.5%**. Of the mutants the unit tests cover, 77% are killed. The low overall score is expected:
most logic is still tested only through the integration harness, and Phase 3 moves it.

## 6. Edge cases

| Case | Handling |
|---|---|
| A test the sorting puts in Unit secretly needs Docker | It fails to compile without the packages, or fails at runtime with no Postgres. Move it to Integration and note it in the PR. |
| Integration test fixtures collide when both old DB projects share one assembly | The two collections (`"Test collection"`, `"Settings collection"`) keep their names, and each has its own container. Parallelism across collections is unchanged. Check that the run time doesn't regress past the current total. |
| A test name that encodes an old namespace (for example an `--filter` in docs) | The docs update (section 8) changes every filter example. |
| KI-115 flake | Not fixed here. It moves with `PaginationTests` to Integration. |
| Stryker's 56 compile-error mutants on Domain | Not a blocker: Stryker drops them. Look into it after 1.1, since the language-ext types change what gets mutated. |
| No CI in the repo | CLAUDE.md says "CI checks compliance", but there is no `.github/` or other pipeline. Section 8 corrects the doc. No CI is added for now (decision 3). |
