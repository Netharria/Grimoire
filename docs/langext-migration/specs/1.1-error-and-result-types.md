# Spec 1.1: error and result types

Status: **implemented 2026-11-14, committed 2026-11-15.** Approved 2026-11-14, with the open questions decided by the owner
(section 10). Tests before and after: unit 430 → 392 (1 skipped, KI-93), integration 1384 → 1384 (38 skipped), no
failures. Build warnings: the 8 from HEAD, plus the 111 intended `FinTaskExtensions` obsolete warnings.

Implements C1 and C4 from the plan, with Q2a, Q2b/F-4, TD-5 and TD-13.

## 1. Scope

**In scope**

- Add `LanguageExt.Core` **`5.0.0-beta-78`**, pinned to that exact version, to `Grimoire.Domain`. The other projects
  get it through their reference to `Grimoire.Domain`. On 2026-11-14 the NuGet index's newest version is still
  `5.0.0-beta-78`, so the spike's version stays (plan, version pin).
- Add the four error cases (C1): `Invalid`, `NotFound`, `Forbidden` and `Unavailable`, all deriving from `Expected`.
- Delete `Grimoire.Domain.Result<T>`, `Validation<T>`, `Error`, `Unit`, `ResultCombinators`, `ResultTaskExtensions` and
  `ValidationCombinators` (C4). Every use moves to `Fin<T>`, `Validation<Error, T>` and `LanguageExt.Unit`.
- Move every smart constructor in `Grimoire.Domain` and `Grimoire.Settings/Domain` to `Validation<Error, T>` (20
  `Create` methods).
- Move the `SettingsModule` services' return types from `Task<Result<T>>` to `Task<Fin<T>>`. They stay `Task`-based
  services until 3.1 ports them to `IO`.
- Make the **mechanical** changes in the callers: `Grimoire` (about 68 files) and both test projects (about 95 files).
  Behaviour doesn't change. Section 4 lists the three exceptions.
- F-4: test assertions on `Error.Code` (54 of them) move to the case and the message.
- TD-13: `GetOrElse` is deleted with `Result`. Its calls move to an obsolete helper with the same behaviour (OQ-1).

**Out of scope**

- Runtimes, capabilities and the command, event and worker boundaries: 1.2. So the generic "[ID …]" reply and the
  alert for `Unavailable` come in 1.2. Until then the old reply helpers render each case as they render its old
  equivalent today (section 4).
- Narrowing `SettingsModule.ExecuteSafelyAsync`'s `catch (Exception)` to database exceptions: 1.3 or 3.1. In 1.1 it
  keeps its catch and produces `Unavailable` instead of `Invalid`.
- Discord lookups returning `Fin` (TD-12): 1.4.
- Porting any feature to `Eff`: Phase 3.
- `closed` hierarchies and a Grimoire base type under `Expected`: Phase 4.

**IDs covered:** C1, C4, Q2a, Q2b, F-4, TD-5, TD-13. No KIs.

## 2. Flow

1.1 adds no runtime flow. What changes is the type each layer returns:

```
smart constructor           Validation<Error, T>           pure: collects every Invalid
   │  .ToFin()  (once, in the command, before any loading: Q2a)
   ▼
SettingsModule service      Task<Fin<T>>                   effect: EF + HybridCache
   │  ExecuteSafelyAsync: exception → Unavailable          (the only place an exception becomes a value)
   ▼
command or handler          Fin<T>.Match(Succ, Fail)       the old reply helpers pick the colour by case
```

- **Pure:** every `Create`, `Validation` composition, and the `ToFin()` conversion.
- **Effects:** the settings services, as today.

## 3. Types

### 3.1 The error cases

One file, `Grimoire.Domain/Errors.cs`:

```csharp
namespace Grimoire.Domain;

/// <summary>Bad input, or an action the rules don't allow. Red. The message is shown to the user.</summary>
public sealed record Invalid(string Message) : Expected(Message, ErrorCase.Invalid, None);

/// <summary>The thing asked for doesn't exist. Yellow. The message is shown to the user.</summary>
public sealed record NotFound(string Message) : Expected(Message, ErrorCase.NotFound, None);

/// <summary>Discord or a permission check refused. Red. The message names what's missing (TD-12).</summary>
public sealed record Forbidden(string Message) : Expected(Message, ErrorCase.Forbidden, None);

/// <summary>
///     A dependency is down: the database, Discord or PluralKit (Q1). The message is for the logs only. From 1.2 the
///     user sees the generic reply. <paramref name="Inner" /> keeps the exception for the log.
/// </summary>
public sealed record Unavailable(string Message, Option<Error> Inner = default)
    : Expected(Message, ErrorCase.Unavailable, Inner);

/// <summary>
///     One fixed code per case. This isn't Q2b's per-error code: the constant exists only because <c>Expected</c>
///     needs one, and language-ext's <c>Is</c> and <c>@catch</c> compare codes. Grimoire code matches on the type.
/// </summary>
internal static class ErrorCase
{
    public const int Invalid = 0x4752_0001;
    public const int NotFound = 0x4752_0002;
    public const int Forbidden = 0x4752_0003;
    public const int Unavailable = 0x4752_0004;
}
```

Rules:

- **An error is its case plus a message** (Q2b). `Code` and `Target` go. No feature adds its own `Expected` subtype in
  1.1. The only place that branches on a code today (`TextCustomCommandProcessor`) is changed so it doesn't need one
  (section 4).
- **Messages of `Invalid`, `NotFound` and `Forbidden` are user-facing**, written as the reply text. `Unavailable`'s is
  not.
- **Any other `Error` is a defect.** In practice that's an `Exceptional` from a thrown exception, or a `ManyErrors`
  that holds one. The 1.2 boundary treats it as a defect. In 1.1 no code creates one on purpose.
- **Several errors** come from `Validation<Error, _>` as `ManyErrors` (language-ext's `Error` is a monoid). The reply
  helpers render each message, with duplicates removed as `CombineErrors` does today.

### 3.2 Old to new

| Old | New |
|---|---|
| `Result<T>` | `Fin<T>` |
| `Result<T>.Ok(v)` | `Fin.Succ(v)`, or `v` through the implicit conversion |
| `Result<T>.Fail(new Error(code, msg))` | `new Invalid(msg)` (implicit conversion to `Fin<T>`) |
| `Result<T>.Fail(error)` | `Fin.Fail<T>(error)` |
| `new Result<T>.NotFound(new Error(code, msg))` | `new NotFound(msg)` |
| `new Result<T>.NotModified(…)` | **not an error any more**: see 3.3 |
| `ExecuteSafelyAsync`'s failure error | `Unavailable.From(msg, exception)`. Its parameter is now the log message, a `string` |
| `Validation<T>` | `Validation<Error, T>` |
| `Validation<T>.Succeed(v)` / `.Fail(e)` | `Success<Error, T>(v)` / `new Invalid(msg)` (implicit conversion) |
| `validation.Match(onValid, onInvalid)` | `validation.Match(Succ: …, Fail: …)`, **always with names**: v5's `Validation.Match` takes the failure first, so positional arguments can compile with the branches swapped. HEAD had 12 calls (found by renaming the old method in a scratch copy); each now names its arguments |
| `Validation.Combine(v1, v2, v3, v4)` | `(v1, v2, v3, v4).Apply((a, b, c, d) => …)` |
| `Validation<T>.ToResult()` | `.ToFin()`. Every error stays: a `ManyErrors` instead of one joined `Error` |
| `Result.WhenAll(t1 … t6)` | `await Task.WhenAll(…)`, then a LINQ query over the six `Fin`s (first failure). Its only caller reads six module states, whose failures are all the same outage |
| `Match(onSuccess, onFailure, onNotFound, onNotModified)` | `Match(Succ: …, Fail: e => e switch { NotFound n => …, _ => … })` |
| `Task<Result<T>>` chains (`Map`, `Bind`, `BindAsync`, `TapAsync`, `Match`, `MatchAsync`) | the same names on `Task<Fin<T>>`, in a temporary `FinTaskExtensions` (3.4), except `Map` and `Bind`, which are `MapFin` and `BindFin` |
| `Unit` / `Unit.Value` | `LanguageExt.Unit` / `unit` |
| `GetOrElse(() => x)` | `[Obsolete] OrDefaultDuringMigration(x)` in `FinTaskExtensions` (OQ-1) |
| `GetOrElse(() => null)` on an id | `[Obsolete] OrNullDuringMigration()`: `Fin<Option<T>>` to `T?` (3.5) |

Where a v5 beta name in this table turns out to differ (the spike found two), the implementation uses the real name,
and this table is corrected in the same change.

### 3.3 `NotModified` becomes a success value

`Result` had a fourth case, `NotModified`: a settings write where the value was already set. C1 has no such case, and
it isn't a failure. The callers treat it as success: `ReplyResultAsync` replies "saved" and still runs `onSaved`, and
`MuteAdminCommands.Create` maps it to no error. Making it an `Expected` would make every `Bind` short-circuit on it.

The settings writes that can return it change from `Task<Result<T>>` to `Task<Fin<Write<T>>>`:

```csharp
/// <summary>What a settings write did. Both cases are successes.</summary>
public abstract record Write<T>
{
    private Write() { }

    public sealed record Saved(T Value) : Write<T>;

    /// <summary>The value was already set, so nothing was stored. The message says so.</summary>
    public sealed record Unchanged(string Message) : Write<T>;
}
```

The writes are `SetGuildSetting` (and the services built on it), the leveling ignores, the diagnostics ignores, the
message-log channel overrides and the spam-filter overrides. A caller that doesn't care maps `Write<T>` away. The one
caller that shows the message (`IgnoreCommandGroup`, yellow) matches `Unchanged`.

### 3.4 `FinTaskExtensions`, temporary

`Grimoire.Domain/Migration/FinTaskExtensions.cs` gives `Task<Fin<T>>` the chain methods that `ResultTaskExtensions`
gave `Task<Result<T>>`, with the same `Task`/`ValueTask` `Match` overloads. That way the callers change only the
types. Every member is `[Obsolete]` (the class can't be: an extension call doesn't name its class, so it wouldn't
warn), so each use shows up in the build as a burn-down, like TD-13. It's deleted once 3.1 and the Phase 3 ports no
longer need it (Phase 5).

`Map` and `Bind` on a task are named **`MapFin` and `BindFin`**. language-ext has its own `Task<T>.Map` and
`Task<T>.Bind` (`LanguageExt.TaskExtensions`), which made the calls ambiguous. Worse, where the lambda ignores its
argument (`.Map(_ => x)`), language-ext's version would compile and map the whole `Fin`, so a failure would turn into
a success. After the change, a scan of the built `Grimoire`, `Grimoire.Settings` and `Grimoire.Domain` assemblies
found no reference to `LanguageExt.TaskExtensions` or `LanguageExt.QueryExtensions`.

### 3.5 Absent values

Several services return a nullable success today (`Result<ChannelId?>`, `Result<RoleId?>`), and two constructors
return `Validation<ModerationReason?>` and `Validation<RewardMessage?>` for an optional input. **Decided (OQ-2):**
these become `Option<T>` (`Fin<Option<ChannelId>>`, `Validation<Error, Option<ModerationReason>>`), which is what an
absent value is in language-ext and what 1.2's pipelines bind over. No `Fin` or `Validation` in scope holds a nullable
success. A unit test pins that v5's `Fin.Succ` and `Success` accept `null` (v4 threw `ValueIsNullException`).

Shell code that still hands `null` to DSharpPlus or EF converts at that point: `option.ToNullable()` for an id (a
struct), and `option.OrNull()` (`Grimoire.Domain/OptionExtensions.cs`) for a reference. The ~20 calls that read an id
setting with `GetOrElse(() => null)` use the bridge's `OrNullDuringMigration()`, which keeps their behaviour exactly
and stays a warning. `GetChannelOption` returns `Validation<Error, Option<DiscordChannel>>`.

### 3.6 Smart constructors (TD-5)

All 20 `Create` methods in scope can fail (checked 2026-11-14: each has at least one failing branch, or delegates to
one that has). So TD-5 changes no signature here. Each moves from `Validation<T>` to `Validation<Error, T>` and fails
with `Invalid`. The `FromDatabase` and `ParseFromDatabase` factories stay `internal` and return the value.

### 3.7 Usings

As built:

| Project | Global usings | Per file |
|---|---|---|
| `Grimoire.Domain`, `Grimoire.Settings` | `LanguageExt`, `LanguageExt.Common`, `static LanguageExt.Prelude` | — |
| `Grimoire`, `Grimoire.UnitTests` | `LanguageExt.Common`, `static LanguageExt.Prelude` | `using LanguageExt;` where a file uses `Fin`, `Option` or `Validation` |
| `Grimoire.IntegrationTests` | `LanguageExt.Common` | `using LanguageExt;` as above |

A global `using LanguageExt;` in `Grimoire` made `HashSet<T>` and `Duration` ambiguous, and `Distinct()` on an EF
query (`LanguageExt.QueryExtensions`). In the integration tests, the global `Prelude` made `Array.Empty` ambiguous.
`Grimoire` aliases `Duration` to `Grimoire.Enums.Duration` globally. The few files that need both name a
`System.Collections.Generic.HashSet<T>` in full, or call `Queryable.Distinct(...)`.

## 4. Edge cases

How the old reply helpers render each case in 1.1. Nothing a user sees changes, except where noted.

| Case | Before (`Result`) | In 1.1 | From 1.2 |
|---|---|---|---|
| Input check fails | `Invalid`, red, ephemeral | `Invalid`, red, ephemeral | same |
| Several input checks fail | one `Error`, messages joined by "; " | `ManyErrors`, rendered joined by "; ", duplicates removed | the boundary renders each message (1.2 spec sets the separator) |
| Thing doesn't exist | `NotFound`, yellow where the caller has `onNotFound`, else red | `NotFound`, the same colour by the same rule | yellow always (Q2c) |
| Setting already has that value | `NotModified`, rendered as saved | `Write.Unchanged`, rendered as saved | same |
| Settings database down | `Invalid` with "Was not able to…", red | `Unavailable` with the same message, red | generic "[ID …]" reply plus an alert (Q1) |
| Discord refuses | exception, central handler | unchanged (1.4 makes it `Forbidden`) | `Forbidden`, red |
| Any other `Error` | can't happen | can't happen | defect: generic reply plus an alert |

The behaviour changes outside replies, and the case changes:

1. **`TextCustomCommandProcessor`** branched on `Error.Code` to choose its log line. Now each log line is written
   where the lookup fails, in `FetchCommandAsync`: "module disabled" (still an `Invalid` that ends the pipeline,
   logged at Debug), and "not found or not allowed", the `NotFound` case, which takes the command name from the parsed
   message instead of `Error.Target`. The pipeline's failure branch does nothing.
2. **`GainUserXp`'s alert** for missing leveling settings says the case and the message instead of the code.
3. **`Result.WhenAll`'s only caller** reports the first failure instead of all distinct ones (3.2). They're the same
   outage, so the user sees the same message.
4. **Two "not found" errors change case.** `/Commands Leaderboard`'s "No command named …" and `/Commands Revert`'s
   "Version not found …" were `Invalid` failures with not-found codes. They're `NotFound` now. Both callers render any
   failure the same way, so nothing visible changes until 1.2's yellow.
5. **`/Diagnostics Ignore Add` with nothing new** still answers with the yellow warning it gave when `NotModified` was
   a failure. It now matches `Write.Unchanged` to do so.

## 8. Tests

**Counts.** Before: 430 unit test cases (336 methods), 1384 integration. After: 392 unit cases (298 methods: 336 − 61
deleted + 23 new; the deleted classes held 63 cases), 1384 integration. Per-class method counts match HEAD for every
class that wasn't deleted or added. Skips unchanged: 1 unit (KI-93), 38 integration.

**Deleted, because they test our own `Result`/`Validation`/`Unit` rather than Grimoire behaviour:** `ResultTests` (34),
`ValidationTests` (16), `ValidationCombinatorTests` (8) and `UnitTests` (3), 61 in all.

**New unit tests** (`Grimoire.UnitTests/Domain/ErrorTests.cs` and `FinTaskExtensionsTests.cs`):

- Each case keeps its message, and `Unavailable` keeps the exception, a `TimeoutException` included.
- `Write<T>`: `Map` keeps `Unchanged` and its message; `Match` picks the branch (`WriteTests`).
- `Validation<Error, _>` over two failing `Create`s collects both `Invalid`s (pins the applicative behaviour that
  `Validation.Combine` tests pinned).
- `ToFin()` on a two-error `Validation` gives a `Fin` whose error holds both.
- The chain methods in `FinTaskExtensions`: success flows through, failure skips the function and keeps its case, and
  the `Task`/`ValueTask` `Match` overloads await the handler (the bug the `Match(Func<T, Task>)` overload exists for).
- `Fin` and `Validation` with a `null` success value (OQ-2): pins whatever v5 does.

**Changed, not rewritten:**

- `ResultShouldExtensions` becomes `FinShouldExtensions`: `ShouldSucceed` for `Fin`, `Task<Fin>`, `ValueTask<Fin>`
  and `Validation<Error, _>`, and `ShouldFail()`, which returns the `Error`. A test asserts the case and message with
  Shouldly: `result.ShouldFail().ShouldBeOfType<Invalid>().Message.ShouldBe(…)`. (The planned
  `ShouldFailWith<TCase>()` was dropped: C# can't infer `T` while `TCase` is given.) For settings writes,
  `ShouldBeSaved()` returns the saved value, `ShouldBeUnchanged()` returns the message, and `ShouldBeSetOrUnchanged()`
  accepts either.
- The `.Code` assertions become the case and the exact message the code stood for, taken from HEAD's
  `new Error(code, message)` (F-4). Test names that said "Code" say "Message".
- The integration tests that asserted `NotModified` assert `ShouldBeUnchanged()` and its message.
- **`ShouldSucceed()` on a settings write became `ShouldBeSaved()`** (57 calls). Before, `ShouldSucceed()` failed on
  `NotModified`. After, it would have accepted `Write.Unchanged`, so those tests would have got weaker silently. The
  calls were found with a temporary `[Obsolete]` overload on `Fin<Write<T>>`, so each one was a compiler warning.
- **Type assertions on `Fin`** (`ShouldBeOfType<Fin<T>.Fail>()`, about 60) became `ShouldFail().ShouldBeOfType<Case>()`
  or `ShouldSucceed()`, with the case from the matching line in HEAD. `ShouldBeOfType<Fin<X>.Fail>()` still compiles
  when `X` is no longer the result type (`Write<X>`, `Option<X>`), but then always fails, and the old pattern lost
  the case (`Invalid` vs `NotFound`).
- `OutageTests` (the settings module with its database refused) asserts `Unavailable` for every call.

**Two bugs found in review of the rewrite, fixed before commit:**

- `UnmuteUser` and `MuteBackgroundTasks` treated `Result.NotFound` as "already cleared". The mechanical rewrite made
  that `Fin.Fail`, so any failure, an outage too, counted as cleared. They now match `Fin<MuteAdded>.Fail(NotFound)`.
  `SettingFailureCallerTests.Unmute_WhenTheMuteCannotBeCleared_SaysSo` caught the unmute case.
- `MuteBackgroundTasks` checked `is Fin<RoleId?>.Fail` on what is now a `Fin<Option<RoleId>>`, a pattern that can
  never match but still compiles, so a failed mute-role read would no longer retry. It's `configuredResult.IsFail`
  now. Every other `is Fin<…>` and `is Validation<…>` pattern in production code was checked against the method it
  tests.

**Mutation** (`dotnet stryker -p Grimoire.Domain.csproj`, and `-p Grimoire.Settings.csproj -m "Domain/**/*.cs"`;
`--since:main` would cover the whole branch, so the scope is given instead):

| Scope | HEAD | 1.1 | Notes |
|---|---|---|---|
| `Grimoire.Domain` | 58.48% | 68.12% | The deleted `Result`/`Validation` had many uncovered mutants. |
| `Grimoire.Settings/Domain` | 62.77% | 60.00% | Same 5 survivors and 45 uncovered mutants. The drop is 16 killed mutants on the old error-code strings, which are gone. |

Stryker runs found one more thing: `Error.New(exception)` turns a `TimeoutException` or an
`OperationCanceledException` into language-ext's own expected error (`TimedOut`, `Cancelled`) and drops the exception.
`Unavailable.From` uses `Error.New(message, exception)`, which keeps it, and `ErrorTests` pins that with a timeout. A
crashed Stryker run leaves its mutated assemblies in the test projects' `bin` (with `*.stryker-unchanged` backups);
delete those and rebuild with `--no-incremental` before trusting a test run.

**Done when:** `dotnet build` has no errors and no new warnings except the `FinTaskExtensions` obsolete warnings, both
test projects pass with the same skips, and a search finds no `Grimoire.Domain.Result`, `Validation<T>` with one type
argument, `new Error(` or `.Code` on an error.
