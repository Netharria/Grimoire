# Spec 1.3: data access

Status: **implemented and committed 2026-11-15.** Approved the same day: the owner took the suggested answer to
every open question (section 10), and asked that database error logs carry enough detail to diagnose the failure
(OQ-4, section 3.6.1). Section 3.12 lists where the code differs from the approved text. Tests before and after: unit
480 → 577 (1 skipped, KI-93), integration 1399 → 1414 (38 skipped). Build warnings: 120 before and after.

Implements C3 from the plan: Dapper for runtime code, with EF Core kept for migrations and the model snapshot. It
covers Q1 (the database half: Postgres failures become `Unavailable` at one edge), Q28 and P-15 (a non-retrying
streaming path), the type-handler half of TD-6 (`jsonb` documents through System.Text.Json), the `Sql` value that
Q16's upsert will use, and Q25's rule applied to the database (a write is never retried). It also prepares for P-9:
ids are sent as `bigint` from the start, so Phase 2's column change needs no code change.

## 1. Scope

**In scope**

- **`IDatabaseIO`**, its live implementation over one pooled `NpgsqlDataSource`, and the `Db<RT>` effect module. It
  adds one field to `GrimoireEnv` and one `Has<>` to each runtime, as the 1.2 spec planned.
- **`Sql`, a statement as a value**: a name, the text, the parameters, and whether it only reads (section 3.1).
- **Reads, writes, transactions and streaming** (sections 3.2–3.5). A retry schedule applies only to reads. Writes,
  transactions and streams are never retried.
- **One error edge** (section 3.6). Npgsql and Postgres exceptions become `Unavailable`, `Errors.Cancelled` or a
  defect there, and nowhere else.
- **Dapper type handlers** (section 3.7): the strongly typed ids, the text value types, `Option<T>` of each,
  `DateTimeOffset`, and a generic `jsonb` handler for System.Text.Json documents. The domain handlers are in
  `Grimoire.Data/Dapper/`, because the domain's `FromDatabase` factories are internal to it. There are no Settings
  handlers yet; see the Out of scope list.
- **One connection pool** (OQ-1): the `NpgsqlDataSource` is built once and both EF contexts use it, so old and new
  code share one pool and one connection limit.
- **A fake database** for unit tests (`FakeDatabase`), which answers by statement name and can fail, and
  **a pattern for SQL tests** in the integration project (section 8), with a read-only check for every `Sql.Read`.
- **Packages:** `Dapper`, pinned to the newest stable version at implementation time (the spike used `2.1.89`), in
  `Grimoire.Data` and `Grimoire`. `Npgsql` stays transitive through the EF provider.

**Out of scope**

- **Porting any query.** No feature moves to Dapper here. Each Phase 3 section moves its own queries, with their
  tests (plan rule 3). The first real users are `/Warn` (3.2) and the settings service (3.1).
- **Settings value handlers** (`XpGainAmount`, `LevelScalingBase`, `RewardMessage` and the rest). TD-6 replaces
  their key/value rows with one `jsonb` document per module in 2.2, so they'd be written only to be deleted. The
  settings documents' own types and versioning are in 2.2 and 3.1. 1.3 supplies the handler they use.
- **The schema.** P-9's `bigint` columns, TD-6's tables and Q9's discriminators are Phase 2. Section 3.7 explains
  why 1.3's handlers work before and after P-9 without a change.
- **Q16's reaction upsert itself** (3.12), **Q28's consumers** (log cleanup 3.13, purge, the backfills in 3.11), and
  **removing `EnableRetryOnFailure`** from the EF contexts, which keep it until Phase 5 removes their runtime use.
- **Spans and metrics** (1.6). 1.3 gives each statement a name for 1.6 to use (section 7).
- **`UseExceptionProcessor()` and `EntityFrameworkCore.Exceptions`.** They stay for the unported code. Ported code
  doesn't catch constraint exceptions; it writes statements that can't raise them (section 4).

**IDs covered:** C3, Q1 (database half), Q25 (applied to the database), Q28, P-15, TD-6 (handlers), Q16 (the `Sql`
type), P-9 (parameter types only). No KIs.

## 2. Flow

### 2.1 A read

```
feature core (pure)          WarnSql.ActiveSinCount(guild, user)  →  Sql.Read("Warn.ActiveSinCount", text, params)
   │
   ▼
Db<RT>.Query<Row>(sql)                                                     effect, built not run
   │  sql.IsRead ──► retry while the error is transient, on IDatabaseIO.ReadRetry (section 3.3)
   ▼
NpgsqlDatabaseIO.Query                                                     live capability (the shell)
   open a pooled connection ──► Dapper QueryAsync(CommandDefinition with EnvIO's token) ──► close
   │  throws ──► DatabaseErrors.Classify(exception, token) ──► Unavailable | Errors.Cancelled | defect
   ▼
Fin<Seq<Row>> back in the Eff  ──►  feature core maps Row → domain record (pure)
```

### 2.2 A write

```
Sql.Write("Warn.InsertSin", text, params)  ──►  Db<RT>.Execute(sql) / Db<RT>.Query<Row>(sql) for RETURNING
   no retry: a transient failure is Unavailable at once (Q25)
```

### 2.3 A transaction

```
Db<RT>.Transaction(session =>                                              the body is IO, not Eff<RT>:
    from id in session.QuerySingle<SinId>(WarnSql.InsertSin(…))           only SQL and pure code can run inside,
    from _  in session.Execute(WarnSql.InsertReason(id, …))                 so no Discord call holds a transaction
    select id)
   │
   ▼
NpgsqlDatabaseIO.Transaction: open ──► BEGIN ──► body(session) ──► COMMIT ──► close
   body fails, or a statement throws ──► ROLLBACK (by disposing) ──► the error, classified
   never retried, the reads inside it included
```

### 2.4 A stream (Q28)

```
Db<RT>.Fold(sql, seed, (state, row) => state')                            step is pure
   │
   ▼
NpgsqlDatabaseIO.Fold: open ──► Dapper QueryUnbufferedAsync (IAsyncEnumerable<Row>) ──► fold ──► close
   never retried; a failure part way through is Unavailable and the partial state is dropped
```

- **Pure:** building every `Sql`, mapping rows to domain records, `DatabaseErrors.Classify`, `DatabaseErrors.IsTransient`,
  the fold step, and the code between statements in a transaction body.
- **Effects:** every call on `IDatabaseIO`, and the retry's waits.

## 3. Types

All in `Grimoire/Functional/` unless a path says otherwise.

### 3.1 `Sql`

```csharp
/// <summary>A statement and its parameters, as a value. Built by pure functions; only IDatabaseIO runs it.</summary>
/// <param name="Name">"Feature.Statement", e.g. "Warn.InsertSin". The fake database matches on it, logs name it,
///     and 1.6 uses it as the span name. Never the SQL text, which may carry parameter values.</param>
/// <param name="Parameters">An anonymous object or DynamicParameters, as Dapper takes them.</param>
public sealed record Sql
{
    public string Name { get; }
    public string Text { get; }
    public object? Parameters { get; }
    /// <summary>True only for a statement that changes nothing. Only these are retried.</summary>
    public bool IsRead { get; }

    public static Sql Read(string name, string text, object? parameters = null);
    public static Sql Write(string name, string text, object? parameters = null);
}
```

Being a read is part of the value because the method doesn't say: `INSERT … RETURNING` goes through `Query`, and
retrying it would insert twice. The constructors are the only way to build one, so every statement states which it
is. The integration tests check that each `Sql.Read` really reads only (section 8).

Feature SQL lives next to the feature, as one static class of pure functions per slice (`WarnSql`, `NicknameSql`),
as in the spike. Identifiers are quoted as EF created them (`"Sins"."GuildId"`, `"Settings"."Mutes"`).

### 3.2 The capability

```csharp
public interface IDatabaseIO
{
    IO<Seq<A>> Query<A>(Sql sql);

    /// <summary>The first row, or None. Works for value types too (the spike's version didn't).</summary>
    IO<Option<A>> QueryOptional<A>(Sql sql);

    /// <summary>Exactly one row. Zero or several rows is a defect: use QueryOptional when absence is possible.</summary>
    IO<A> QuerySingle<A>(Sql sql);

    /// <summary>The number of rows affected.</summary>
    IO<int> Execute(Sql sql);

    /// <summary>
    ///     Runs the body in one transaction on one connection. Commits when the body succeeds and rolls back when
    ///     it fails. The session can't start a transaction, so transactions don't nest.
    /// </summary>
    IO<A> Transaction<A>(Func<IDatabaseSession, IO<A>> body, IsolationLevel isolation = IsolationLevel.ReadCommitted);

    /// <summary>
    ///     Streams the rows through a pure fold, holding the connection only while it runs. Never retried. For large
    ///     reads (Q28): backfills, export-like work. A step that needs Discord doesn't belong here (P-15).
    /// </summary>
    IO<S> Fold<A, S>(Sql sql, S seed, Func<S, A, S> step);

    /// <summary>The schedule Db&lt;RT&gt; retries reads on. Live: section 3.3. Fake: no delay.</summary>
    Schedule ReadRetry { get; }
}

/// <summary>The statements of one open transaction. No retries, no nesting.</summary>
public interface IDatabaseSession
{
    IO<Seq<A>> Query<A>(Sql sql);
    IO<Option<A>> QueryOptional<A>(Sql sql);
    IO<A> QuerySingle<A>(Sql sql);
    IO<int> Execute(Sql sql);
}
```

`Db<RT>` mirrors these as `Eff<RT, _>`, and adds the read retry to `Query`, `QueryOptional` and `QuerySingle` when
`sql.IsRead`. The retry is in the effect module, not the live capability, so unit tests see it against the fake.

`NpgsqlDatabaseIO` takes the `NpgsqlDataSource`. Each call opens a pooled connection and closes it when done, as in
the spike. Every Dapper call gets a `CommandDefinition` with the `EnvIO` token, so shutdown cancels a running
statement. The command timeout stays at Npgsql's default of 30 s.

### 3.3 Retry

```csharp
public static class DatabaseRetry
{
    /// <summary>Three retries, about 100, 200 and 400 ms with jitter: under a second in all.</summary>
    public static Schedule Reads { get; }

    /// <summary>Only Unavailable whose cause Npgsql or Postgres marks transient (section 3.6). Pure.</summary>
    public static bool IsTransient(Error error);
}
```

A retried read that still fails is `Unavailable`, which the boundary turns into the generic reply and an Urgent alert
(1.2). Three retries under a second is shorter than EF's `EnableRetryOnFailure` default (six, up to 30 s), because a
command has a user waiting on it, and a longer outage is better reported than hidden. A worker's next tick is its
retry.

### 3.4 Transactions

- **The body is `IO`, not `Eff<RT, A>`**, so it can only run SQL through the session and pure code. A Discord call,
  a log post or a clock read inside a transaction doesn't compile. Read what the body needs before it starts.
- **Rollback** happens when the body fails or throws, or the token is cancelled, by disposing the transaction.
- **Isolation** is `ReadCommitted` unless the caller asks. A `Serializable` transaction that hits a serialization
  failure (`40001`) is `Unavailable` and isn't retried (OQ-3).

### 3.5 Streaming (Q28, P-15)

`Fold` uses Dapper's `QueryUnbufferedAsync`, which returns an `IAsyncEnumerable` over an open reader. The fold step
is pure, so nothing else runs while the reader is open. Work that calls Discord per row (log cleanup) reads a bounded
page with a plain `Query` (`… ORDER BY … LIMIT @n`) and handles it after the connection is closed, which is P-15's
rule that no reader stays open across a Discord call. Section 3.13 decides its own paging.

The retrying execution strategy that made EF buffer every `AsAsyncEnumerable` (P-15) doesn't exist on this path, so
`Fold` really streams.

### 3.6 The error edge (Q1)

```csharp
internal static class DatabaseErrors
{
    /// <summary>
    ///     The one place a database exception becomes a value. Pure, so it's unit-tested case by case. Takes the
    ///     statement so the error names it (section 3.6.1).
    /// </summary>
    public static Error Classify(Exception exception, Sql sql, CancellationToken token);
}
```

| Exception | Becomes | Transient (retried if a read) |
|---|---|---|
| any, while `token` is cancelled | `Errors.Cancelled` (the boundary logs shutdown at Information) | no |
| `NpgsqlException` with `IsTransient` (connection refused or lost, socket, the pool's open timeout) | `Unavailable("The database is unavailable.")` with the exception | yes |
| `TimeoutException`, or `NpgsqlException` wrapping one (command timeout) | `Unavailable` | yes |
| `PostgresException` class `08` (connection), `53` (insufficient resources), `57P01`–`57P03` (shutdown, cannot connect now) | `Unavailable` | yes |
| `PostgresException` `57014` (statement timeout or cancel) without our token cancelled | `Unavailable` | yes |
| `PostgresException` `40001` (serialization), `40P01` (deadlock) | `Unavailable` | no, since only reads are retried and a deadlock needs writes |
| `PostgresException` `23xxx` (unique, foreign key, not null, check) | defect | — |
| `PostgresException` `42xxx` (syntax, unknown column), `22xxx` (data, e.g. a value too long) | defect | — |
| Dapper mapping errors, a handler's `FromDatabase` throwing, `QuerySingle` with zero or several rows | defect | — |
| anything else | defect | — |

A defect is `Error.New(exception)`, which the boundary reports as `UnhandledException` with an Urgent alert (1.2).
`Unavailable.From` keeps the exception for the log. The message the user could see is only the generic reply.

#### 3.6.1 What a database error log says (OQ-4)

`Include Error Detail=true` comes out of the connection string, because Postgres's `Detail` field holds row values
(for a unique violation, the key; for a failed insert, the whole row), which can be message content. The log keeps
everything else Postgres reports, which is enough to find the statement, the object and the cause without the row
values.

`Classify` wraps the original exception in a `DatabaseException` (internal to `Grimoire/Functional/Data/`) before it
goes into `Unavailable.From` or `Error.New`. Its message holds the diagnosis, and the original Npgsql exception, with
its stack trace, is its inner exception. So the boundary's existing log line ("Error on Command: [ID …]", the event
and worker lines) and the alert carry it without any change to 1.2's code.

```
Database statement Warn.InsertSin failed (Write, in a transaction, attempt 1 of 1):
  23505 unique_violation: duplicate key value violates unique constraint "PK_Sins"
  Object: schema "public", table "Sins", column —, constraint "PK_Sins", type —
  Hint: — · Position: — · Where: — · Routine: _bt_check_unique
  Parameters: @GuildId, @UserId, @ModeratorId, @Reason, @SinType          (names only, never values)
```

| Field | From | Logged | In the alert |
|---|---|---|---|
| Statement name, read or write, in a transaction or not, the attempt (with retries) | `Sql`, `Db<RT>` | yes | yes |
| SQLSTATE and its condition name | `PostgresException.SqlState` | yes | yes |
| Postgres's message text | `MessageText` | yes | yes |
| Schema, table, column, constraint, data type | the `PostgresException` fields | yes, those Postgres sets | yes |
| Hint, position in the statement, `Where` context, routine | the `PostgresException` fields | yes | no |
| Parameter names | `Sql.Parameters` | yes | no |
| Parameter values, `Detail` | — | **never** | never |
| The Npgsql exception, its inner exceptions and the stack | the inner exception | yes | the type and first line only, as today |
| For a connection failure (no `PostgresException`): the host, the port, the socket error, and whether the pool timed out | `NpgsqlException`, its inner `SocketException` or `TimeoutException` | yes | yes |

**One limit:** for a few data errors (`22xxx`, such as `22P02` invalid input syntax), Postgres puts the bad value
inside `MessageText` itself. It stays in, because the error can't be diagnosed without it, and those errors mean a
validation bug in our own code rather than user content passing through. A development database can still turn
`Detail` on through its own `ConnectionStrings:Grimoire`.

`Unavailable`'s user-facing message stays "The database is unavailable.", which only the generic reply's wording
replaces (1.2, UX-2). The diagnosis is in the exception, which only the log and the alert show.

**Constraint violations are defects on purpose.** Today `AddMessageEvent`, `DeleteMessageEvent` and `ReactionEvents`
catch `UniqueConstraintException` for an expected race. Ported code writes the race into the statement instead
(`ON CONFLICT DO NOTHING`, a CTE, an `INSERT … SELECT … WHERE EXISTS`), as the spike did, so a violation that still
happens is a bug.

### 3.7 Type handlers (`Grimoire.Data/Dapper/DapperTypeHandlers.cs`)

`DapperTypeHandlers.Register()` is called once by `AddEffectRuntime`. Dapper's table is process-wide, so it's
idempotent (an `Interlocked` flag, as in the spike).

| CLR type | Column today | Sent as | Read from |
|---|---|---|---|
| `GuildId`, `UserId`, `ChannelId`, `MessageId`, `RoleId`, `ModeratorId`, `AttachmentId`, `EmojiId` | `numeric(20,0)` (`bigint` after P-9) | `bigint` (`(long)id.Value`) | `numeric` or `bigint` |
| `SinId` | `bigint` | `bigint` | `bigint` |
| `Nickname`, `Username`, `ModerationReason`, `MessageContent`, `CustomCommandName`, `CustomCommandContent`, `CustomCommandEmbedColor`, `AttachmentUrl`, `AvatarFileName`, `PluralKitSystemId`, `PluralKitMemberId`, `InviteCode` | `text` | `text` | `text`, through the type's `FromDatabase`, or `Create` where it has none |
| `Option<T>` of each type above | nullable | `NULL` for `None` | `NULL` as `None` |
| `DateTimeOffset` | `timestamptz` | UTC (Npgsql refuses another offset) | `DateTime` (UTC) to `DateTimeOffset` |
| `Jsonb<T>` (section 3.8) | `jsonb` | `NpgsqlDbType.Jsonb` | `text`, through System.Text.Json |

**Ids go as `bigint` now, before P-9.** Postgres compares a `bigint` parameter with a `numeric` column by casting the
parameter, so the index is still used. A `numeric` parameter against a `bigint` column would cast the column and lose
the index. Sending `bigint` is right for both schemas, and Settings (2.2) and Grimoire (2.3) can change their columns
in different sections without touching a handler. An integration test pins the index use with `EXPLAIN` (section 8).
Snowflakes stay below 2^63 until about 2084 (P-9), so the cast is exact.

**Not through handlers:**

- **Enums.** Dapper sends an enum as its number and ignores handlers for enums. The Q9 discriminator columns are
  text, so SQL takes `type.ToString()`, and Dapper parses text into the enum when reading. A test pins both.
- **`ModerationActor`.** `NULL` means `System`, but Dapper never calls a handler for `NULL` on a class, so it would
  read `null`. Rows read the column as `long?` and map it with `ModerationActor.FromColumn`.
- **Arrays.** Dapper doesn't apply handlers to array elements. `= ANY(@ids)` takes `long[]`, built with
  `ids.Map(id => (long)id.Value)`, through one helper per id kind.
- **Rows.** A query reads into a private row record next to its SQL, and a pure function maps it to the domain type.
  Dapper doesn't construct domain entities, so their invariants stay behind their smart constructors.

A unit test checks by reflection that every type in `Grimoire.Domain` with a `FromDatabase` or `ParseFromDatabase`
factory, and every id type, has a handler, so a new value type can't be forgotten.

### 3.8 `jsonb` documents (TD-6)

```csharp
/// <summary>A value stored as a jsonb document. The wrapper is what Dapper's handler binds to.</summary>
public readonly record struct Jsonb<T>(T Value);

/// <summary>Registers the handler for one document type, with the options its documents use.</summary>
public static void RegisterDocument<T>(JsonSerializerOptions options);
```

- 1.3 provides the handler and its tests with a test-only document type. 2.2 and 3.1 register the settings documents
  and own their versioning (who, when, the version number) and what a missing document means.
- **Unknown fields are ignored and missing fields take the record's defaults**, so adding a setting needs no
  migration (TD-6). A document that doesn't parse is a defect. Whether settings fall back to the last good value
  instead is SET-10's call, in 3.1.
- **Documents use nullable fields, not `Option<T>`.** System.Text.Json doesn't know language-ext's types, and the
  document is a storage shape. The settings domain maps it to its own records.

### 3.9 Registration and the shared pool (OQ-1)

```csharp
// GrimoireServiceRegistration, after the connection string is resolved:
var dataSource = new NpgsqlDataSourceBuilder(connectionString).Build();
services
    .AddSingleton(dataSource)
    .AddPooledDbContextFactory<GrimoireDbContext>(options =>
        options.UseNpgsql(dataSource, npgsql => npgsql.EnableRetryOnFailure()).UseExceptionProcessor())
    .AddSettingsServices(dataSource)            // was the connection string
    .AddEffectRuntime();                        // registers IDatabaseIO over the same data source
```

Today the two EF contexts share Npgsql's pool for the connection string. A separate data source for Dapper would be
a second pool, which can double the connection count under load. One data source for all three keeps one limit.

`GrimoireEnv` gains `IDatabaseIO Database`. `GrimoireRuntime` and `CommandRuntime` each gain

### 3.11 The fake database (`Grimoire.UnitTests/Functional/Fakes/FakeDatabase.cs`)

- **Answers by statement name:** `db.Returns("Warn.ActiveSinCount", rows)`, or a function of the `Sql`. A statement
  with no answer fails the test with its name, so no pipeline runs against an accidental empty result.
- **Records every call in order** in the shared `Journal`, with the `Sql` value, so a test asserts the parameters
  and the order.
- **Can fail:** `db.Fails("Warn.InsertSin", error)`, or fail the first n times, to test the read retry. Its
  `ReadRetry` has no delay.
- **Transactions** record `Begin`, each statement, and `Commit` or `Rollback`, so a test sees that a failed body
  rolled back.

### 3.12 As built (2026-11-15)

Where the code differs from the approved text above, and why:

- **Enums sent as numbers aren't always refused.** An insert into a `text` column stores the number ("1"), because
  Postgres casts anything to text on assignment; only a comparison is refused (`42883`). That makes `ToString()` more
  important, not less. An integration test pins both, and section 4's row is corrected.
- **The diagnosis doesn't give the attempt number.** The retry is in `Db<RT>`, above the capability that builds the
  message, so the first line says "read, retried while transient" or "write, never retried" instead. The alert key
  collapses repeats of the same statement's failures anyway.
- **The read-only check is a read-only connection**, not a `READ ONLY` transaction per read: `DatabaseTestEnv` sends
  every `Sql.Read` to a second data source with `default_transaction_read_only=on`. Same effect, no extra round trip,
  and it covers `Fold` too. Statements inside a transaction's body aren't checked.
- **The unreachable-database test uses a closed port** instead of pausing the shared container: it's fast and can't
  disturb the other database tests.
- **`ModerationActor` is mapped by `DatabaseColumns.Actor` and `DatabaseColumns.ActorColumn`** (with `Ids(…)` for
  arrays) in `Grimoire.Data/Dapper`, since the EF converter's `FromColumn` is internal and takes `decimal?`.
- **More handlers than the table lists:** `EmojiId`, `ReactionEmoji`, `InviteUrl`, `PositiveXpAmount` and
  `NegativeXpAmount` (`bigint`). The reflection test found them.
- **`Grimoire.Data` gains `InternalsVisibleTo`** for both test projects, so the handlers are tested directly.
- **`Sql` checks its own name and text** and throws `ArgumentException` for a blank one: a programming error, caught
  by the first test that builds the statement.
- **The alert's exception chain** is the `DatabaseException`'s short message, then Npgsql's own message. Without
  `Include Error Detail`, Npgsql's message for a server error says the detail was redacted, so it adds no values.
- **No separate arm for an `NpgsqlException` with a socket, IO or timeout inner exception**: Npgsql's own
  `IsTransient` already covers exactly those, so the arm could never run (Stryker found it uncovered).
- **`MultiGuildTests.BothGuildsMembers_AreSyncedAtStartup` now waits for the sync.** It read `NicknameHistory` as
  soon as the bot was ready, but the startup sync runs on `GuildDownloadCompleted` in the background. The race was
  always there; the shared pool changed the timing enough to lose it about half the time. It polls with
  `EventuallyAsync`, as the other background-write tests do.
- **The integration harness shares one `NpgsqlDataSource`** (`GrimoireCoreFactory.DataSource`) across every test bot
  on the container, registered as an instance so a host's disposal leaves it open. Before 1.3, every host's EF used
  Npgsql's process-wide pool for the same connection string, which earlier tests had warmed. A fresh pool per host
  made each startup open cold connections, so the startup sync (`UpdateAllGuilds`) still ran after the bot was ready.
  That exposed a second existing race: `GeneralLeftoverTests.AfterTheBotLeavesAndRejoins_ModulesViewStillWorks` sends
  `GUILD_DELETE` while the sync is still reading members, and the sync throws `KeyNotFoundException` from
  `DiscordMember.Guild`. Production has one host and one pool, so it doesn't change there, but the sync's fragility
  is real if a guild leaves during startup: KI-116, assigned to 3.19 (guild sync).

## 4. Edge cases

| Case | What happens | Error case |
|---|---|---|
| Postgres down at a read | Three retries under a second, then `Unavailable`. A command gets the generic reply and an Urgent alert (1.2) | `Unavailable` |
| Postgres down at a write | No retry | `Unavailable` |
| The connection drops during `COMMIT` | The outcome is unknown: the write may have happened. `Unavailable`, not retried. Statements that may run again after this are written to be idempotent (`ON CONFLICT`) | `Unavailable` |
| A transient failure on a read inside a transaction | Not retried; the transaction rolls back | `Unavailable` |
| A transaction body fails with a Grimoire case (e.g. `NotFound` from a row it read) | Rollback; the case is kept, not turned into `Unavailable` | its case |
| A transaction body throws | Rollback | defect |
| Shutdown during a statement | The token cancels it; Npgsql raises `57014` | `Errors.Cancelled` (logged as shutdown) |
| Statement timeout (30 s) | | `Unavailable` |
| The pool is exhausted (the open times out) | | `Unavailable` |
| A stream fails part way | The partial state is dropped; the caller can run again from the start | `Unavailable` |
| A unique or foreign-key violation | The statement should have prevented it | defect |
| A value too long for its column, a bad cast | Validation should have prevented it | defect |
| `QuerySingle` gets zero rows | Use `QueryOptional` plus `Effect.Require(…, new NotFound(…))` where absence is possible | defect |
| `QueryOptional` on a value type with no row | `None` (the spike's `QueryFirstOrDefault` gave `default`, e.g. `0`) | — |
| A `NULL` id column read as `Option<GuildId>` | `None` | — |
| A `NULL` actor column | Read as `long?`, mapped to `ModerationActor.System` | — |
| A stored text value that no longer passes `Create` (old data) | `FromDatabase` trusts stored data as today; types without one go through `Create`, and a failure is a defect | defect |
| An enum parameter passed without `ToString()` | An insert into a `text` column quietly stores the number; a comparison is refused (section 3.12) | stored wrong, or a defect (`42883`); the SQL test catches both |
| A `Sql.Read` that writes | The integration tests run every read in a `READ ONLY` transaction and fail (section 8). In production it would be retried | — |
| A `DateTimeOffset` with a non-zero offset | Npgsql refuses it. Time comes from `ITimeIO`, which is UTC | defect |
| A `jsonb` document with an unknown field | Ignored | — |
| A `jsonb` document that isn't valid for its type | | defect (3.1 decides the settings fallback) |
| Any database failure | The log and the alert name the statement, the SQLSTATE, Postgres's message and the table, column and constraint (section 3.6.1). Row values and parameter values are never logged; the user sees only the generic reply | its case |
| A data error whose Postgres message quotes the bad value (`22P02`) | Logged, since it's needed for the diagnosis (section 3.6.1) | defect |
| EF and Dapper write the same table during the migration | Separate statements on the same pool; no shared transaction is needed, since a feature moves whole | — |

## 5. UX suggestions

None. Data access has no user-facing output: an outage already gets 1.2's generic reply. One behaviour a user could
notice: a database blip during a command now gives up after about a second instead of EF's up to 30 s. That is
section 3.3's rule, not a UX choice, and it's listed as OQ-2.

## 7. Telemetry

None in 1.3: OpenTelemetry comes in 1.6. 1.3 prepares for it:

- **`Sql.Name`** is the span name 1.6 gives each statement ("db Warn.InsertSin"), with the outcome case as a tag.
  The SQLSTATE, table and constraint from section 3.6.1 become span tags too. Postgres's message text stays in the
  log only, since a `22xxx` message can quote a value.
  The SQL text and parameters never go into a span or a log (defect 9). Npgsql's own instrumentation, added in 1.6,
  carries the statement detail under it.
- **The read retry** is where 1.6 counts retries (`grimoire.db.retries`), so a flapping database shows in metrics
  even when the retries succeed.
- **The pool** is the one `NpgsqlDataSource`, whose built-in metrics 1.6 exports.

What a failure looks like in 1.6: a command's root span with outcome `Unavailable`, a child span
`db Warn.ActiveSinCount` with three retry events and the `NpgsqlException` recorded, and the same trace id in the
user's "[ID …]".

## 8. Tests

**Unit** (`Grimoire.UnitTests/Functional/Data/`), no database:

- `DatabaseErrorsTests`: each row of the table in section 3.6, with constructed `NpgsqlException`,
  `PostgresException` (public constructors) and `TimeoutException`; cancellation wins over every other case.
- `DatabaseExceptionTests`: the diagnosis holds the statement name, SQLSTATE, message text, every object field
  Postgres set, and the parameter names; it never holds a parameter value or `Detail` (a constructed exception with a
  marker string in both); a connection failure names the host and the socket error; the original is the inner
  exception.
- `DatabaseRetryTests`: only transient `Unavailable` is retried; a defect and the Grimoire cases aren't.
- `DbEffectTests`, against `FakeDatabase`: a read that fails twice then succeeds is retried and succeeds; one that
  fails four times is `Unavailable`; a write that fails once isn't retried; a `RETURNING` write through `Query` isn't
  retried; a failing transaction body records `Rollback`.
- `SqlTests`: `Read` and `Write` set `IsRead`; the name is required.
- `DapperTypeHandlerCoverageTests`: by reflection, every id type and every domain type with a `FromDatabase` or
  `ParseFromDatabase` has a registered handler, and `Option<>` of each.
- Handler unit tests for the pure halves: id ↔ `long` at the edges (`0`, a current snowflake, `long.MaxValue`), and
  `decimal` input (today's columns).

**Integration** (`Grimoire.IntegrationTests/Database/Dapper/`), in the existing `"Test collection"` with the
Testcontainers fixture and Respawn, each row of section 6. They run the live `NpgsqlDatabaseIO` directly, not through
the bot.

**The pattern for every later section's SQL tests** (documented in `architecture.md`):

- One test class per feature SQL module, named after it (`WarnSqlTests` for `WarnSql`). Each `Sql` function gets a
  test that builds the value with the pure function, runs it through a `DatabaseTestEnv` over the container's data
  source, and checks the result with a plain query.
- **`DatabaseTestEnv` runs every `Sql.Read` inside a `READ ONLY` transaction**, so a statement marked as a read that
  writes fails its test. This costs nothing in production.
- Seed with SQL or the EF context, whichever is shorter. The SQL under test is always the production `Sql` value.

**Old tests mapped:** none. 1.3 ports no feature and moves no test. The spike's `LeaderboardSqlTests` aren't on
this branch; they come back with 3.15.

**Mutation:** `dotnet stryker -p Grimoire.csproj -m "**/Functional/Data/**/*.cs"`. The aim is no surviving mutant in
`DatabaseErrors`, `DatabaseRetry` and `Sql`. `NpgsqlDatabaseIO` is integration-only and isn't covered by the unit run.

As built: 80.16% (101 killed, 7 survived, the rest of `NpgsqlDatabaseIO` not covered). The first run scored 51.56%. It
found weak assertions on the log's details (they passed through the inner exception's `ToString()`), unasserted
transient flags, the unreachable arm above, and two static initializers Stryker can't mutate usefully (the
condition-name table and the read schedule), which became a method and a computed property. All are now tested. The
seven survivors:

- **Equivalent (3):** `First()` → `FirstOrDefault()` on a non-empty group; `&` → `|` when applying the jitter
  transformer; and `exponential & recurs(3)` → `exponential | recurs(3)`, which also stops after three.
- **Integration-only (4):** the `Database.Begin` and `Database.Commit` statements' name and text in
  `NpgsqlDatabaseIO`, which only appear in the diagnosis of a failed `BEGIN` or `COMMIT`.

**Done when:** `dotnet build` has no new warnings; both test projects pass with the current skips; the existing
integration tests pass unchanged with EF on the shared data source; nothing outside the tests calls `IDatabaseIO`.
