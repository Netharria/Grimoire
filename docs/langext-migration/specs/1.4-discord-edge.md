# Spec 1.4: the Discord edge

Status: **implemented 2026-11-16, not yet committed.** Approved 2026-11-15: the owner took the suggested answer to
every open question (section 10) and accepted every UX suggestion (section 5). Section 3.13 lists where the code
differs from the approved text. Tests before and after: unit 577 → 658 (1 skipped, KI-93), integration 1414 → 1433
(41 skipped: the 38 before, plus the 3 explicit DSharpPlus investigations). Build warnings: 120 → 119. OQ-9 (403 or
404 for a guild the bot can't reach) still needs the owner's check against real Discord. Any problem found in DSharpPlus goes in
[`../../upstream/dsharpplus.md`](../../upstream/dsharpplus.md), where the owner reviews it, then reports or fixes it.
Entries DSP-3 to DSP-7 come from this spec; DSP-7 was checked and isn't a bug.

Implements the plan's section 1.4: `IDiscordIO`, the capability through which ported code calls Discord, with the one
place DSharpPlus exceptions become the C1 error cases (TD-12). It also applies Q25 (SH-15) to Discord, so calls that
create something aren't retried; replaces the three guild log message classes with one record that carries the
event's time (Q26, SH-10); puts the log gate in `GuildLog` (Q26b, LOG-2); and investigates and contains KI-54. 1.2
deferred two things to this section, and both are in scope: `Forbidden` from Discord, and the "bot missing
permissions" guild issue that comes with it (spec 1.2, sections 1 and 4).

## 1. Scope

**In scope**

- **`IDiscordIO`**, its live implementation over `DiscordClient`, and the `Discord<RT>` effect module. It adds one
  field to `GrimoireEnv` and one `Has<>` to each runtime, as the 1.2 spec planned (section 3.1).
- **Lookups that return the error cases (TD-12)**: channel, user, member, role and message. Each returns a Grimoire
  snapshot record, not a DSharpPlus entity (C5, section 3.2). `NotFound` is the only result that means "gone".
- **A first set of actions**: send a message, send a direct message, and delete a message. Phase 3 sections add the
  actions they need (ban, kick, timeout, roles, overwrites, the audit log, invites) through the same edge (section
  3.4).
- **One error edge** (section 3.5): `DiscordErrors.Classify`, the only place a DSharpPlus or HTTP exception becomes
  `NotFound`, `Invalid`, `Forbidden`, `Unavailable`, `Errors.Cancelled` or a defect. It replaces 1.2's interim mapping
  in `LiveCommandIO`.
- **The retry split (Q25, SH-15)** (section 3.6). Reads and idempotent calls are retried on a short schedule.
  Calls that create something are never retried: new messages, follow-ups, DMs and initial interaction responses.
  This applies to the unported code too, through `DiscordRetryPolicy`.
- **The bot's missing permissions as a guild issue** (section 3.7). A `Forbidden` from Discord can record which bot
  permission was refused, and the three boundaries report the guild issue for it. This needs `IGuildIssueIO`, a
  capability over `GuildIssueReporter`.
- **`GuildLogMessage`, one record (Q26, SH-10)** with factory methods and a required event time (section 3.8). The
  old classes become a bridge for unported code (OQ-1).
- **The log gate in `GuildLog` (Q26b, LOG-2)** (section 3.9): `GuildLog` gains a `SettingsModule` dependency and a
  gated overload. `GuildLogs<RT>.Post` is the only way ported code posts a log. The three handlers that gate by hand,
  and the edit log, which doesn't gate at all (defect 17), move to the overload.
- **`GuildLogPublisher` on the new edge**: its channel lookup and post go through `IDiscordIO`, and the post is no
  longer retried (Q25, defect 11).
- **KI-54** (section 3.10): reproduce it, get the stack trace, and contain it at the edge. This includes the
  DSharpPlus behaviour found while writing this spec: a request that times out on its first call to a route can
  leave that route stuck as "pending".
- **A fake Discord** for unit tests (`FakeDiscord`), which answers from a small in-memory guild, records calls in the
  `Journal`, and can fail any operation. Also a **fake guild-issue capability** (`FakeGuildIssues`).

**Out of scope**

- **Porting any feature.** No handler or command moves to `IDiscordIO` here, apart from `GuildLogPublisher` and the
  four LOG-2 call sites. Each Phase 3 section ports its own calls and removes its uses of the `…OrDefaultAsync`
  helpers.
- **Removing the `…OrDefaultAsync` helpers** (SH-3). They stay for unported code and go in Phase 5 with the other
  old helpers. They aren't marked `[Obsolete]`, because 26 new warnings would bury the build's signal (OQ-6).
- **Moving the 48 old guild log sites** to the new record (OQ-1). Each Phase 3 section moves its own sites.
- **Moderation actions** (ban, kick, timeout, mute roles, overwrites): sections 3.3–3.5 add them as operations
  (section 3.4 gives the pattern).
- **Splitting `GuildLogPublisher` by channel** (Q29, backlog), and moving its purge scheduling off EF (3.10, 3.13).
- **PluralKit** (1.5) and **spans and metrics** (1.6). 1.4 gives each operation a name for 1.6 (section 7).
- **SH-7** (shared helpers read the wall clock). The bridge stamps old log messages with `TimeProvider` (section
  3.8). The rest of SH-7 is fixed as each section ports to `Clock<RT>`.

**IDs covered:** TD-12, Q25 (Discord half), SH-15, Q26, SH-10, Q26b, LOG-2, defect 11, defect 17, defect 27, Q1 (the
Discord half: an outage is `Unavailable` at one edge), SH-3 (replaced by TD-12 for ported code), KI-54.

## 2. Flow

### 2.1 A lookup

```
feature effect                Discord<RT>.GetMember(guild, user)                          effect, built not run
   │  read ──► retry while the error is transient, on IDiscordIO.ReadRetry (section 3.6)
   ▼
LiveDiscordIO.GetMember                                                                    live capability (the shell)
   DiscordClient.GetGuildAsync ──► guild.GetMemberAsync      DSharpPlus's cache first, REST when it misses
   │  throws ──► DiscordErrors.Classify(exception, operation, token)
   │             ──► NotFound | Invalid | Forbidden | Unavailable | Errors.Cancelled | defect
   │  returns ──► MemberSnapshot.From(member)                                              pure copy
   ▼
Fin<MemberSnapshot> in the Eff ──► the feature's pure decision
```

### 2.2 A call that creates something

```
Discord<RT>.SendMessage(channel, builder)     never retried (Q25): a 502 may mean Discord already posted it
   │
   ▼
LiveDiscordIO.SendMessage ──► channel.SendMessageAsync ──► MessageId
   throws ──► Classify ──► the case; Forbidden can name the bot's missing permission (section 3.7)
```

### 2.3 A guild log post (Q26b)

```
GuildLogs<RT>.Post(guild, type, build)                         build : Eff<RT, GuildLogMessage>
   │
   ├─ IGuildLogIO.IsLogged(guild, type)       module on and log channel set (SettingsModule, a cache hit)
   │     false, or settings unavailable ──► done; build never runs
   ▼
build                                          may look up an avatar, download images: runs on the caller's fibre,
   │                                           not the publisher's single reader
   ▼
IGuildLogIO.Enqueue(message) ──► GuildLog queue ──► GuildLogPublisher
                                                        ├─ re-checks the setting (it can change while queued)
                                                        ├─ IDiscordIO.GetChannel  NotFound ──► LogChannelMissing issue
                                                        ├─ IDiscordIO.SendMessage (not retried)
                                                        │     Forbidden ──► CannotSendInChannel issue
                                                        │     Unavailable ──► Warning log; this log is lost (Q25)
                                                        └─ purge scheduled for message logs (EF, unchanged)
```

### 2.4 A Discord refusal reaching a boundary

```
Discord<RT>.… fails with Forbidden { Refusal: Some(BotRefusal(guild, channel?, permission, operation)) }
   │
   ▼
CommandBoundary: the red refusal (1.2) ──► GuildIssues<RT>.Report(GuildIssueCatalog.BotMissingPermission(refusal))
EventBoundary:   Warning log and alert (1.2)  ──► the same report
Worker items:    backoff, no alert (1.2)      ──► the same report
   the reporter's daily throttle keeps repeats to one a day per issue code
```

- **Pure:** the snapshots' `From` mappings, `DiscordErrors.Classify`, `DiscordErrors.IsTransient`, the
  `GuildLogMessage` factories and `ToBuilder`, `GuildIssueCatalog.BotMissingPermission`, and the gate's decision.
- **Effects:** every call on `IDiscordIO`, `IGuildLogIO` and `IGuildIssueIO`, and the retry's waits.

## 3. Types

All in `Grimoire/Functional/` unless a path says otherwise. The Discord files go in a new `Discord/` folder, next to
`Data/`.

### 3.1 The capability

```csharp
/// <summary>
///     Discord through DSharpPlus (spec 1.4). Takes ids and returns snapshots, so pipelines run against a fake. Every
///     exception becomes an error case in one place (DiscordErrors). Discord&lt;RT&gt; adds the read retry, so it is
///     the API features use.
/// </summary>
public interface IDiscordIO
{
    // Lookups (TD-12). NotFound only when Discord says the thing doesn't exist.
    IO<ChannelSnapshot> GetChannel(ChannelId channel);
    IO<UserSnapshot> GetUser(UserId user);
    IO<MemberSnapshot> GetMember(GuildId guild, UserId user);
    IO<RoleSnapshot> GetRole(GuildId guild, RoleId role);
    IO<MessageSnapshot> GetMessage(ChannelId channel, MessageId message);

    // Actions.
    /// <summary>Creates a message. Never retried (Q25).</summary>
    IO<MessageId> SendMessage(ChannelId channel, DiscordMessageBuilder message);

    /// <summary>
    ///     Opens the member's DM channel and posts. Never retried. Closed DMs are Forbidden with no BotRefusal: the
    ///     member's setting, not the guild's.
    /// </summary>
    IO<Unit> SendDirectMessage(GuildId guild, UserId user, DiscordMessageBuilder message);

    /// <summary>Idempotent, so it's retried. A message that's already gone counts as deleted (section 4).</summary>
    IO<Unit> DeleteMessage(ChannelId channel, MessageId message, string reason);

    /// <summary>The schedule Discord&lt;RT&gt; retries reads and idempotent calls on. Live: DiscordRetry.Reads. Fake: no delay.</summary>
    Schedule ReadRetry { get; }
}
```

`Discord<RT>` mirrors each method as `Eff<RT, _>`. Lookups and `DeleteMessage` go through
`RetryWhile(io.ReadRetry, DiscordErrors.IsTransient)`; `SendMessage` and `SendDirectMessage` don't. As in `Db<RT>`,
the retry is in the effect module and not the live capability, so unit tests see it against the fake.

**Why ids and not entities.** A `DiscordGuild` or `DiscordMember` can't be built in a test (C5), so a capability that
took or returned them would keep every pipeline that uses it out of the unit tests. The live implementation resolves
the ids itself with DSharpPlus's own lookups: `DiscordClient.GetGuildAsync(id)`, `GetChannelAsync`,
`DiscordGuild.GetMemberAsync` and the rest. Each already returns DSharpPlus's cached entity when it has one and asks
REST when it doesn't. (`GetGuildAsync` makes a REST call regardless only when `withCounts` is true, which we never
pass.) **Grimoire keeps no cache of Discord entities.** A snapshot lives only as long as the effect that asked for it,
and the next lookup asks DSharpPlus again.

### 3.2 Snapshots (`Discord/Snapshots.cs`)

A snapshot is a copy of what Discord said at the time of the lookup. It isn't a domain entity, and it isn't stored.
Each has one pure `From` that maps the DSharpPlus entity. A Phase 3 section that needs another field adds it there,
with a test (OQ-5).

```csharp
public sealed record ChannelSnapshot(
    ChannelId Id, Option<GuildId> Guild, string Name, DiscordChannelType Type, Option<ChannelId> Parent);

public sealed record UserSnapshot(
    UserId Id, Username Username, Option<string> GlobalName, string AvatarUrl, bool IsBot);

public sealed record MemberSnapshot(
    GuildId Guild,
    UserSnapshot User,
    Option<string> Nickname,
    string AvatarUrl,                    // the guild avatar if set, else the user's (SH-4: one lookup, not two)
    Seq<RoleId> Roles,
    int TopRolePosition,                 // the highest role's position, for the hierarchy checks in 3.3–3.5
    DiscordPermissions Permissions,
    DateTimeOffset JoinedAt,
    Option<DateTimeOffset> TimedOutUntil)
{
    /// <summary>Server nickname, else global display name, else username (TD-9's display name).</summary>
    public string DisplayName { get; }
}

public sealed record RoleSnapshot(
    RoleId Id, GuildId Guild, string Name, int Position, DiscordPermissions Permissions, bool IsManaged);

public sealed record MessageSnapshot(
    MessageId Id, ChannelId Channel, Option<GuildId> Guild, UserId Author, string Content,
    DateTimeOffset CreatedAt, Option<DateTimeOffset> EditedAt, Seq<string> AttachmentUrls);
```

`DiscordPermissions` and `DiscordChannelType` are value types that tests can construct, as 1.2's `Invocation`
already uses. `Username` is the domain value type. A name that fails `Username.Create` is a defect: Discord's own
rules are stricter than ours.

The names end in `Snapshot` so they don't clash with the domain's `Member`, `User`, `Channel`, `Role` and `Message`,
and so it's clear they're copies.

### 3.3 Operations (`Discord/DiscordOperation.cs`)

Each live method describes itself once, for classification, the error message and (from 1.6) the span:

```csharp
/// <summary>What one Discord call was. Internal to the live capability and DiscordErrors.</summary>
internal sealed record DiscordOperation(
    string Name,                     // "Discord.GetMember", "Discord.SendMessage"
    string Target,                   // for messages: "the member", "the channel <#123>"
    Option<GuildId> Guild,
    Option<ChannelId> Channel,
    Option<string> BotPermission);   // "Send Messages", "Manage Messages"; None for lookups
```

Whether the call is retried isn't part of the operation. `Discord<RT>` decides it per method (section 3.1), as `Db<RT>`
decides by `Sql.IsRead`, so it stays visible in the code that unit tests run.

### 3.4 Adding an operation (the pattern for Phase 3)

1. Add the method to `IDiscordIO`, taking ids and returning a snapshot, an id or `Unit`.
2. In `LiveDiscordIO`, build its `DiscordOperation` and run the DSharpPlus call through the private
   `Call(operation, async token => …)`, which applies `Classify`. There's no try/catch in the method.
3. In `Discord<RT>`, choose: retried (a read, or an idempotent call such as PUT a role, DELETE, PATCH, ban) or not
   (it creates something). The doc comment says which and why.
4. Add the operation to `FakeDiscord`.
5. Add an integration test against the fake REST for success, 404, 403 with code 50013, and 500.

### 3.5 The error edge (TD-12, Q1)

```csharp
internal static class DiscordErrors
{
    /// <summary>The one place a Discord or HTTP exception becomes a value. Pure, so it's unit-tested row by row.</summary>
    public static Error Classify(Exception exception, DiscordOperation operation, CancellationToken token);

    /// <summary>Unavailable from a 5xx, a timeout or a lost connection. Not from a rate limit (section 3.6).</summary>
    public static bool IsTransient(Error error);
}
```

DSharpPlus throws `UnauthorizedException` for both 401 and 403 (`RestClient.ExecuteRequestAsync` at the pinned
commit), but the exception keeps the response's `HttpStatusCode` (checked by the owner, DSP-7). So `Classify` branches
on the status first, then on the JSON `code` from `DiscordException.JsonMessage`.

| Exception | Discord code | Becomes | Transient |
|---|---|---|---|
| any, while `token` is cancelled | — | `Errors.Cancelled` | no |
| `NotFoundException` (404) | 10xxx (Unknown …) | `NotFound("{Target} no longer exists.")` | no |
| `UnauthorizedException`, status 403, on the guild lookup itself (**provisional, OQ-9**) | 50001 Missing Access | `NotFound`: the bot is no longer in the guild (section 4) | no |
| `UnauthorizedException`, status 403 | 50001 Missing Access, 50013 Missing Permissions | `Forbidden("I don't have permission to {verb} {Target}…")` with a `BotRefusal` (section 3.7) | no |
| `UnauthorizedException`, status 403 | 50007 Cannot send messages to this user | `Forbidden("{Target} doesn't accept direct messages.")`, no refusal | no |
| `UnauthorizedException`, status 403 | any other | `Forbidden` naming the operation, no refusal | no |
| `UnauthorizedException`, status 401 | — | defect: the token is bad, nothing will work (OQ-7) | — |
| `BadRequestException` (400, 405) | 50035 invalid form body, 30xxx limits, others | `Invalid("Discord refused {verb} {Target}: {Discord's message}.")` | no |
| `RequestSizeException` (413) | — | `Invalid("The upload is too large for Discord.")` | no |
| `BulkDeleteFailedException` | — | `Invalid` (messages older than 14 days) | no |
| `ServerErrorException` (500, 502, 503, 504) | — | `Unavailable("Discord could not be reached.")` with the exception | yes |
| `TaskCanceledException` or `TimeoutException` not from `token` (HttpClient timeout) | — | `Unavailable` | yes |
| `HttpRequestException`, `IOException`, `SocketException` | — | `Unavailable` | yes |
| `RateLimitException` (DSharpPlus retries 429s itself, so this is a global or very long limit) | — | `Unavailable` | no |
| `NullReferenceException` whose top frame is in DSharpPlus's REST client (KI-54) | — | `Unavailable`, logged with the stack (section 3.10) | no |
| anything else | — | defect | — |

- **`Forbidden` is a refusal**, rendered red with its message (Q2c). **`Invalid` from Discord** is red too. Discord's
  own message ("Invalid Form Body") is quoted after ours, because it's often the only clue. Only the JSON's top-level
  `message` is quoted, never `errors`, which can echo the request's content (defect 9).
- **The message names what's missing** (TD-12): the operation's `BotPermission`, and for member and role actions,
  that the bot's role must be above theirs. Discord returns the same 50013 for both causes.
- **Unavailable keeps the exception**, as in `Unavailable.From`, so the log has the route, the status and the stack.
  The user sees only the generic reply (1.2).
- **Not transient: a rate limit.** DSharpPlus already waits out an ordinary 429 (its `RateLimitStrategy` retries on
  the reset time). A `RateLimitException` that still reaches us means waiting longer than our schedule would help.

`LiveCommandIO` switches from its interim `Classify` to `DiscordErrors.Classify`, with an operation per method
(`Discord.Defer`, `Discord.Reply`, `Discord.Refuse`, `Discord.React`). That's the "1.4's Discord edge" its remark
promises.

### 3.6 Retry (Q25, SH-15)

```csharp
public static class DiscordRetry
{
    /// <summary>Three retries at about 0.5, 1 and 2 s with jitter: under 4 s in all (OQ-2).</summary>
    public static Schedule Reads { get; }
}
```

| Call | Retried | Why |
|---|---|---|
| Lookups (channel, user, member, role, message, audit log) | yes | Reads |
| Edits (the deferred response, a message), deletes, PUT/DELETE of a role, ban, unban, overwrites, timeouts | yes | Idempotent: a retry after a 502 that went through does nothing new. A delete that finds the message gone counts as done |
| New messages, follow-ups, DMs, log posts | **no** | A 502 may come after Discord created the message, and a retry would post a duplicate. A rare lost post is better than a rare duplicate (Q25) |
| The initial interaction response and the defer | **no** | Past Discord's 3-second window a retry can only fail with Unknown Interaction |
| Thread creation, invite creation, role creation (`/Mutes Create`) | **no** | They create something |

**Why under 4 s and not today's ~45 s** (`DiscordRetryPolicy`: four retries from 3 s, doubling). A command has a user
waiting. An event handler holds its place in DSharpPlus's dispatch while it waits. A worker's next tick is already a
retry. A 5xx that lasts longer than a few seconds is an outage, which should alert rather than hang. This matches
1.3's reasoning for the database.

**The unported code** (`DiscordRetryPolicy`) is split as SH-15 proposed, so Q25 holds before Phase 3:

- `RetryDiscordRead` keeps today's policy for its current reads and edits (`DeleteResponseAsync`,
  `EditResponseAsync`, `AddOverwriteAsync` in `MuteAdminCommands`, the audit log read). Unported code keeps its
  longer schedule until it's ported, because shortening it now would change behaviour with no tests to catch it.
- **Creates lose their retry**: `CommandContextExtension.ReplyAsync`'s initial `RespondAsync` (both branches) and
  `FollowUpAsync`, `GuildLogPublisher`'s post, and `LiveCommandIO`'s two follow-ups.
- The default-value overload stays, for `MuteAdminCommands`.

### 3.7 The bot's missing permissions as a guild issue

`Forbidden` gains an optional field. Its message and case don't change (C1):

```csharp
// Grimoire.Domain/Errors.cs
/// <summary>What Discord refused the bot, so a boundary can tell the guild how to fix it.</summary>
public sealed record BotRefusal(GuildId Guild, Option<ChannelId> Channel, string Permission, string Operation);

public sealed record Forbidden(string Message, Option<BotRefusal> Refusal = default)
    : Expected(Message, ErrorCase.Forbidden, None);
```

`DiscordErrors.Classify` sets `Refusal` only for 50001 and 50013 when the operation has a guild. A `Forbidden` from
our own rules (a moderator check, closed DMs) has none.

```csharp
public interface IGuildIssueIO { IO<Unit> Report(GuildIssue issue); }   // over GuildIssueReporter
public static class GuildIssues<RT> where RT : Has<Eff<RT>, IGuildIssueIO> { Eff<RT, Unit> Report(GuildIssue issue); }

// GuildIssueCatalog
public static GuildIssue BotMissingPermission(BotRefusal refusal);
//   code   "bot-missing-permission:{Operation}:{Channel or guild}"
//   text   "Discord refused {Operation} in <#channel>: I don't have **{Permission}**."
//   fix    "Give my role **{Permission}** (in that channel, if it's channel-specific). For an action on a member or
//           role, move my role above theirs in Server Settings > Roles."
```

**The boundaries report it.** The command boundary, the event boundary and the worker's item rule each run
`GuildIssues<RT>.Report` for every `Forbidden` with a refusal, after their 1.2 handling and through `Attempt`, so a
failed report is only logged. `GuildIssueReporter`'s daily throttle collapses repeats.

**A feature can report something more specific.** A section that knows better (3.4's `CannotUnmuteMember`, 3.5's
`CannotUnlockChannel`) catches the `Forbidden`, reports its own issue and returns its own outcome, so the boundary
doesn't report a second one. `CommandHandler`'s `BotMissingPermissions(guild, command)` stays for unported commands.

**Report without waiting.** `GuildIssueReporter` posts through the guild log queue. `LiveGuildIssueIO.Report` starts
the report and returns, as `GuildLogPublisher.Report` does today, so a report from inside the publisher can't wait on
the queue that only the publisher reads.

### 3.8 `GuildLogMessage` (Q26, SH-10)

```csharp
// Features/Shared/Channels/GuildLog/GuildLogMessage.cs
public sealed record GuildLogMessage(GuildId Guild, GuildLogType Type, DateTimeOffset At, DiscordMessageBuilder Message)
{
    public static GuildLogMessage Text(GuildId guild, GuildLogType type, DateTimeOffset at, string description,
        DiscordColor? color = null, string title = "", string footer = "");

    public static GuildLogMessage Embed(GuildId guild, GuildLogType type, DateTimeOffset at, DiscordEmbed embed);

    public static GuildLogMessage Of(GuildId guild, GuildLogType type, DateTimeOffset at, DiscordMessageBuilder message);

    /// <summary>The message to post: each embed with no timestamp gets At. Pure.</summary>
    public DiscordMessageBuilder ToBuilder();
}
```

- **`At` is required and is the event's time** (defect 27): the event's own time when Discord gives one (a message's
  edit time, an audit log entry's time), otherwise `Clock<RT>.UtcNow` when the handler runs. It's never the posting
  time.
- **`ToBuilder` fills in only missing timestamps.** An embed that sets its own (20 of today's custom embeds do) keeps
  it.
- **Bridge for unported code (OQ-1).** `GuildLogMessageBase` and its three subclasses stay, unchanged, for the 48 old
  sites. `GuildLog.SendLogMessageAsync(GuildLogMessageBase)` converts with `ToMessage(at)`, stamping `at` from
  `TimeProvider` when the message is queued. That's handling time, which fixes defect 27's queue lag for the old
  sites too. Each Phase 3 section moves its sites to the factories, and Phase 5 deletes the old classes.
- **The builder is mutable**, which the record can't prevent. It's allowed in the core (C5). The rule is that it's
  built once by a factory and never changed afterwards. The queue holds the one record.
- **Uploads aren't rewound any more.** The publisher rewound file streams before each retry (I-7). With no retry
  (Q25), each stream is read once.

`Reply.Log` becomes `Option<GuildLogMessage>`. `Reply.Logged(guild, type)` needs the time, so it becomes
`Logged(guild, type, at)`. The boundary posts the log through `GuildLogs<RT>.Post`.

### 3.9 The log gate (Q26b, LOG-2)

```csharp
public interface IGuildLogIO
{
    /// <summary>
    ///     Whether a log of this type would be posted: the module is on and the log has a channel. A cache hit
    ///     (SettingsModule). A failed settings lookup counts as no, as SettingsModule.IsLogChannelSet does today:
    ///     the publisher would drop the log too.
    /// </summary>
    IO<bool> IsLogged(GuildId guild, GuildLogType type);

    IO<Unit> Enqueue(GuildLogMessage message);
}

public static class GuildLogs<RT> where RT : Has<Eff<RT>, IGuildLogIO>
{
    /// <summary>Runs build only when someone will see the log. The only way ported code posts one.</summary>
    public static Eff<RT, Unit> Post(GuildId guild, GuildLogType type, Eff<RT, GuildLogMessage> build);

    /// <summary>A message that's already built: Post with a pure build.</summary>
    public static Eff<RT, Unit> Post(GuildLogMessage message);
}
```

- **The gate is in `GuildLog`**, as Q26b decided: `GuildLog` gains `SettingsModule` and the overload
  `SendLogMessageAsync(GuildId, GuildLogType, Func<ValueTask<GuildLogMessage>> build, …)`. `LiveGuildLogIO.IsLogged`
  and the overload call the same `GuildLog.IsLoggedAsync`, so old and new code apply one rule.
- **Old sites that move now**: `DeleteMessageEvent`, `BulkMessageDeletedEvent` and `UpdatedAvatarEvent` replace their
  hand-written `IsLogChannelSet` checks with the overload. `UpdateMessageEvent` gets the gate it was missing, so a
  logged edit no longer looks up the author's avatar when the edit log is off (defect 17). That's 4 files.
- **The build runs on the caller's fibre**, never in the publisher, whose single reader would otherwise wait on every
  avatar and image download (LOG-2).
- **A failing build fails `Post`** with its case. The caller decides whether the log matters more than the step that
  failed. Handlers write their history row first, as today, so a failed log never loses data.
- **`GuildMemberAddedEvent`'s invite fetch isn't gated** (LOG-2): `InviteService` needs every join to keep its
  snapshot right.
- The publisher keeps its own check of the setting, because the setting can change while a message is queued.

### 3.10 KI-54

**What's known.** After an HttpClient timeout on `POST channels/{id}/messages`, about 1 run in 5, the next post to
the same channel throws `NullReferenceException` from inside DSharpPlus. Without a timeout, 10 of 10 runs were clean.

**Read for this spec** (DSharpPlus at the pinned commit `6d4bff4`, `Net/Rest/`):

- `RateLimitStrategy.ExecuteCore` handles a route it hasn't seen before differently from a known one. On the first
  request it records the route as `"pending"`, awaits the request **without a try/catch**, and only afterwards stores
  the bucket and removes `"pending"`. A timeout on that first request skips the cleanup, so the route stays
  `"pending"`, and `CleanAsync` never removes it. Every later request on the route gets a synthesized pre-emptive rate
  limit, which DSharpPlus's own retry (unlimited attempts, 2.5 s apart) runs again. That would stall the route rather
  than throw, and it matches neither the NRE nor its 1-in-5 rate. Whether the timed-out request was the first on its
  route would explain a rate, though.
- No path found leaves a bucket `null`. The likeliest NRE in the code read is `ex.Response.ResponseCode` in
  `ExecuteRequestAsync`'s `catch (DiscordException)` for an exception with no response. Not confirmed.
- Whether DSharpPlus's Polly pipeline retries a timed-out POST wasn't checked. If it does, a timed-out send can post
  twice, below our Q25 rule.

**Steps in 1.4:**

1. **Reproduce** with an integration test: an urgent alert times out, then a second urgent alert posts to the same
   channel (the variant KI-54 names). Run it 30 times. Capture the full stack trace.
2. **Test the stall**: time out the *first* request on a fresh channel's messages route, then post again, and expect
   the post within 10 s. Count the POSTs during the timed-out send, to answer the duplicate question.
3. **Contain** what the trace shows, at the edge only:
   - an NRE from DSharpPlus's REST client becomes `Unavailable`, not transient (table above). The post is lost, as Q25
     accepts, and the next one goes through;
   - if the stall is real, the timed-out call's operation is logged as having "left the route pending in DSharpPlus".
     The fix belongs upstream: no client-side workaround touches DSharpPlus internals;
   - if DSharpPlus retries timed-out POSTs, the edge doesn't turn off DSharpPlus's own pipeline.
4. **Record the DSharpPlus side in [`docs/upstream/dsharpplus.md`](../../upstream/dsharpplus.md)**, not in
   known-issues: DSP-4 (the NRE) gets the stack trace, and DSP-3 (the stall) and DSP-5 (the duplicate POST) move to
   *confirmed* or *not a bug*, each with the test that showed it. The owner reviews them, then reports or fixes them.
   Any other DSharpPlus problem met while implementing 1.4 gets its own DSP entry there too.
5. **known-issues.md**: KI-54 is marked **contained** (the bot keeps working and later posts succeed), with the
   containment and a link to DSP-4. It's marked fixed only if the cause turns out to be ours (OQ-4). A confirmed
   DSP-3 or DSP-5 gets a KI only if it changes what Grimoire does; otherwise the DSP entry is enough.

### 3.13 As built (2026-11-16)

Where the code differs from the approved text above, and why:

- **KI-54's cause was found, and it isn't the timeout** (section 3.10, step 1). The `NullReferenceException` comes
  from a startup race in DSharpPlus: a guild's cached channels briefly have no client reference while `GUILD_CREATE`
  is handled, and `DiscordChannel.Guild` dereferences it without a check. It cleared within 3 s every time, and only
  the first bot in a test process hit it. In one of its two stacks the post had already gone through, so not
  retrying it (Q25) is right. The containment is as planned (`Unavailable`, not retried). The details are in
  `docs/upstream/dsharpplus.md` (DSP-4, now *confirmed*). KI-54 is marked **contained**.
- **DSP-3 (the "pending" stall) wasn't reproduced** in 150 runs, and **DSP-5 (a resent POST) isn't a bug**: one POST
  per timed-out send, every run. No new KI was needed. The investigation stays as
  `DSharpPlusTimeoutInvestigation`, three explicit tests that a normal run skips.
- **`DiscordErrors` is split in two for testing.** DSharpPlus's REST exceptions have internal constructors, so
  `DiscordFailure.Read` reads the exception into data (kind, status, JSON code, top-level message), and the decision
  is a pure function of that, tested row by row. `Read` is tested against the real exceptions, built by reflection,
  so a DSharpPlus upgrade that changes them fails a unit test first.
- **Every defect keeps a `DiscordCallException`** whose message is the description. language-ext rethrows an
  exceptional error's exception while an effect runs and rebuilds the error from it, so a description passed to
  `Error.New(message, exception)` was lost: an integration test saw DSharpPlus's "Unauthorized: Unauthorized" instead
  of ours. A unit test now runs a defect through an effect.
- **`DiscordOperation` has two more fields**: `Action` (what the bot was doing, worded for the user) and
  `IsGuildLookup` (for OQ-9's provisional rule). Missing Access (50001) with no named permission is worded and
  refused as **View Channel**.
- **Closed DMs (50007) have a fixed message**, "The member doesn't accept direct messages from me.", since the target
  wording read badly for the invoker.
- **`SendDirectMessage` takes only the user** (`UserId`), not a guild: DSharpPlus sends a DM through `DiscordUser`,
  so the guild was never used.
- **`DeleteMessage` treats a missing channel as done too**, not just a missing message.
- **`GuildLogMessage` has no `ToBuilder`.** The factories stamp any embed without a timestamp instead, so the record
  holds a finished message from the start, and nothing is marked `[Pure]` that changes a builder. `Of` stamps the
  builder it's given, in place; pass a new one.
- **The old text class is renamed `GuildLogTextMessage`**, because the record takes the name `GuildLogMessage`. That
  touched the 28 old sites, as a rename only.
- **The gated overload on `GuildLog` takes a builder of the old types** (`Func<ValueTask<GuildLogMessageBase>>`),
  because the four LOG-2 sites still build old messages. The edit log asks `GuildLog.IsLoggedAsync` itself, since it
  can post two messages.
- **The gate also checks the module**, not only the channel as `IsLogChannelSet` did. What gets posted doesn't change,
  since the publisher already required the module.
- **The publisher runs the Discord effect itself** (`Discord<GrimoireRuntime>.SendMessage`) and matches its result.
  It keeps the old Error log for a refused post (a test pins it), and creates its `EnvIO` **without** the stopping
  token: registering on the background service's token raced the host disposing it at shutdown, which failed three
  unrelated tests with `ObjectDisposedException`. DSharpPlus's send takes no token, so nothing is lost. The purge
  row's `CreatedAt` stays on the wall clock (SH-7 is out of scope).
- **`LiveCommandIO`'s text replies name a permission** (Send Messages, or Add Reactions for the 🔒), so a text
  command the bot can't answer in its channel becomes a guild issue through the boundary.
- **`FakeGuildLog` has a gate** (`Logged`, `GateFails`), and records `guild log gate <type>` in the journal, which
  two existing journal assertions now include.

## 5. UX suggestions

All three suggestions were accepted (owner, 2026-11-15).

- **Accepted:** the refusal for a Discord 50013 names the permission and the role order in one sentence: "I don't
  have permission to ban that member. I need **Ban Members**, and my role must be above theirs." Today's unported
  commands say only "Discord refused `Ban`: I do not have permission to do that." in the mod log.
- **Accepted:** the guild issue for a missing permission names the channel when the refusal was channel-specific
  ("in <#123>"), so a moderator fixes the overwrite and not the role.
- **Accepted:** a 400 from Discord shows "Discord refused that: {Discord's message}." in red, instead of the generic
  error reply that unported code gives today. Discord's text is in English and sometimes terse ("Invalid Form Body"),
  but it's more useful than an error id. The alternative is the generic reply plus a Warning alert, which treats a 400
  as our bug (OQ-3).
- **Behaviour a user might notice:** a log post that hits a Discord 5xx is now lost instead of retried for up to 45
  s. That's Q25's decision, not a new choice.
