# Spec 2.5: Settings collections as documents

Status: **approved 2026-11-19.** The owner took the suggested answer to all four open questions (section 10) and
accepted the three UX suggestions (section 5). UX suggestion 1 was widened to cover a reward moved to another level,
so `SetRewardAsync` returns the reward it replaced (section 3.2). **Implemented 2026-11-19, not yet committed.**
Tests: unit 893 (1 skipped), integration 1,456 passing (39 skipped, unchanged) of 1,495. Build warnings: 125 (133
before). Mutation score of the new pure code: 88.7%, the rest equivalent (section 11). The equivalence check on a
production restore is still to run (2.4). Section 11 lists the results and where the code differs from this text.

Implements the plan's section 2.5, which is conflict C14 and domain decision DD-2. Five per-guild collections in
`Settings` are append-only event logs today, where the newest row for a key decides and "off" is a row of its own:

- level rewards (`Rewards`)
- XP exclusions (`XpTrackedItems`)
- the message log channel overrides (`MessageLogChannelOverrides`)
- the spam filter channel overrides (`SpamFilterOverrides`)
- the diagnostics ignores (`DiagnosticsIgnoredItems`), which delete rows instead and so keep no history at all

Each one becomes a versioned `jsonb` document per guild, stored and written exactly like 2.2's settings documents. A
change inserts a new version with who and when, and history is the list of versions. A missing entry means no reward,
not excluded, or no override, so `Inherit`, the `Watched…` types and `RewardRemoved` go. Settings `Initial`'s legacy
copy builds the documents from `main`'s tables and keeps only what is in force. Everything edits the undeployed
Settings migrations in place (Q6, C9), inside 2.0's one chain (C12).

**What the plan left to this spec**, each answered below:

| Question | Answer | Where |
|---|---|---|
| One document per collection, or fewer? | **One per collection, five new kinds in the existing `GuildSettings` table.** No sibling table | 3.1, OQ-1 |
| How is a reward's level held before DD-7's `Level` exists? | **A JSON number, an `int` in C#**, checked by `RewardEntry.Create`. DD-7 later changes the C# type and leaves the data alone. A legacy level 0 becomes 1, with the same behaviour | 3.2, OQ-3 |
| What do the cache entries become? | **One entry per guild and document**, under 2.2's `CacheKey.Document`. The two per-channel override keys go | 3.6 |

## 1. Scope

**In scope**

- **Five new document kinds** (section 3.1): `Rewards`, `XpExclusions`, `MessageLogOverrides`, `SpamFilterOverrides`
  and `DiagnosticsIgnores`. They're rows in `Settings."GuildSettings"`, written through 2.2's `UpdateDocument` and its
  version race, and read through `GetDocument`.
- **The collections are keyed in the JSON** (a map or a set), so a key can appear only once. There is no newest-row
  rule left to apply.
- **Five tables go.** `Initial` stops creating `Rewards`, `XpTrackedItems`, `MessageLogChannelOverrides` and
  `SpamFilterOverrides`, along with their two `GuildId` indexes. The post-`main` migration
  `20260919233857_AddDiagnosticsIgnoredItems` is deleted: nothing on `main` feeds it, so it has nothing to copy.
- **The types that go:** `Reward`, `RewardAdded`, `RewardRemoved`, `XpTrackedItem`, `XpWatchedItem`, the three
  `Watched…` records, the `Inherit` value of both override enums, `MessageLogChannelOverride`, `SpamFilterOverride`,
  and `DiagnosticsIgnoredItem` with its two subtypes. They are replaced by the document records and, if OQ-2 is
  accepted, by DD-8's two target unions.
- **The legacy copy** in `Initial` is rewritten to build one version-1 document per guild and collection from `main`'s
  tables, keeping only what's in force (section 6.3).
- **Keeping the bot working (ground rule 2).** `SettingsModule` keeps every read API and every behaviour. Its write
  API keeps its behaviour, but its signatures change where they took a type that goes (section 3.5). The callers,
  15 production files, change mechanically. The internals stay on EF until 3.1, as in 2.2 (2.2's OQ-4).
- **KI-103's last sites.** The override writes use `cache.SetAsync` and skip clearing the cache when nothing changed.
  These were the last places KI-103 lived, and they go, because every document write clears its key on both paths
  (2.2's rule).

**Decisions this implements:** C14, DD-2, Q5 as amended by C14, KI-103 (the override half; 2.2 fixed the guild
settings half), and, if the owner accepts them, the type half of DD-8 (OQ-2) and Q41b's check (OQ-3).

**Out of scope**

- **3.1's settings service:** the Dapper port, the final cache layout, the 1-hour expiry (Q19), fail-safe (SET-10),
  KI-105, and DD-10 (no wording in `Write<T>.Unchanged`). The `Unchanged` messages stay as they are for now.
- **DD-7's `Level` and `LevelCurve`** (3.14, 3.15). This spec holds the level as an `int`.
- **The callers of DD-8:** `XpExclusions.Excludes(...)` used directly by XP gain (3.16) and the diagnostics checks
  (3.8). This spec gives the documents those pure functions and keeps the current `IsMessageIgnored` and
  `IsMemberIgnored` API on top of them.
- **KI-73** (an ignored category covers nothing) and **KI-78**. They stay with 3.16.
- **UX changes 2 and 3** (section 5), which the sections that own those commands make. Change 1 is in scope.
- **Dropping `main`'s legacy tables** (`public."Rewards"`, `IgnoredChannels`, …). That's P-7, in a later release.

## 2. Flow

### 2.1 The Settings chain, after 2.5

| Migration | Before | After |
|---|---|---|
| `20260524035623_Initial` | 4 document-era tables + 4 collection tables, 9 indexes; copies the collections into event rows | **Edited:** the 4 collection tables and their 2 indexes go; the copy builds 4 kinds of document (section 6.3) |
| `20260919233857_AddDiagnosticsIgnoredItems` | creates `DiagnosticsIgnoredItems` | **Deleted** |

Nothing else in the chain moves, so 2.0's order holds, with Settings `Initial` running straight after
`ModelRedesign`. `Initial.Designer.cs` and the snapshot are regenerated. `EntitySetConventions` stops listing the
collection tables. That list has two parts: the names that `Initial` no longer creates, and the tables that share a
name with a `public` one. Of those, `Rewards` and `SpamFilterOverrides` go and only `Mutes` is left.

### 2.2 Reading a collection (interim, until 3.1)

1. A caller asks, for example, `ShouldLogMessage(channel, guild, channelNodes)`. The API doesn't change.
2. The module gate, as today: read `Modules` (cached), and stop if the module is off.
3. Read the guild's `MessageLogOverrides` document from the cache, under the key `Settings_MessageLogOverrides_{guild}`.
   On a miss (effect: database), read the latest version or nothing, and parse it (pure). A missing document is
   `Empty`.
4. Resolve the decision (pure): walk from the channel up through its parents. The first override found decides.
   With no override anywhere on the path, the message is logged, as today.

This replaces up to one cache read per channel in the chain, each under its own key, with one read per guild. The
other four collections read the same way. Rewards and exclusions are read on every XP gain, as today, so this costs
one cached document each.

### 2.3 Writing a collection (interim, until 3.1)

1. A command calls, for example, `IgnoreXpAsync(guild, moderator, targets)` (section 3.5).
2. Validate the input (pure): a non-empty set, and for a reward, `RewardEntry.Create`.
3. 2.2's `UpdateDocument` loop runs from here. Read the latest version, uncached (effect).
4. Apply the change to the parsed document (pure). The change also returns what it changed **against that
   version**, for example the targets that weren't already excluded.
5. If nothing changed, return `Write.Unchanged` and store nothing.
6. Otherwise insert version `n + 1`, but only if `n` is still the latest (effect, 2.2's statement). If the insert
   loses the race, go back to step 3, up to 3 times in all. After that, fail as `Unavailable`.
7. Remove the document's cache key, on both paths (KI-103).

Step 4 is the one change to 2.2's machinery: `UpdateDocument` gets an overload whose change function returns
`(T Document, R Result)`, and it returns `Write<R>`. Today's `AppendIgnoredItemsEvent` and
`AddDiagnosticsIgnoredItemsAsync` decide what changed from a separate read before they write, which is a small race.
Here the decision is made against the version that is replaced, so the reply is always right.

### 2.4 The legacy copy (in `Initial`)

All of it runs in `Initial`'s one transaction, against `main`'s tables. `ModelRedesign` leaves those tables in
place:

1. **Rewards:** one document per guild that has at least one row in `public."Rewards"`, holding each role's level
   and message. A level of 0 becomes 1 (OQ-3).
2. **XP exclusions:** one document per guild with any row in `IgnoredChannels`, `IgnoredMembers` or `IgnoredRoles`.
3. **Overrides:** one document per guild for each override table, holding only `AlwaysLog`/`NeverLog` or
   `AlwaysFilter`/`NeverFilter` (`ChannelOption` 0 or 1). Any other value meant "inherit", so it's left out.
4. **Diagnostics ignores:** nothing to copy (`main` has no such table).

Every document is version 1, with `SetBy` 0 and `SetAt` `0001-01-01`, the sentinels 2.2's copy uses. A guild with
nothing in a collection gets no document, which reads as `Empty`.

## 3. Types

### 3.1 The document kinds

```csharp
public enum SettingsDocument
{
    Modules, General, Leveling, MessageLog, Moderation, UserLog,                          // 2.2
    Rewards, XpExclusions, MessageLogOverrides, SpamFilterOverrides, DiagnosticsIgnores  // 2.5
}
```

**Why five documents, not fewer (OQ-1).** Rewards and exclusions could be folded into `Leveling`, and the overrides
into `MessageLog` and `Moderation`. That would save one cache entry per module and lose three things:

- Each collection has its own commands, so a reward change would add a version to the XP settings' history, and the
  reverse.
- A change would clear the cache entry that every XP gain reads, for something that gain may not care about.
- A collection can grow large (a guild with hundreds of overrides), while the module documents are a few hundred
  bytes. Every write copies the whole document into a new version, so one big collection would bloat the history
  of every setting it shares a document with.

C13 made the same trade-off for `Modules`. All five go in `GuildSettings`, because 2.2 deliberately left `Document`
without a check on its values. A new kind needs no migration, and the primary key serves the reads.

### 3.2 Rewards

```csharp
/// <summary>A guild's level rewards: at most one per role (C14).</summary>
public sealed record LevelRewards : ISettingsDocument<LevelRewards>
{
    public Map<RoleId, Reward> Roles { get; init; }
    public static SettingsDocument Kind => SettingsDocument.Rewards;
    public static LevelRewards Empty { get; } = new();

    public IReadOnlySet<RewardEntry> Entries { get; }                       // what GetLevelingRewardsAsync returns
    public (LevelRewards, RewardChange Change) Set(RewardEntry entry);      // add, or replace the role's reward
    public (LevelRewards, Set<RoleId> Removed) Remove(Set<RoleId> roles);   // only the roles that had one
}

public sealed record Reward(int Level, RewardMessage? Message);

/// <summary>What Set did, decided against the version it replaced, so the reply can't be wrong after a race.</summary>
public abstract record RewardChange
{
    public sealed record Added : RewardChange;
    public sealed record Moved(int FromLevel) : RewardChange;          // the level changed (the message may have too)
    public sealed record MessageChanged : RewardChange;               // same level, different message
    public sealed record Unchanged : RewardChange;                    // identical: nothing is stored
}

// Kept: callers read it today. Create moves here from RewardAdded.
public sealed record RewardEntry(RoleId RoleId, int RewardLevel, RewardMessage? RewardMessage)
{
    public static Validation<Error, RewardEntry> Create(RoleId roleId, int level, RewardMessage? message);
}
```

- **The level is an `int`, held as a JSON number.** DD-7's `Level` (3.14) reads the same number, so 3.14 changes the
  C# type and doesn't touch the data. `Create` refuses a level below 1, which is Q41b (OQ-3). Until now, Q41b was
  3.14's job.
- **Per-entry who and when are no longer stored.** They belong to the version. The design review (D-10) found no
  reader of `SetBy` or `SetAt` on any of these records, and the mod log post is the audit trail people actually read.

### 3.3 XP exclusions and diagnostics ignores

If OQ-2 is accepted, the target types are DD-8's unions, introduced here, because the old hierarchies are being
rewritten anyway:

```csharp
public abstract record XpTarget
{
    public sealed record Channel(ChannelId Id) : XpTarget;
    public sealed record Member(UserId Id) : XpTarget;
    public sealed record Role(RoleId Id) : XpTarget;

public sealed record XpExclusions : ISettingsDocument<XpExclusions>

    public static XpExclusions Empty { get; } = new();

    public bool Excludes(XpTarget target);
    /// <summary>IsMessageIgnored, pure: the channel or its parent, the member, or any of their roles (X-12).</summary>
    public bool ExcludesMessage(UserId member, IReadOnlySet<RoleId> roles, ChannelId channel, ChannelId? parent);
    public bool ExcludesMember(UserId member, IReadOnlySet<RoleId> roles);
    public IReadOnlySet<XpTarget> Targets { get; }
    public (XpExclusions, Set<XpTarget> Added) Add(IEnumerable<XpTarget> targets);

public abstract record DiagnosticsTarget
{
    public sealed record Role(RoleId Id) : DiagnosticsTarget;
    public sealed record Member(UserId Id) : DiagnosticsTarget;
}

public sealed record DiagnosticsIgnoreList : ISettingsDocument<DiagnosticsIgnoreList>

    public Set<RoleId> Roles { get; init; }

```

The document is named `DiagnosticsIgnoreList` because `Grimoire/Features/Moderation/Diagnostics/DiagnosticsIgnores.cs`
already has a `DiagnosticsIgnores` record. That record holds two `ulong` sets built from the settings, and now it can
be built straight from the document. 3.8 decides whether it stays.

If OQ-2 is declined, `IgnoredChannel`, `IgnoredMember`, `IgnoredRole` and the two `DiagnosticsIgnored…` records stay
under their current names. They lose `GuildId`, `SetBy` and `SetAt`, and 3.16 and 3.8 rename them later.

### 3.4 Channel overrides

```csharp
public enum MessageLogOverrideOption { AlwaysLog, NeverLog }       // Inherit goes
public enum SpamFilterOverrideOption { AlwaysFilter, NeverFilter }  // Inherit goes

public sealed record MessageLogOverrides : ISettingsDocument<MessageLogOverrides>
{
    public Map<ChannelId, MessageLogOverrideOption> Channels { get; init; }
    public Option<MessageLogOverrideOption> For(ChannelId channel);
    public (MessageLogOverrides, bool Changed) With(ChannelId channel, Option<MessageLogOverrideOption> option);
    /// <summary>
    ///     The first override from the channel up through its parents decides; none means log. Total: it stops after
    ///     as many steps as there are channels, so a cycle in the map can't hang it.
    /// </summary>
    public bool ShouldLog(ChannelId channel, IReadOnlyDictionary<ChannelId, ChannelId?> parents);
}

public sealed record SpamFilterOverrides : ISettingsDocument<SpamFilterOverrides>
{
    public Map<ChannelId, SpamFilterOverrideOption> Channels { get; init; }
    public Option<SpamFilterOverrideOption> For(ChannelId channel);
    public (SpamFilterOverrides, bool Changed) With(ChannelId channel, Option<SpamFilterOverrideOption> option);
}
```

`None` means "follow the parent". The commands keep `Inherit` as an option a user can pick: it is how a user says
`None`, but the domain no longer stores it. The spam filter keeps walking `DiscordChannel.Parent` in
`SpamTrackerModule`, asking `For` at each step. Each step reads the same cached document. 3.7 can move that walk into
a pure function, as `ShouldLog` does here.

### 3.5 `SettingsModule`'s API

All reads keep their signatures, except the two listing calls (OQ-4). The writes change only where they took a type
that goes:

| Today | After 2.5 |
|---|---|
| `GetLevelingRewardsAsync(guild)` → `IReadOnlySet<RewardEntry>` | Unchanged |
| `SetRewardAsync(RewardAdded)` → `Fin<RewardAdded>` | `SetRewardAsync(guild, by, RewardEntry)` → `Fin<Write<RewardChange>>` (`Saved` holds `Added`, `Moved` or `MessageChanged`) |
| `SetRewardAsync(RewardRemoved)` → `Fin<RewardRemoved>`, after a separate read for `NotFound` | `RemoveRewardsAsync(guild, by, Set<RoleId>)` → `Fin<Write<Set<RoleId>>>` (the roles that had one) |
| `GetAllIgnoredItems(guild)` → `FrozenSet<XpIgnoredItem>` | → `IReadOnlySet<XpTarget>` |
| `IsMessageIgnored(…)`, `IsMemberIgnored(…)` | Unchanged; they call `XpExclusions.ExcludesMessage`/`ExcludesMember` |
| `AppendIgnoredItemsEvent(guild, set of Ignored…/Watched…)` | `IgnoreXpAsync(guild, by, targets)` and `UnignoreXpAsync(guild, by, targets)` → `Fin<Write<IReadOnlySet<XpTarget>>>` (only the changes, as X-12 does today) |
| `ShouldLogMessage(…)` | Unchanged; it calls `MessageLogOverrides.ShouldLog` |
| `SetChannelLogOverride(channel, guild, by, option)` → `Write<MessageLogChannelOverride>` | `option` becomes `Option<MessageLogOverrideOption>`; → `Write<Option<MessageLogOverrideOption>>` |
| `GetAllOverriddenChannels(guild)` → `IAsyncEnumerable<…>`, empty on failure | → `Task<Fin<Map<ChannelId, MessageLogOverrideOption>>>` (OQ-4) |
| `GetSpamFilterOverrideAsync(guild, channel)` → `Fin<SpamFilterOverrideOption>` (`Inherit` for none) | → `Fin<Option<SpamFilterOverrideOption>>` |
| `GetAllSpamFilterOverrideAsync(guild)` → `IAsyncEnumerable<…>`, empty on failure | → `Task<Fin<Map<ChannelId, SpamFilterOverrideOption>>>` (OQ-4) |
| `SetSpamFilterOverrideAsync(…, option)` | `option` becomes `Option<SpamFilterOverrideOption>` |
| `GetDiagnosticsIgnoredItemsAsync(guild)` → `FrozenSet<DiagnosticsIgnoredItem>` | → `IReadOnlySet<DiagnosticsTarget>` |
| `AddDiagnosticsIgnoredItemsAsync(guild, items)` | `(guild, by, targets)`; same results |
| `RemoveDiagnosticsIgnoredItemsAsync(guild, items)`, `NotFound` when none were ignored | `(guild, by, targets)`; same results |
| `RemoveDiagnosticsIgnoredRoleAsync(guild, role)` | `(guild, by, role)`. The handler passes the bot's id, as `GainUserXp` does for a deleted reward role. A version needs a who, and today nothing records one because the row is just deleted |

**Two behaviours change slightly**, and each one only affects a reply:

- **`/Rewards Add`** returns what it did (`RewardChange`). Today it appends a row whatever the change. The command
  words each case differently, as section 5's accepted UX change 1 sets out.
- **`/Rewards Remove` for a role with no reward** returns `Unchanged`, decided against the replaced version. The
  command words it as today ("Did not find a saved reward for @role."), so the domain carries no mention (DD-10's
  direction).

`GainUserXp`'s clean-up of rewards whose roles were deleted (LVL-41) becomes one `RemoveRewardsAsync` call for all of
them, so one version is written instead of one row per role.

### 3.6 Cache entries (feeds 3.1)

One entry per guild and document, under 2.2's `CacheKey.Document(kind, guild)`. Five keys go:
`LevelingRewards_{guild}`, `XpIgnoredItems_{guild}`, `DiagnosticsIgnoredItems_{guild}`, and the two per-channel keys
`LogOverrides_{channel}` and `SpamFilterOverrides_{channel}`. The per-channel keys were never cleared on a "not
modified" write, which was KI-103. Their cache filled one channel at a time, and the listing commands skipped the
cache altogether.

After 2.5, settings use 11 kinds of document and 2 kinds of state entry (locks), so 3.1's layout question covers
everything in `Settings` except mutes. The expiry stays at 1 day until 3.1 applies Q19.

### 3.7 JSON encoding

This uses 2.2's `SettingsJson.Options`, with three additions:

| Value | In JSON | How |
|---|---|---|
| `Map<K, V>` with a snowflake key | an object keyed by the id as a string: `{"123…": …}` | A `JsonConverterFactory` for LanguageExt's `Map`. The snowflake converter gains `ReadAsPropertyName`/`WriteAsPropertyName` |
| `Set<T>` of snowflakes | an array of strings, sorted by id | A `JsonConverterFactory` for `Set` |
| The override enums | their names, `"AlwaysLog"` | `JsonStringEnumConverter` for these two enums only |
| An empty map or set | left out | `Map` and `Set` are structs whose default is empty, so 2.2's `WhenWritingDefault` already drops them |

`Map` and `Set` give value equality. 2.2's `Unchanged` check compares documents with `EqualityComparer<T>.Default`,
so a document has to compare by value. A record that held a `Dictionary` or a `HashSet` would compare by reference,
and every write would count as a change, which was 2.2's `==` bug in another form. They also keep the keys sorted,
so the stored JSON is the same for the same content. That makes the copy's output stable and the equivalence check's
`EXCEPT` exact.

`Map` and `Set` need their keys to be ordered, so the snowflake ids (`ChannelId`, `RoleId`, `UserId`, and the others
in `StronglyTypedIds.cs`) implement `IComparable<T>`, ordered by `Value`. That's one line each, in `Grimoire.Domain`.

Example, a guild's `XpExclusions` version:

```json
{"Channels": ["111111111111111111"], "Roles": ["222222222222222222", "333333333333333333"]}
```

### 3.8 Errors

No new cases. A target the document doesn't hold is `Unchanged`, or `NotFound` where the API returns that today (the
diagnostics removes). An invalid reward is `Invalid`. A lost write race, after 3 tries, is `Unavailable`. A document
that doesn't parse becomes `Unavailable` until 3.1, as in 2.2.

## 4. Edge cases

| Case | What happens | Error case |
|---|---|---|
| A guild with no document for a collection | `Empty`: no rewards, nothing excluded, no overrides, nothing ignored. The same as a guild with no rows today | — |
| Removing the last entry | A new version holding `{}`. The latest version, not the absence of one, says "empty", and history keeps who emptied it | — |
| Two moderators change the same collection at once (say, `/Ignore Add` for different members) | Both apply to the latest version, and the loser re-reads and re-applies. Both changes land, and each reply lists only what its own write changed | — |
| `/Ignore Add` for a mix of new and already-excluded targets | Only the new ones are added. The reply names both groups, as X-12 does today | — |
| `/Ignore Remove` for targets that aren't excluded | `Unchanged`, the same reply as today ("… were not ignored.") | — |
| `/Rewards Add` for a role that already has a reward at another level | The role's reward is replaced: `Saved(Moved(from))`. The reply says it moved, and that members who already have the role keep it (UX change 1) | — |
| `/Rewards Add` for the same role and level with a new message | `Saved(MessageChanged)` | — |
| `/Rewards Add` with exactly the reward that's set | `Unchanged`: nothing stored, a yellow reply, no mod log line | — |
| A reward moved while another moderator moves it too | Each `RewardChange` is decided against the version it replaced, so the second reply says "from" the first one's level | — |
| `/Rewards Add` at level 0 (if OQ-3 is accepted) | Refused by `RewardEntry.Create` ("Reward Level must be at least 1."), and the option's minimum becomes 1 | `Invalid` |
| `/Rewards Remove` for a role with no reward | `Unchanged`, which the command words as today's "Did not find a saved reward" | — |
| Two members level up while `GainUserXp` removes rewards for deleted roles | Each removal is one write of all the deleted roles. A lost race re-applies, and a role that's already gone isn't counted twice, so the guild issue lists each role once | — |
| `/Log Message Override option:Inherit` on a channel with no override | `Unchanged`, the same reply as today | — |
| `/SpamFilter View` with an `Inherit` entry | Can't happen any more: the `Inherit/Default` arm goes, since the document never holds one | — |
| The override listing during a database outage (OQ-4) | The generic error reply. Today it shows an empty list ("None"), which looks like "no overrides" | `Unavailable` |
| A channel's parent chain loops (it can't in Discord, but the map is input) | `ShouldLog` stops after as many steps as there are channels, then logs, as with no override | — |
| A diagnostics-ignored role is deleted in Discord | It's removed by the bot, in a version with the bot's id as `SetBy`. The mod log line is unchanged (KI-62) | — |
| A collection document that doesn't parse | `Unavailable` until 3.1, then a defect (2.2's rule). It's never read as empty: an unparsed `XpExclusions` read as empty would quietly start giving ignored members XP | `Unavailable` |
| A legacy reward at level 0 | Copied as level 1 (OQ-3). Members get exactly the same roles, because every member is at least level 1 (`GetLevelFromXp` returns `low + 1`, and rewards apply when `RewardLevel <= level`) | — |
| A legacy reward whose role was deleted | Copied. The first XP gain in that guild removes it and reports it (LVL-41), as today | — |
| A legacy override with a `ChannelOption` other than 0 or 1 | Left out: it meant "inherit" | — |
| A legacy reward message of `''` | Copied as it is, as today. `RewardMessage.FromDatabase` reads it (S-1) | — |
| A guild with hundreds of overrides | One document of a few kilobytes per version. A write copies it in full, and these writes are rare moderator commands | — |
| An empty database | The legacy tables exist and are empty, so nothing is copied. The `IF EXISTS` guards stay | — |

## 5. UX changes (accepted by the owner, 2026-11-19)

All three were accepted. Change 1 is made in 2.5, because the command changes here anyway and the data it needs
(`RewardChange`) comes from this section. Changes 2 and 3 are made by the sections named. Apart from change 1, the
only thing a user sees change in 2.5 is OQ-4's error reply where an empty list used to show.

1. **Accepted, done in 2.5: `/Rewards Add` says what it did.** Today every case gets "Successfully updated the
   rewards to include @role at level N." and a mod log line, even when nothing changed or a reward moved:

   | `RewardChange` | Reply | Mod log |
   |---|---|---|
   | `Added` | Green: "@role is now a reward at level 5." | "@mod added @role as a reward at level 5." |
   | `Moved(3)` | Green: "@role moved from level 3 to level 5. Members who already have it keep it." | "@mod moved the @role reward from level 3 to level 5." |
   | `MessageChanged` | Green: "Updated the message for the @role reward (level 5)." | "@mod updated the message for the @role reward (level 5)." |
   | `Unchanged` | Yellow: "@role is already a reward at level 5." | None |

   "Keep it" matters when the level goes up. Rewards are only ever granted, never taken away (the reason removing a
   reward leaves members their roles, LVL-114), so members between the old and the new level keep the role. When
   the level goes down, members between the two get it on their next XP gain, which needs no warning.
2. **Accepted (3.16, 3.18, 3.8):** each list view (`/Rewards View`, `/Ignore View`, `/Log Message ViewOverrides`,
   `/SpamFilter View`, `/Diagnostics Ignore View`) ends with "Last changed by @mod, <time>", read from the latest
   version. Today that information is spread across rows, and the diagnostics list has none.
3. **Accepted (3.1):** the `/settings history` view proposed in 2.2 covers these five documents too. It could show
   what each version added and removed (a diff of two sets, which is pure), not only who and when.

## 6. SQL

### 6.1 Tables

No new table. `Settings."GuildSettings"` is 2.2's, unchanged. These go from `Initial`:

```sql
-- No longer created:
"Settings"."Rewards", "Settings"."XpTrackedItems",
"Settings"."MessageLogChannelOverrides", "Settings"."SpamFilterOverrides",
"IX_MessageLogChannelOverrides_GuildId", "IX_SpamFilterOverrides_GuildId"
-- No longer created by the deleted AddDiagnosticsIgnoredItems:
"Settings"."DiagnosticsIgnoredItems"
```

After 2.5, `Settings` holds four tables: `GuildSettings`, `Mutes`, `ChannelLocks` and `ThreadLocks`.

### 6.2 Statements

There are no new statements. A collection is read with 2.2's latest-document `SELECT` and written with 2.2's
guarded `INSERT … ON CONFLICT DO NOTHING`, run through `UpdateDocument`. Five readers that used `GroupBy … First()`
and the filter for the newest row go, along with the in-memory filtering that EF forced on two of them.

### 6.3 The legacy copy (in `Initial`, each block in today's `DO $$ … IF EXISTS … $$` guard)

```sql
-- Rewards: one object per guild, keyed by role; level 0 becomes 1 (OQ-3); a null message is left out.
INSERT INTO "Settings"."GuildSettings" ("GuildId", "Document", "Version", "Value", "SetBy", "SetAt")
SELECT r."GuildId"::bigint, 'Rewards', 1,
       jsonb_build_object('Roles', jsonb_object_agg(r."RoleId"::bigint::text, jsonb_strip_nulls(jsonb_build_object(
           'Level', GREATEST(r."RewardLevel", 1), 'Message', r."RewardMessage")))),
       0, '0001-01-01T00:00:00Z'
FROM public."Rewards" r
GROUP BY r."GuildId";

-- XP exclusions: three sorted arrays per guild, each left out when empty. One guard covers all three tables,
-- which main created in one migration.
INSERT INTO "Settings"."GuildSettings" ("GuildId", "Document", "Version", "Value", "SetBy", "SetAt")
SELECT t."GuildId"::bigint, 'XpExclusions', 1, jsonb_object_agg(t.kind, t.ids), 0, '0001-01-01T00:00:00Z'
FROM (
    SELECT "GuildId", kind, jsonb_agg(id::bigint::text ORDER BY id) AS ids
    FROM (SELECT "GuildId", 'Channels' AS kind, "ChannelId" AS id FROM public."IgnoredChannels"
          UNION ALL SELECT "GuildId", 'Members', "UserId" FROM public."IgnoredMembers"
          UNION ALL SELECT "GuildId", 'Roles',   "RoleId" FROM public."IgnoredRoles") AS rows
    GROUP BY "GuildId", kind) AS t
GROUP BY t."GuildId";

-- Message log overrides: only what is in force (0 AlwaysLog, 1 NeverLog).
INSERT INTO "Settings"."GuildSettings" ("GuildId", "Document", "Version", "Value", "SetBy", "SetAt")
SELECT "GuildId"::bigint, 'MessageLogOverrides', 1,
       jsonb_build_object('Channels', jsonb_object_agg("ChannelId"::bigint::text,
           CASE "ChannelOption" WHEN 0 THEN 'AlwaysLog' ELSE 'NeverLog' END)),
       0, '0001-01-01T00:00:00Z'
FROM public."MessagesLogChannelOverrides"
WHERE "ChannelOption" IN (0, 1)
GROUP BY "GuildId";

-- Spam filter overrides: the same, with AlwaysFilter and NeverFilter.
```

`jsonb` sorts an object's keys itself, and the arrays are sorted by numeric id, the same order `Set` writes. So a
document that the copy writes and one that C# writes are equal for the same content. A unit test pins that (section
8).

**Tests for the SQL:** the copy is tested in section 8. The statements are 2.2's, and `SettingsSchemaTests` already
covers them: a lost race, a version per write, and the check constraints. One case is added for a collection kind.

## 7. Telemetry

None new, as in 2.2. Reads and writes go through EF until 3.1, and Npgsql's instrumentation (1.6) puts each statement
under the boundary's root span. No document content goes into a span: the documents are bound as parameters, which
aren't recorded (defect 9). That matters more here than in 2.2, because these documents hold member ids, which must
never be a tag. 3.1 adds the cache spans.

## 11. Results and differences from the spec

**Checks:**

- **Tests.** Unit: 893 passing, 1 skipped (856 before). Integration: 1,456 passing, 39 skipped (the same 39), out of
  1,495. Build warnings: 125, down from 133, because the code that used the obsolete `Task<Fin<T>>` bridge
  helpers (`MapFin`, `OrDefaultDuringMigration`) on these collections is gone. All on SDK 10.0.114.
- **`has-pending-model-changes`** reports nothing, and `MigrationModelTests` passes. The chain's order is unchanged
  apart from the deleted `AddDiagnosticsIgnoredItems`.
- **`SettingsCopyTests`** gains two tests that run the real deploy path. `EveryLegacyCollection_BecomesADocument_ReadTheSameWay`
  covers rewards (one at level 0, read back as 1), every kind of exclusion, overrides of each option, an override that
  meant "inherit" (left out), a guild whose only entry was one, and an id above 2^53. `ACopiedCollection_IsWhatTheBotWouldWrite`
  checks that a copied document parses to the record C# builds and has the same `jsonb` text.
- **The write races**:
  - Two concurrent `IgnoreXpAsync` calls both land, and each returns only its own member.
  - Two concurrent removals of one reward: one is `Saved`, the other `Unchanged`.
- **Mutation testing** of the new pure code (the five documents, `SettingsJson`, `RewardEntry`): 73% at first,
  counting the command's Discord shell, which only integration tests cover. The survivors pointed to three missing
  tests: removing a diagnostics role, an override found at the very last step of the parent walk, and a stored `null`
  inside a map or a set. With those added it is 88.7% (55 killed, 2 survived, 5 not covered). All seven are
  equivalent:
  - The four `_ => throw` arms of the two target unions can't be reached, because the unions' constructors are
    private. Phase 4's `closed` removes the arms.
  - The reward message's null branch is never called, because System.Text.Json reads a nullable struct's `null`
    itself.
  - Dropping `reader.Read()` before a map value changes nothing, because `Deserialize` skips the property name on
    its own.
  - The `Set` factory's `CanConvert` mutant makes no difference to how these documents are read or written.
  There was no score before: this code is new.
- **Not run: the equivalence check on a production restore** (section 8). As for 2.2 and 2.3, it needs the owner to
  restore a backup. It belongs in 2.4's rehearsal, with the count of level-0 rewards.

**Where the code differs from the text:**

- **Outage wording kept.** `UpdateDocument<T, TResult>` takes the collection's old failure message ("Could not save
  the ignored items.", "Could not set channel log override.", …), because `/Ignore Add`, the override commands and
  `/Diagnostics Ignore Add` show that `Unavailable` message, and three tests pin it.
- **No guild check on the targets.** `AppendIgnoredItemsEvent` refused items whose `GuildId` didn't match the call's
  guild (`Invalid`). The targets carry no guild now, so that state can't be built, and its four tests are gone.
- **The override `With` returns the document only**, not `(document, bool)`. `UpdateDocument` already sees "no
  change" by comparing documents, so the flag was redundant.
- **`RewardChange.Unchanged` exists but never reaches the command.** `Set` stays total, so it says when nothing
  changed. `UpdateDocument` then returns `Write.Unchanged`, and the command words both the same way.
- **A level-0 reward is refused before the command runs.** The option's minimum is now 1, so Discord's client won't
  send 0. A request that sends it anyway fails DSharpPlus's own parameter check, and the command error handler logs
  that as it does for any out-of-range option, so the reply is the generic one, not "Reward Level must be at least
  1." `RewardEntry.Create` still refuses it, for every other caller.
- **The lookup-failure tests break a document, not a table.** `SettingLookupFailureTests` made the rewards
  unreadable by renaming their table, which left every other setting readable. All guild settings now share
  `GuildSettings`, so the tests store a rewards document that doesn't parse instead. That fails the same way an
  outage does (`Unavailable`), and only for the rewards.
- **`/Diagnostics Ignore Remove` and the role-deleted handler keep `NotFound`** for "none of those were ignored", as
  before, on top of the `Unchanged` write. `RemoveDiagnosticsIgnoredRoleAsync` takes the bot's id as its `setBy`.
- **The override enums moved** to `Grimoire.Settings.Domain.Documents`, beside the documents that use them.
- **`IdConverterTests.ASettingsItemsPlainId_IsStoredAsBigint` is deleted:** no Settings entity has a plain `ulong`
  id any more.
- **A trap found on the way:** LanguageExt's `Set.Select` builds another sorted `Set`, which needs the mapped type to
  be comparable. Mapping ids to `XpTarget` that way threw at runtime. The documents use `Enumerable.Select`, with a
  comment saying why.
- **Docs:** `architecture.md`, CLAUDE.md, `known-issues.md` (KI-103 fixed), the plan (3.1, 3.8, 3.14, 3.16), and
  the manual test docs 04, 05 and 06.
