# Spec 1.6: Telemetry

Status: **implemented 2026-11-16, not yet committed.** Approved 2026-11-16: the owner took the suggested answer to
every open question (section 10), and the sidecar was replaced by in-process export at the owner's request (App
Platform has no sidecars). Section 3.12 lists where the code differs from the approved text.

Implements the plan's section 1.6: OpenTelemetry traces, metrics and logs, exported over OTLP from the bot's own
process to `grafana/otel-lgtm` on the owner's home server. **Owner, 2026-11-16:** the bot runs on DigitalOcean App
Platform, which has no sidecars, so the plan's sidecar collector is replaced by the in-process exporter (section
3.10). Each boundary
opens a root span. Each call through a capability opens a child span, so a failed command's trace shows which step
failed and why. The "[ID …]" in the generic error reply becomes the trace id. This spec also follows up the telemetry
notes that specs 1.2 to 1.5 left for it (their section 7).

Facts this spec relies on. The ones marked *(check)* are from memory and are checked against the pinned versions
before any code:

- **`Activity.Current` is an `AsyncLocal`.** A span started inside an async method is current for everything that
  method awaits. The caller doesn't see it once the method returns. So a span has to **run its body inside itself**.
  One `IO` can't start a span for a later `IO` to stop (section 3.3).
- **.NET 10's `HttpClient` has its own `ActivitySource` and `Meter`** (`System.Net.Http`), and the runtime has the
  `System.Runtime` meter. **Npgsql** has an `ActivitySource` and a `Meter` named `Npgsql`. No instrumentation
  packages are needed for these three. *(check)*
- **Serilog 4 stores `Activity.Current`'s trace and span ids on every log event.** An output template can show
  `{TraceId}`. `Serilog.Sinks.OpenTelemetry` sends them as the log record's trace context. *(check)*
- **DigitalOcean App Platform** runs each component as its own container. It has no sidecars and no persistent
  volumes: the filesystem is wiped on every deploy and restart. A component can reach another component of the same
  app over the app's internal network. *(check)*
- **The .NET OTLP exporter** sends from a background thread. Each signal has a bounded in-memory queue (traces: the
  batch processor's queue), and spans are dropped when it's full, so the caller never waits. It retries transient
  failures (429, 502, 503, 504, timeouts) in memory. It takes auth headers from `OTEL_EXPORTER_OTLP_HEADERS`.
  *(check)*
- **Metrics are cumulative** (the OTLP default). A failed export loses resolution, not counts: the next export that
  succeeds carries the running totals.
- **`grafana/otel-lgtm` is published as an image for development, demos and testing.** It holds an OpenTelemetry
  Collector (contrib), Tempo, Loki, Mimir (or Prometheus) and Grafana in one container. The collector's config file can
  be replaced by mounting one, which is where tail sampling goes (section 3.10). It keeps data across restarts only on
  a mounted data volume. It works for a one-owner home setup, but upgrades and retention are the owner's to manage.
  *(check)*
- **Discord puts the interaction token in the URL path** (`/interactions/{id}/{token}/callback`,
  `/webhooks/{application}/{token}/messages/@original`). .NET redacts query strings in `url.full`, but not paths. A
  token is valid for 15 minutes, so HTTP spans must be redacted before they're exported (section 3.6).

## 1. Scope

**In scope**

- **One telemetry capability.** `ITraceIO` becomes `ITelemetryIO` (section 3.1), with the error id, spans, span
  events and counters. Its effect module, `Telemetry<RT>`, replaces `Trace<RT>`. Its live implementation sits over one
  `ActivitySource` and one `Meter`, both named `Grimoire`.
- **Root spans at the three boundaries** (`CommandRunner`, `EventRunner`, `EffectBackgroundService`), plus two shell
  roots: the guild log publisher (one span per post, linked to the trace that queued it) and the old
  `GenericBackgroundService` tick (OQ-6).
- **Child spans in the effect modules**: `Db<RT>`, `Discord<RT>` and `PluralKit<RT>`, one span per logical call.
  Each retry is an event on that span. Npgsql's and `HttpClient`'s own spans nest under it.
- **Pure parts**: how a finished operation becomes an outcome, a status and tags (`SpanResult`, `TelemetryTags`), the
  sampler's rule for spans with no parent, and URL redaction. All are unit tested.
- **Metrics**: duration histograms for commands, events, worker ticks and capability calls, all tagged with the
  outcome, so the outcome counts come from the histograms. Also counters for retries, guild log posts, guild issues
  and alerts, and gauges for the guild log queue, the PluralKit queue and the gateway. Built in: runtime, Npgsql pool,
  `HttpClient` and FusionCache.
- **Logs**: Serilog's events carry the trace id. They go to the console as now, and over OTLP to home (OQ-4).
- **The error id**: the trace id, in the reply, the log line and the alert (section 5).
- **Configuration**: the standard `OTEL_*` environment variables. With no endpoint set, nothing is exported, but
  spans still run in process, so the error id is still a trace id.
- **In-process export** straight to home over HTTPS with basic auth, with bounded queues sized for short home
  outages (section 3.10). The home side's config goes in the repo (`deploy/otel-lgtm/`: the collector config with tail
  sampling), along with a runbook (`docs/operations/telemetry.md`: NPM routes, `otel-lgtm`'s volume and retention, and
  App Platform's environment variables). The owner deploys it.
- **Small changes to the error exceptions** so tags can be read from values rather than strings. `DatabaseException`
  gains `SqlState`, `Table` and `Constraint`. `DiscordCallException` gains `Status` and `Code`.
  `PluralKitCallException` gains `Status`.
- **A name for the Npgsql data source** (`"grimoire"`). Otherwise Npgsql's pool metrics are tagged with the
  connection string, which names the host, database and user.

**Out of scope**

- **Spans for the settings capability**: it arrives in 3.1, which follows section 3.9's convention. Until then,
  FusionCache's own metrics give the cache hit rate.
- **The outbox backlog gauge**: there's no outbox until TD-1 lands (2.2, 3.4, 3.5). The name
  `grimoire.outbox.backlog` is reserved here, and 3.4 registers it.
- **Traces for unported commands and event handlers.** They don't go through a runner, and DSharpPlus.Commands has no
  hook that wraps a command's execution. Unported commands still get the duration metric (section 3.7). Each Phase 3
  port gets traces through the runner.
- **Grafana dashboards and alert rules.** The runbook suggests a starter set, and the owner builds them in Grafana.
- **Running the home server.** The runbook describes it, and the owner runs it.
- **Profiling and exemplars.** Can be added later. Nothing here prevents them.

**IDs covered:** plan 1.6; defect 9 (no content or names in spans, tags or metrics); the telemetry hand-offs in
specs 1.2 (outcome tag, error id, root spans), 1.3 (statement spans, retries, the pool), 1.4 (operation spans,
retries, guild log counters, guild issues) and 1.5 (the PluralKit span, its queue gauge and retries).

## 2. Flow

### 2.1 A command, from DSharpPlus to Grafana

```
DSharpPlus ──► CommandRunner.Execute                                                 shell
   │  Telemetry<RT>.Span(command "Warn", root) runs CommandBoundary.Run inside it     effect; Activity.Current = root
   │     privacy, validate                                                            pure
   │     act:
   │       Db<RT>.Query(WarnSql.ActiveSinCount)
   │         └─ span "db Warn.ActiveSinCount" (Client) ── retry events
   │              └─ Npgsql's span (built in; the parameterised text, no values)
   │       Discord<RT>.SendMessage(…)
   │         └─ span "discord Discord.SendMessage" (Client)
   │              └─ System.Net.Http's span (built in; URL redacted, section 3.6)
   │     render; on an outage or a defect: ErrorId = the root's trace id
   │       ──► log line (carries the trace id) ──► alert "[Id …]" ──► reply "[ID …]"
   ▼
 root span ends: SpanResult.Of(outcome) ──► outcome tag, status                      pure, then effect
CommandHandler (CommandExecuted) ──► grimoire.command.duration                       shell, every command
```

### 2.2 Export

```
App Platform (bot container)                       home server
────────────────────────────                       ───────────
spans   ─┐ bounded queues, background                Nginx Proxy Manager
metrics ─┼─ export threads; retry transient ─HTTPS─►  TLS + basic auth (access list)
logs    ─┘ in memory; drop when full;    OTLP/http     │
           never block the bot                         ▼
                                                     otel-lgtm
console ──► App Platform runtime logs                  collector: tail_sampling (traces), batch
           (every line, with its trace id)              Tempo · Mimir · Loki · Grafana :3000
                                                            ▲
                                                  NPM: TLS + Grafana login
```

Nothing in the bot waits on the export. If home is down, each queue fills while the exporter retries, then new data
is dropped. After the outage, traces and logs from that gap are missing, and metrics recover their totals. The
console logs in App Platform still have every line with its trace id (OQ-3).

### 2.3 One span

1. **Start** (effect): `ActivitySource.StartActivity(name, kind, tags)` with the operation's initial tags. Root spans
   carry `grimoire.root`, which is how the sampler tells them apart (section 3.5). The start time is taken from the
   monotonic clock.
2. **Run the body** (effect): the body's `IO` runs inside the same async method, so the span is
   `Activity.Current` for all of it.
3. **Classify** (pure): `SpanResult.Of(result, shuttingDown, outcomeOf)` returns the outcome label, whether it's an
   error status, the tags read from the error, and the exception to record.
4. **Finish** (effect): set the tags and the status, record the exception, stop the span, and record the duration
   histogram for the operation's kind with the outcome tag. The body's result is returned unchanged: success, or the
   same `Error`.

If the span isn't sampled (for example a database call with no parent, from a bridge), steps 1, 2 and 4 still time
the call and record the metric. Only the span is skipped.

## 3. Types

In `Grimoire/Functional/Telemetry/` unless a path says otherwise.

### 3.1 The capability

```csharp
/// <summary>
///     Spans, span events and counters (spec 1.6). One capability, because a span and its duration metric share the
///     outcome. Replaces ITraceIO. The live implementation is the only code that touches ActivitySource and Meter.
/// </summary>
public interface ITelemetryIO
{
    /// <summary>The current trace id (32 hex characters). 10 random hex characters when no span is recording.</summary>
    IO<string> ErrorId { get; }

    /// <summary>
    ///     Runs <paramref name="body" /> inside a span. The span is current for everything the body awaits, so Npgsql's
    ///     and HttpClient's spans nest under it. When it ends, the span gets the result's outcome, tags and status, and
    ///     the duration is recorded for the operation's kind. The result passes through unchanged.
    /// </summary>
    IO<A> Span<A>(Operation operation, IO<A> body, Func<A, string> outcomeOf);

    /// <summary>An event on the current span ("retry", "guild-issue"). Does nothing when no span is recording.</summary>
    IO<Unit> Event(string name, Tags tags);

    IO<Unit> Count(Counter counter, Tags tags);
}

/// <summary>What a span is about. Its name is never content, a person's name or SQL text (defect 9).</summary>
public sealed record Operation(OperationKind Kind, string Name, Tags Tags)
{
    public static Operation Command(Invocation invocation);          // "command Warn", root, Server
    public static Operation Event(string handler, Option<GuildId> guild);  // "event DeleteMessageEvent", root, Consumer
    public static Operation WorkerTick(string worker);              // "worker LogCleanup", root, Internal
    public static Operation WorkerItem(string worker, string key);  // "worker.item", Internal; key as a tag
    public static Operation Database(Sql sql);                      // "db Warn.InsertSin", Client
    public static Operation Discord(string operation, Option<GuildId> guild);  // "discord Discord.GetMember", Client
    public static Operation PluralKit();                            // "pluralkit PluralKit.GetMessage", Client
}

public enum OperationKind { Command, Event, WorkerTick, WorkerItem, GuildLogPost, Database, Discord, PluralKit, Settings }

/// <summary>Tag names and values. Values are ids, numbers, enums or fixed labels: never free text.</summary>
public sealed record Tags(Seq<(string Name, object Value)> Items);

public enum Counter { Retries, WorkerItems, GuildLogSkipped, GuildLogPosts, GuildIssues, Alerts, PluralKitQueueFull }
```

```csharp
public static class Telemetry<RT> where RT : Has<Eff<RT>, ITelemetryIO>
{
    public static Eff<RT, string> ErrorId { get; }

    /// <summary>
    ///     Runs the effect inside a span. It gets the runtime and runs the body's IO with it, inside the span, so the
    ///     span covers the whole effect, Discord and database calls included.
    /// </summary>
    public static Eff<RT, A> Span<A>(Operation operation, Eff<RT, A> body, Func<A, string>? outcomeOf = null);

    public static Eff<RT, Unit> Event(string name, Tags tags);
    public static Eff<RT, Unit> Count(Counter counter, Tags tags);
}
```

`outcomeOf` defaults to `"Success"`. The root spans pass `CommandOutcome.ToString()`, because a boundary never fails:
its result is the outcome. `PluralKit<RT>` passes the `ProxyLookup` case (`NotProxied`, `ReplacedByProxy`, …).

### 3.2 The outcome of a span (pure)

```csharp
public static class SpanResult
{
    /// <summary>What a finished operation looks like in its span and its metric. Pure.</summary>
    public static SpanEnd Of<A>(Fin<A> result, bool shuttingDown, Func<A, string> outcomeOf);

    /// <summary>For a root span, whose result is the boundary's outcome.</summary>
    public static SpanEnd Of(CommandOutcome outcome);
}

public sealed record SpanEnd(string Outcome, bool IsError, Tags Tags, Option<Exception> Exception);
```

| Result | `grimoire.outcome` | Status | Tags | Exception recorded |
|---|---|---|---|---|
| Success | `outcomeOf(value)` | unset | — | — |
| `Invalid`, `NotFound`, `Forbidden` | the case | unset: a refusal isn't a fault | `TelemetryTags.Of(error)` | — |
| `Unavailable` | `Unavailable` | **error**, `error.type` = `Unavailable` | `TelemetryTags.Of(error)` | the one it keeps (`DatabaseException`, …) |
| Defect | `Defect` | **error**, `error.type` = the exception's type, or `Defect` | `TelemetryTags.Of(error)` | yes |
| Cancelled by shutdown | `Cancelled` | unset | — | — |
| Root: `CommandOutcome` | its name | error for `Unavailable` and `Defect` | — | — (the child span that failed has it) |

The case comes from `Outcome.Classify`, the function the boundaries already use, so a span and its reply can't
disagree. Errors on spans mean only outages and bugs, so "status = error" is what tail sampling and Grafana alerts
key on (OQ-2).

### 3.3 Tags read from an error (pure)

```csharp
public static class TelemetryTags
{
    /// <summary>The tags a failure adds to its span. Reads typed fields only, never a message. Pure.</summary>
    public static Tags Of(Error error);
}
```

| Error | Tags |
|---|---|
| any failure | `grimoire.outcome` |
| `Unavailable` with a `DatabaseException` | `db.response.status_code` (SQLSTATE), `db.collection.name` (table), `grimoire.db.constraint`, `grimoire.transient` |
| `Unavailable` or a defect with a `DiscordCallException` | `http.response.status_code`, `grimoire.discord.code`, `grimoire.transient` |
| `Unavailable` with a `PluralKitCallException` | `grimoire.pluralkit.problem`, `http.response.status_code` when there was one |
| `Forbidden` with a `BotRefusal` | `grimoire.permission` (the permission's name) |
| a `ManyErrors` | the tags of its worst case (the one `Outcome.Classify` picked) |

**Never put on a span:** an error's message, Postgres's message, Discord's error body, the SQL text built by us, a
parameter value, a message's content, a user's or member's name, or a user id. Guild, channel and message ids are
allowed. A refusal's message is shown to the user, and it may name someone, which is why the message isn't a tag.

The recorded exception carries its message, as the error log already does. Our exceptions are written to hold no
content (specs 1.3 and 1.4). A defect thrown by a library could quote a value, and that risk is the same as in today's
error log.

### 3.4 The live capability

```csharp
internal sealed class LiveTelemetryIO(ActivitySource source, GrimoireMetrics metrics, TimeProvider time)
    : ITelemetryIO
```

- **`Span`** is one `IO.liftAsync`. It starts the activity, runs the body's `IO` in the same async method (so the
  body's awaits see it as current), classifies the result with `SpanResult.Of`, finishes the span, records the
  histogram, and returns the result. If the body fails, the `IO` fails with the same `Error`.
- **`ErrorId`** reads `Activity.Current?.TraceId`. When nothing is recording (no listener, or code outside any span),
  it returns 10 random hex characters, as `LiveTraceIO` does today.
- **`Event`** adds an `ActivityEvent` to `Activity.Current`. **`Count`** adds 1 to the counter.
- `ActivitySource` and `Meter` (both `"Grimoire"`) are singletons created by `AddTelemetry`. `GrimoireMetrics` holds
  the instruments.

### 3.5 The sampler (pure rule)

```csharp
internal sealed class GrimoireSampler : Sampler
{
    /// <summary>
    ///     A span with a parent follows its parent. A span with no parent is kept only when it is one of ours and
    ///     carries grimoire.root. Everything else with no parent is dropped. That covers Npgsql's spans from unported
    ///     EF code, HttpClient spans DSharpPlus sends on its own flow, and our own capability spans in a bridge.
    /// </summary>
    public override SamplingResult ShouldSample(in SamplingParameters parameters);

    internal static bool KeepRoot(IEnumerable<KeyValuePair<string, object?>>? tags);   // pure, tested
}
```

Without this rule, each unported settings read and each DSharpPlus REST call made outside our spans would become a
one-span trace. Every kept trace is recorded in full. Which traces are stored is decided by the collector at home (OQ-2).
Metrics are recorded before sampling and don't depend on it.

### 3.6 URL redaction (pure)

```csharp
internal static class UrlRedaction
{
    /// <summary>
    ///     Replaces the token segment in Discord's interaction and webhook paths with "{token}":
    ///     /interactions/{id}/{token}/…, /webhooks/{application}/{token}/…. Other URLs are unchanged.
    /// </summary>
    public static string Redact(string url);
}
```

A `BaseProcessor<Activity>` (`RedactingProcessor`) runs it on `url.full` and `url.path` in `OnEnd` for every
`System.Net.Http` span, before the exporter sees it. The HTTP span's name is just the method (`POST`), so it's safe.
`HttpClient`'s metrics carry only the host, never the path.

### 3.7 Where spans and metrics come from

| Place | Span | Kind | Initial tags | Metric |
|---|---|---|---|---|
| `CommandRunner.Execute`, around `CommandBoundary.Run` | `command {name}` | Server, root | `grimoire.command`, `grimoire.invocation` (slash/text), `grimoire.guild.id`, `grimoire.command.queue_delay_ms` (Discord's timestamp to the runner) | — (see `CommandHandler`) |
| `CommandHandler.HandleEventAsync` / `CommandErrored`, every command, ported or not | — | — | — | `grimoire.command.duration`, from Discord's timestamp, as the "finished" log line already measures it |
| `EventRunner.Run` | `event {handler}` | Consumer, root | `grimoire.handler`, `grimoire.guild.id` | `grimoire.event.duration` |
| `EffectBackgroundService.Supervised` | `worker {TaskName}` | Internal, root | `grimoire.worker`; at the end `grimoire.worker.items` (attempted) | `grimoire.worker.tick.duration` |
| `Items.Item` (when not in backoff) | `worker.item` | Internal | `grimoire.worker`, `grimoire.worker.item` (the key) | `grimoire.worker.items` counter, by outcome |
| `GenericBackgroundService` tick (OQ-6) | `worker {TaskName}` | Internal, root | as above | as above |
| `GuildLogPublisher`, per post | `guildlog post` | Consumer, root, **linked** to the span that queued it | `grimoire.guild.id`, `grimoire.guildlog.type` | `grimoire.guildlog.posts`, by outcome |
| `Db<RT>` `Query`, `QueryOptional`, `QuerySingle`, `Execute`, `Fold` | `db {Sql.Name}` | Client | `db.system.name` = `postgresql`, `grimoire.sql.read` | `grimoire.call.duration` |
| `Db<RT>.Transaction` | `db transaction` | Client | `grimoire.db.isolation` | `grimoire.call.duration` |
| `Discord<RT>`, each method | `discord Discord.{Method}` | Client | `grimoire.guild.id` when known | `grimoire.call.duration` |
| `PluralKit<RT>.Lookup`, when it asks | `pluralkit PluralKit.GetMessage` | Client | — | `grimoire.call.duration`; the outcome is the `ProxyLookup` case |
| each retry in `Db`, `Discord`, `PluralKit` | event `retry` on the call's span: `attempt`, the failed attempt's case and tags | — | — | `grimoire.call.retries` |
| `BotRefusals.Report` | event `guild-issue`: `code` | — | — | `grimoire.guild_issues`, by code |
| `GuildLogs<RT>.Post`, the gate says no | — | — | — | `grimoire.guildlog.skipped`, by type |
| `LivePluralKitIO`, after the bucket | tag `grimoire.pluralkit.queue_wait_ms` on the current span | — | — | `grimoire.pluralkit.queue.wait` |

**Statements inside a transaction** run through `IDatabaseSession`, which is `IO`, not `Eff`, so they get no
Grimoire span. Npgsql's child spans under `db transaction` show each statement's parameterised text. That's enough to
find the step, and it keeps the session interface unchanged.

**The guild log link**: `LiveGuildLogIO.Enqueue` and the bridge overloads capture `Activity.Current?.Context` with
the message. `GuildLog`'s channel holds `(GuildLogMessage, ActivityContext?)`, so the record itself is unchanged
(C5). The publisher starts its span with a link to that context. A slow log post then shows up under its own trace,
and the command's trace links to it.

**Why `CommandHandler` records the command metric** rather than the runner: it sees every command, including
unported ones and the failures that happen before our code runs (`CheckFailed`, `ParseError`), and it already times
from Discord's timestamp, which is what the user waits for. The root span times only the runner.
`grimoire.command.queue_delay_ms` tells the two apart.

### 3.8 Runtime changes

- `ITraceIO` → `ITelemetryIO`, `Trace<RT>` → `Telemetry<RT>`, and `GrimoireEnv.Trace` → `GrimoireEnv.Telemetry`.
  The `Has<>` on both runtimes is renamed. `CommandBoundary.Crashed` uses `Telemetry<RT>.ErrorId`.
- **`Db<RT>`, `Discord<RT>` and `PluralKit<RT>` gain `Has<Eff<RT>, ITelemetryIO>` in their constraints** (OQ-1).
  Both runtimes already satisfy it. Generic feature functions that use them (today: `DeletedMessageLookup<RT>` and
  the tests) add it to their `where` clause.
- **The boundaries' constraints** gain it as well: `CommandBoundary` already has it as `ITraceIO`.
  `EventBoundary`, `BotRefusals` and the worker classes add it.
- `TestEnv` gets `FakeTelemetry` (section 3.11).

### 3.9 The convention for Phase 3

- **A feature gets its spans for free.** Every database, Discord, PluralKit and (from 3.1) settings call is a span,
  and the runner opens the root. A feature adds a span only around a step that isn't a capability call but can be
  slow, for example an image download in the shell.
- **A feature may add counters for its own events** (`grimoire.spam.mutes`, `grimoire.xp.awarded`), named in its spec
  section 7, with bounded tags only: never a guild, user or channel id on a metric.
- **3.1** wraps `Settings<RT>` calls in `settings {Module}.{Read|Write}` spans (Client kind, `OperationKind.Settings`)
  and tags a cache hit. **3.4 and 3.5** register `grimoire.outbox.backlog`.

### 3.10 Configuration and registration

`AddTelemetry(configuration, environment)` in `Grimoire/Functional/Telemetry/TelemetryServiceRegistration.cs`, called
from `AddGrimoire`:

- **Resource**: `service.name` = `grimoire`, `service.version` = the assembly's informational version (with the commit
  hash), `deployment.environment.name` = the host environment, and `service.instance.id`. `OTEL_RESOURCE_ATTRIBUTES`
  can add more.
- **Tracing**: `GrimoireSampler`; sources `Grimoire`, `Npgsql` and `System.Net.Http`; `RedactingProcessor`; and the
  OTLP exporter when an endpoint is set. Batch export, with the queue below. A full queue drops spans, and the exporter
  never blocks the caller.
- **Metrics**: meters `Grimoire`, `Npgsql`, `System.Net.Http`, `System.Runtime` and FusionCache's (through
  `ZiggyCreatures.FusionCache.OpenTelemetry`, metrics only); the OTLP exporter when an endpoint is set, every 30 s.
  Durations are in seconds, with explicit buckets 5 ms, 10, 25, 50, 100, 250, 500 ms, 1 s, 2, 5, 10, 30.
- **Logs**: `Serilog.Sinks.OpenTelemetry` is added in code (not in `appsettings.json`) when an endpoint is set, at the
  level the `Serilog` section sets. The console sink stays. Its template gains `{TraceId}` (section 5).
- **Endpoint**: the standard `OTEL_EXPORTER_OTLP_*` variables (below), read by the exporters themselves. Grimoire
  reads the endpoint only to decide whether to add them. Serilog's sink gets the same endpoint and headers.
- **Off** (no endpoint: development, tests): spans, metrics and the error id still work in process, and nothing is
  exported. One Information line at startup: "Telemetry export is off: OTEL_EXPORTER_OTLP_ENDPOINT is not set."
- **Shutdown**: the host disposes the providers, which flush (App Platform gives a container time to stop on a
  deploy). A crash loses what's still queued.
- **Npgsql**: `NpgsqlDataSource.Create(connectionString)` becomes a `NpgsqlDataSourceBuilder` with
  `Name = "grimoire"`, so the pool metrics aren't tagged with the connection string.
- **Packages** (exact versions, pinned when the code is written): `OpenTelemetry.Extensions.Hosting`,
  `OpenTelemetry.Exporter.OpenTelemetryProtocol`, `Serilog.Sinks.OpenTelemetry`,
  `ZiggyCreatures.FusionCache.OpenTelemetry`, and `OpenTelemetry.Exporter.InMemory` in the integration tests.

**Export from the bot's process.** The exporters send straight to home over HTTPS. App Platform sets these as
app-level environment variables, with the header encrypted:

| Variable | Value |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `https://otlp.<domain>` |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf` |
| `OTEL_EXPORTER_OTLP_HEADERS` | `Authorization=Basic <base64 user:password>` (encrypted) |
| `OTEL_EXPORTER_OTLP_TIMEOUT` | `10000` (ms per export) |

- **Queues, sized for short outages.** Traces: a queue of 16,384 spans, exported in batches of 512 every 5 s. Logs:
  the Serilog sink's queue, at a matching bound. Metrics hold no queue: they're cumulative. With these bounds, memory
  stays at a few tens of MB at most, and a home outage of a few minutes loses nothing. Past that, new spans and logs
  are dropped (OQ-3). Exact sizes come from the first week's volume.
- **Retries:** the exporter's built-in in-memory retry for transient failures. Its disk retry would write to
  App Platform's wiped filesystem, so it would survive a home outage but not a deploy. It's left off (OQ-3).
- **Dropped data is counted.** The SDK's own counts of dropped spans and failed exports, plus Serilog's self-log, go
  to the console at Warning, at most once a minute. That way a long home outage shows in App Platform's logs.
- **A separate collector component** in the same App Platform app (an internal service) would buffer through a bot
  redeploy, but it costs another container and still has no persistent disk. It's not needed unless OQ-3 says so.

**The home side** (`deploy/otel-lgtm/`, and the runbook):

- `otel-lgtm` with its data directory on a volume, and its bundled collector's config replaced by
  `deploy/otel-lgtm/otelcol-config.yaml`. That file is the image's default with `tail_sampling` added to the traces
  pipeline (OQ-2), plus a `memory_limiter`. Tail sampling has to run here, because it needs the whole trace and the
  bot exports spans as they end. Exact keys are checked against the image's collector version.
- **NPM proxy host 1**, for example `otlp.<domain>`, goes to `otel-lgtm:4318`, with TLS and an access list using basic
  auth. It accepts OTLP/HTTP only (`/v1/traces`, `/v1/metrics`, `/v1/logs`); 4317 and 4318 are never published
  directly. Its request body limit is raised to at least 8 MB, so a large batch isn't refused with a 413.
- **NPM proxy host 2**, `grafana.<domain>`, goes to `otel-lgtm:3000`, with TLS and Grafana's login (the admin
  password changed from the default), plus an access list if wanted.
- Retention for Tempo, Loki and Mimir is set in their config files (OQ-8).

### 3.11 The fakes

- **`FakeTelemetry`** (`Grimoire.UnitTests/Functional/Fakes/`) replaces `FakeTrace`. It runs the body and records a
  `RecordedSpan(Kind, Name, Tags, Outcome, IsError, Events, Parent)` in the `Journal` as `span {name} {outcome}`, and
  one entry per event and counter. Parenthood is tracked with its own `AsyncLocal`, so a test can check nesting
  without a real `ActivitySource`. `ErrorId` is a fixed value, as `FakeTrace.Id` is today.
- **Integration**: `GrimoireTestBot` gains `WithTelemetry()`, which adds in-memory exporters and exposes the exported
  spans and metrics.

### 3.12 As built (2026-11-16)

Where the code differs from the approved text above, and why:

- **The checked facts.** `Activity.Current` flows from a span into its body across `IO.liftAsync`, `Task.Yield`,
  `RetryWhile`, `Timeout` and `Fork` (probed, and guarded by `LiveTelemetryIOTests`). Npgsql 10's source and meter
  are `Npgsql`, and its spans carry `db.query.text`. The OTLP exporter retries in memory (`in_memory`; an
  experimental `disk` mode exists and is left off). Serilog's OTLP sink reads the same `OTEL_EXPORTER_OTLP_*`
  variables and sends the trace and span ids. Packages: OpenTelemetry 1.21.0, `Serilog.Sinks.OpenTelemetry`
  4.2.0, `ZiggyCreatures.FusionCache.OpenTelemetry` 2.8.0 (matching FusionCache).
- **`Span` takes `Func<A, SpanEnd>`**, not a label. A boundary never fails, so its root's status has to come from
  its outcome (`Telemetry<RT>.Root`, which uses `SpanResult.Of(CommandOutcome)`), and the guild log publisher
  describes a failed post with `SpanResult.OfError`. Labelled successes use `SpanResult.Succeeded(label)`.
- **`ITelemetryIO.Tag`** was added, for what's known only at the end of a span (a tick's `grimoire.worker.items`).
- **The boundaries open their own roots.** `CommandBoundary.Run` and `EventBoundary.Run` wrap themselves in the root
  span, rather than the runners doing it, so the unit tests see the roots. `CommandBoundary` gains an `ITimeIO`
  constraint for the queue delay.
- **The worker's failure reports run inside the tick's span**, so the alert's "[Id …]" is the tick's trace id.
- **`FakeTelemetry` keeps its own lists**, not the `Journal`: putting spans in the journal would have changed every
  test that checks the order of calls.
- **Retry events** are recorded at the start of each attempt after the first, so their number is exactly the
  number of retries (an event per failure would count the last, unretried one too).
- **Item and post counters** (`grimoire.worker.items`, `grimoire.guildlog.posts`) are recorded by the span when it
  ends, so they aren't in the `Counter` enum.
- **The trace link (OQ-9)** is an `Alert.TraceId` field, set by the boundaries, and `FormatUrgent` adds
  "[View trace](<url>)" when `telemetryTraceUrl` is set and the id is a real trace id (32 characters). The daily
  warning report doesn't link.
- **Export problems** are read from the OpenTelemetry SDK's EventSources by `ExportHealth` (an `EventListener`,
  registered only when exporting), at most one log line per kind a minute.
- **The tail-sampling config** is a block to merge into `otel-lgtm`'s own collector config
  (`deploy/otel-lgtm/tail-sampling.yaml`), not a whole file: the image's internal exporter endpoints aren't
  documented, and a guessed copy would break on an upgrade. The policy is an `ottl_condition` on the tick span
  itself, so a failed tick whose children succeeded isn't dropped.
- **Optional dependencies.** `LivePluralKitIO` and `AlertService` take `GrimoireMetrics` (and `AlertService` the
  configuration) as optional constructor parameters, so tests that build them directly are unchanged.
- **The integration tests' `DatabaseRuntime`** gained `ITelemetryIO` (OQ-1's cost), backed by the live capability on
  a source nothing listens to.
- **HTTP spans can't be seen in the test host.** .NET creates `HttpClient`'s span inside the socket handler, and the
  fake Discord REST replaces that handler. So the fake REST records the span that was current when each request
  arrived (`RecordedRequest.SentFrom`), which is the parent a real HTTP span gets. **Finding:** DSharpPlus sends its
  REST calls on the caller's flow, so in production they nest under our `discord` span and the interaction's calls
  under the command's root. No DSP entry is needed. Redaction is unit-tested on the processor itself
  (`RedactingProcessorTests`).
- **Npgsql 10 traces a connect as well as the command** when the pool opens a connection, both under the `db` span.
- **No `GrimoireTestBot.WithTelemetry()`.** Only one test class needs the exporters, so it adds them through
  `configureHost`.
- **The telemetry integration tests run on a pool of their own**, built by `AddGrimoire` as in production, so the
  pool's name (`grimoire`) is checked; other tests keep the shared pool.

## 4. Edge cases

| Case | What happens | Outcome, status |
|---|---|---|
| Home down for a few minutes | The exporters retry in memory and the queues hold the backlog; it arrives late. The bot is unaffected | — |
| Home down longer than the queues hold | New spans and logs are dropped and counted (a console Warning, at most once a minute). Metrics recover their totals at the next export. App Platform's console logs still have every line with its trace id (OQ-3) | — |
| A bot redeploy or restart | What's queued is flushed on a clean stop, and lost on a crash. The new container starts with empty queues | — |
| Home's basic auth wrong or the NPM route missing (401, 403, 404, 413) | Not transient: each batch is dropped at once and counted. The console Warning names the status | — |
| A burst bigger than the trace queue | The newest spans are dropped, so some traces are partial; their root spans still carry the outcome if they end after the burst | — |
| No endpoint set (development, tests) | Nothing is exported, with one startup line. The error id is still the trace id | — |
| A failure outside any span (a bridge, unported code) | The error id is 10 random hex characters, as today | — |
| An unported command fails | The old handler replies with its random id. `grimoire.command.duration` is recorded with the outcome. No trace | — |
| An outage in a command | Root span outcome `Unavailable` (status error). Child `db …` span with retry events and the exception. The same trace id in the reply, the log line and the alert | `Unavailable`, error |
| A refusal (`Invalid`, `NotFound`, `Forbidden`) | Root outcome is the case, status unset. The child that refused has the tags (status 403, code 50013, the permission). No id is shown to the user (refusals don't show one) | the case, unset |
| A read retried twice, then success | One `db` span, outcome `Success`, two `retry` events, `grimoire.call.retries` + 2 | `Success` |
| A write that fails | One span, no retry events (Q25) | the case |
| DSharpPlus sends a REST call on a flow other than ours | Its `HttpClient` span has no parent and is dropped by the sampler. Our `discord` span still has the duration and, on failure, the status and code. The integration test finds out which is true; if REST calls don't nest, that's a DSP entry | — |
| An EF query in unported code | No parent, so its Npgsql span is dropped. Inside a `GenericBackgroundService` tick, it nests under the tick (OQ-6) | — |
| A worker tick that finds nothing to do | A short root span with `grimoire.worker.items = 0`. Whether it's stored is up to tail sampling (OQ-2) | `Success` |
| An item skipped by its backoff | No span. The tick's `grimoire.worker.items` doesn't count it | — |
| Shutdown during a span | Outcome `Cancelled`, status unset. The providers flush on dispose | `Cancelled` |
| A Discord interaction URL | The token segment becomes `{token}` before export (section 3.6) | — |
| PluralKit's queue full | The span's outcome is `Unavailable` with `grimoire.pluralkit.problem = QueueFull`, and `grimoire.pluralkit.queue.full` goes up by 1 | `Unavailable`, error |
| A user quotes an id from a trace tail sampling dropped | Can't happen for `Unavailable` or a defect, because errors are always kept. The logs (Loki) carry the trace id either way | — |
| Clock skew between the cloud and home | Spans use the bot's clock, so their order within a trace holds. Grafana shows ingestion lag only | — |
| A guild with very many commands | Guild ids are on spans only, never on metrics, so metric cardinality stays bounded: command names × outcomes, statement names × outcomes | — |

## 5. UX suggestions

- **Suggested:** the generic reply quotes the **full 32-character trace id**, in a code span so it copies cleanly:
  "Something went wrong while running `/warn`. It's been reported. If it keeps happening, quote ID
  `4bf92f3577b34da6a3ce929d0e0e4736`." Tempo finds a trace only by its full id, so a shortened one would need a
  Loki search first (OQ-7).
- **Suggested:** the Urgent alerts from events and workers also carry "[Id …]" (today only command alerts do), so
  every alert leads to its trace.
- **Suggested:** an optional `telemetryTraceUrl` setting, for example
  `https://grafana.<domain>/explore?…{traceId}…`. When it's set, alerts add a "View trace" link. This is for the
  owner's alert channel only; users never see it (OQ-9).
- **Suggested:** the console template gains the trace id when there is one:
  `[{Timestamp:HH:mm:ss} {Level:u3}] {Message:lj} {TraceId}{NewLine}{Exception}`.
- **Moderators and members see no other change.**

## 6. SQL

None. 1.6 adds no statement.

Npgsql's spans carry each statement's parameterised text (`db.query.text`). Dapper's text is a constant with `@`
placeholders, and spec 1.3 forbids building a value into it, so the text holds no values. EF's text, from unported
code, is also parameterised, and those spans are mostly dropped as parentless anyway (OQ-10).

## 8. Tests

**Unit** (`Grimoire.UnitTests/Functional/Telemetry/`), with no exporter and no network:

- `SpanResultTests`: one test per row of section 3.2: each case's outcome and status; a `ManyErrors` takes its worst
  case; cancellation during shutdown, and outside it (`Unavailable`); a root outcome for each `CommandOutcome`.
- `TelemetryTagsTests`: one test per row of section 3.3, built from real `DatabaseException`, `DiscordCallException`
  and `PluralKitCallException` values. For each, no tag value contains the error's message or Postgres's message.
- `GrimoireSamplerTests`: a parentless span with `grimoire.root` is kept; a parentless span without it is dropped
  (Client, Internal, any source); a child follows its parent, sampled or not.
- `UrlRedactionTests`: interaction callback, the webhook's original and follow-up messages, a webhook with a query
  string, a URL with no token, and PluralKit's and Discord's ordinary routes left unchanged.
- `LiveTelemetryIOTests`: the live capability with a test-only `ActivitySource` name, a `System.Diagnostics`
  `ActivityListener` and a `MeterListener`, all scoped to that name, so tests running in parallel don't see each
  other. **This is the test that guards the design's main risk**: a child span opened inside the body is a child of
  the parent across `IO.liftAsync`, `Task.Yield`, `RetryWhile`, `Timeout` and a `Fork`. `Activity.Current` is
  restored after the span. The error id equals the root's trace id. A failed body sets status error, records the
  exception and fails with the same `Error`. A refusal leaves status unset. The duration histogram is recorded with
  the outcome tag even when the span isn't sampled.
- **Pipelines against `FakeTelemetry`** (in the existing boundary and effect test classes):
  - `CommandBoundaryTests`: one root span for each outcome, with the outcome tag; the generic reply's id is the
    fake's id; a refusal's span has no id.
  - `EventBoundaryTests`: the root span, its outcome, and the alert carrying the id (section 5).
  - `WorkerTests`: one tick span, item spans under it, `grimoire.worker.items`, and no span for an item in backoff.
  - `DbEffectTests`, `DiscordEffectTests`, `PluralKitEffectTests`: one span per call. A read failing twice and then
    succeeding has two `retry` events and two retries counted. A write has none. PluralKit's outcome is the
    `ProxyLookup` case. Nothing is recorded when PluralKit isn't asked (it's off, or the message is too old).
  - `BotRefusalsTests`: one `guild-issue` event and one count per distinct issue.

## 10. Decisions (owner, 2026-11-16)

The owner took the suggested answer to each question.

| # | Question | Decision |
|---|---|---|
| OQ-1 | **Spans in the effect modules or in the live capabilities?** In the modules (`Db<RT>` …), there's one span per logical call with its retries as events, and the unit tests can check it. The cost is that `Db<RT>`, `Discord<RT>` and `PluralKit<RT>` need `Has<Eff<RT>, ITelemetryIO>`, so every generic feature function lists it too. In the live capabilities, constraints don't change, but each attempt is its own span, retries can't be counted, and only integration tests see spans. | **In the modules.** Telemetry is an effect, so the constraint says so. Little generic code uses the modules today (`DeletedMessageLookup<RT>`), so this is the cheapest moment. |
| OQ-2 | **Tail sampling.** Storage is plentiful, but the Mute and Lock workers tick every 5 s, which is about 35,000 mostly empty traces a day between them, and the upload comes out of the cloud host. | **Keep every trace except successful worker ticks that attempted no item.** Revisit with a percentage for successful events if the volume is high once Phase 3 ports `MessageCreated`. |
| OQ-3 | **Telemetry lost in a long home outage.** Without a sidecar there's no disk queue that outlasts an outage: the bot's queues hold a few minutes, then traces and logs are dropped. The plan's "holds telemetry through a home outage" no longer holds. Options: (a) accept it; the console logs in App Platform keep every line with its trace id, and metrics recover their totals; (b) turn on the exporter's disk retry, which survives an outage but not a deploy; (c) add a collector as a second App Platform component, which survives a bot redeploy but costs a container and still has no persistent disk. | **(a).** The home outages that matter are short, metrics lose nothing, and App Platform's logs cover the gap for an investigation. Revisit with (c) if outages turn out to be long or frequent. |
| OQ-4 | **Logs over OTLP too?** Loki then holds the logs next to the traces, linked by trace id. The console stays. | **Yes.** |
| OQ-5 | **The "finished" log line's `{CommandOptions}`** holds the arguments: warn reasons, custom command text. Over OTLP, they'd be stored at home with long retention. They're moderator input, not members' messages, so defect 9 doesn't cover them. | **Keep them.** They're how a moderator's report is reproduced. Revisit if retention goes past a year. |
| OQ-6 | **Unported code.** `GenericBackgroundService` ticks could get root spans now (a few lines; that class goes in Phase 5), so the old workers' EF and Discord calls show up as traces before Phase 3. Unported commands get the duration metric from `CommandHandler` but no trace. Unported event handlers get nothing until they're ported. | **Yes to the old worker ticks and the command metric.** No shims for unported event handlers. |
| OQ-7 | **The error id's length.** The full trace id is 32 hex characters. A shorter one is easier to read out, but Tempo can't look it up. | **Full**, in a code span, so it can be copied. |
| OQ-8 | **Retention at home.** | **Traces 90 days, logs 90 days, metrics 2 years.** The owner's storage decides. |
| OQ-9 | **A "View trace" link in alerts** (`telemetryTraceUrl`). | **Yes, optional.** With no URL set, the alerts show only the id. |
| OQ-10 | **Npgsql's spans carry the parameterised SQL text.** It has no values (section 6), and it's how a statement inside a transaction is identified. | **Keep it.** |
