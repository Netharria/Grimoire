## 1. Scope

**In scope**

- **Pardons (Q8, Q8b, Q11).** `Pardons` goes back to `main`'s key, `SinId`, so a sin has at most one pardon: who
  pardoned it and when (`SetAt`, renamed from `main`'s `PardonDate`). The reason moves to a new
  `PardonReasonHistory` (`SinId`, `SetAt`, `Reason`, `ModeratorId`), as `SinReasonHistory` does for sins. A second
  `/Pardon` on a pardoned sin adds a reason row and leaves the pardon's moderator and date alone. `Pardons."GuildId"`
  and `Pardons."Reason"` go. `ModelRedesign`'s phase 2, which made pardons a history keyed by `(SinId, SetAt)`, is
  removed.
- **`MessageHistory."GuildId"` goes (Q11, D-19, LOG-10).** `Reactions."GuildId"` stays (Q11).
- **The obsolete types leave the EF model (Q10, D-20).** The 18 types in `Grimoire.Domain/Obsolete/` and `IModule`,
  their 18 configurations, and the 18 `[Obsolete]` `DbSet`s go. The tables stay in the database, untouched, until
  P-7's later release drops them. The new migration's `Up` doesn't drop them: only the snapshot forgets them.
- **`NicknameHistory` becomes `ServerDisplayNameHistory` (TD-9).** The table, its key, the entity, the `DbSet` and the
  query helpers are renamed, and the column `Nickname` becomes `DisplayName` (OQ-3). What the history records (the
  display name rather than the nickname) and the log wording change in 3.11, which owns that behaviour.
- **Q6 index pairs (Grimoire half).** `ModelRedesign` stops creating `IX_SinReasonHistory_SinId_SetAt`,
  `IX_Pardons_SinId_SetAt`, `IX_CustomCommandUsages_GuildId_Name_UserId` and `IX_XpHistory_GuildId_Xp`.
  `SyncIndexesWithModel` stops creating `IX_Sin_Id_GuildId`. The Grimoire `DropRedundantIndexes` is deleted.
- **`bigint` ids in `public` (P-9, Q7).** Every id column of a live table becomes `bigint`. The two tables created
  after `main` (`SinReasonHistory`, `CustomCommandUsages`) are created with `bigint`. The 15 tables from `main` are
  converted in the new migration, one `ALTER TABLE` each (section 6.2). The legacy tables stay `numeric(20,0)`. The
  EF converters become `long` by convention, `ModerationActorConverter` becomes `long?`, KI-31's explicit
  `numeric(20,0)` column types go, and 2.2's `UseBigintIds` helper is deleted.
- **String discriminators, rewritten once (Q9).** `XpHistory."Type"` (integer to `Earned`/`Awarded`/…) and
  `MessageHistory`'s `Action` (integer to the `Discriminator` strings) are converted in the same `ALTER TABLE` as their
  ids. `ModelRedesign` keeps its guards and clean-ups, which run on the integers, but no longer converts either
  column. `MessageHistory` no longer gets a full-table `UPDATE`.
- **The leaderboard view (Q12, Q12b, defect 23, TD-9).** Created once, at the end of the chain, after the `bigint`
  rewrite: ranks break ties by `UserId`, members with a total of 0 or less are left out, and each row carries the
  member's latest server display name and username. The `LeaderboardView` migration, which created it before
  `ModelRedesign`, is deleted.
- **Keeping the bot working (ground rule 2).** `/Pardon`, `/SinLog` and `/Publish Unban` move to the new pardon shape
  (section 2.3). The five writers of `MessageHistoryEntry.GuildId` and `PardonSin` stop setting the dropped columns.
  The rename is mechanical. Nothing else a user sees changes, apart from Q12b and the tie-break on `/Leaderboard`.

**Decisions this implements:** Q6 (Grimoire pairs), Q7/P-9 (`public` half), Q8, Q8b (in today's readers), Q9 (one
rewrite per table), Q10/D-20, Q11/D-19/LOG-10, Q12 (the view stays), Q12b, TD-9 (the rename and the view's names),
defect 7 (mixed pardon rows, fixed by construction) and defect 23 (the tie-break). 2.1's two requests: the folded
`XpHistory` rewrite and the dropped pair.

**Out of scope**

- **What `ServerDisplayNameHistory` records** (the display name, with the global name and username as fallbacks),
  TD-7's backfill and the "display name changed" wording. That is 3.11. Until then the history records nicknames, as
  today, under the new name.
- **The leaderboard's rendering** of the names (TD-9's "DisplayName (username)"), TD-10, LVL-3/7 and Q12's folded count
  query. That is 3.15. In 2.3 the view has the columns and `/Leaderboard` still prints mentions.
- **Sins' commands as a whole** (SIN-1..6, SIN-2's single projection, the Q8b wording in a re-pardon reply). That is
  3.6. 2.3 changes only the three readers and the writer the new tables force.
- **P-16's XP compaction**, which 2.1 found necessary. That is 3.14.
- **Dropping the legacy tables** (P-7), in a later release.
- **The deploy rehearsal** on a production copy and the runbook's `ANALYZE` and `VACUUM`. That is 2.4.

Each kept migration's `Designer.cs` is regenerated to match the model after its own step, and the snapshot is
regenerated, as in 2.2. Down methods are kept in step with each Up. The production rollback is still the backup
(2.4), not `Down`.

**Why the new work goes at the end, not into `ModelRedesign`** (OQ-2). TD-9 placed the rename in `ModelRedesign`.
But three later migrations name the old shapes: `DropOrphanedLegacyForeignKeys` drops `FK_NicknameHistory_*`,
`FK_Pardons_*` and `FK_MessageHistory_*`, and `SyncIndexesWithModel` drops `IX_Pardons_GuildId`,
`IX_NicknameHistory_GuildId` and `IX_MessageHistory_GuildId_DeletedByModeratorId`. Moving the drops and the rename
earlier would mean editing both of those too. More importantly, P-9 can't run before `DropOrphanedLegacyForeignKeys`:
Postgres refuses a foreign key from a `bigint` column to a `numeric` one, and until step 7 the live tables still have
keys into the legacy tables. So the `bigint` rewrite must come after step 7. The discriminator conversions move with
it so that each table is rewritten once, and the rest moves with them so the old shapes stay valid for every
migration that names them.

### 2.2 The new migration, in order (all in one transaction, as EF runs each migration)

1. **Guards** (effect: database). Stop with a clear message if `XpHistory."Type"` holds a value outside 0–3, or
   `MessageHistory."Action"` a value outside 0–2. Today's conversion maps an unknown value to `Earned` or `Deleted`
   without a word. 2.1 found only 0–4 and 0–2, and `ModelRedesign` deletes `Type 4` first, so both guards are 0
   today.
2. **Drop the six foreign keys** over columns that change type: `MessageHistory`, `Attachments`, `Reactions` and the
   two `ProxiedMessages` keys to `Messages."Id"`, and `CustomCommandsRole` to `CustomCommands`.
3. **Pardons:** create `PardonReasonHistory`, copy each pardon's reason into it (OQ-1: not an empty one), rename
   `PardonDate` to `SetAt`, then drop `Reason` and `GuildId` and convert `ModeratorId` in one `ALTER TABLE`.
4. **One `ALTER TABLE` per table**, largest first (`XpHistory`, `Messages`, `MessageHistory`, …): every id column to
   `bigint`, and on `XpHistory` and `MessageHistory` the discriminator too. `MessageHistory` drops `GuildId` in the
   same statement, so the rewrite doesn't copy it. Then `MessageHistory."Action"` is renamed `Discriminator`.
5. **The rename:** `NicknameHistory` to `ServerDisplayNameHistory`, its key to `PK_ServerDisplayNameHistory`, and
   `Nickname` to `DisplayName` (metadata only, after its own rewrite in step 4).
6. **`IX_XpHistory_UserId_GuildId_Xp`**, built once, on the rewritten table. Today it is built in `ModelRedesign`
   and then rebuilt by the rewrite.
7. **Re-add the six foreign keys** (each checks its rows: 0.03 s together on 2.1's copy).
8. **The view and its two unique indexes** (section 6.3).

### 2.3 Pardons at runtime (interim EF, until 3.6)

**`/Pardon sin_id reason`:**

1. Validate the reason (pure, unchanged: `ModerationReason.Create`).
2. Find the sin in the guild (effect: database, unchanged). None: "Could not find a sin with that ID.", as today.
3. In one transaction (effect: database), through raw SQL, so the race is in the statement:
   insert the `Pardon` (`ON CONFLICT ("SinId") DO NOTHING`), then insert the reason row.
4. The reply and the log, unchanged.

The first `/Pardon` of a sin creates the pardon and its first reason. A second one keeps the first moderator and
date and adds a reason (Q8). Two moderators pardoning at once both land: one pardon, two reasons.

**`/SinLog`** reads the pardon's own moderator and date: "Pardoned by {first moderator} on {first date}" (Q8b). Today it
mixes the newest pardon's moderator with the oldest pardon's date (defect 7). **`/Publish Unban`** reads the pardon's
date and the latest reason (Q8b). Each needs one join instead of two or three correlated subqueries.

### 2.4 The leaderboard (unchanged path)

The refresh worker still runs `REFRESH MATERIALIZED VIEW CONCURRENTLY leaderboard_view` every 15 minutes, and
`GetLeaderboard` still reads it. What changes is what the view holds: no member at 0 XP or less (Q12b), so the count
and the pages shrink (from 25,043 rows to about 10,400 on production, 2.1), and ties ranked by `UserId`, so a page no
longer reorders between refreshes. The name columns are read from 3.15 on.

## 3. Types

### 3.1 Pardons

```csharp
/// <summary>A sin's pardon: who first pardoned it, and when. Neither changes (Q8). One per sin.</summary>
public sealed record Pardon
{
    public required SinId SinId { get; init; }
    public required ModeratorId ModeratorId { get; init; }
    public required DateTimeOffset SetAt { get; init; }
    public Sin? Sin { get; init; }
    public ICollection<PardonReasonHistory> ReasonHistory { get; init; } = [];
}

/// <summary>One wording of a pardon's reason. A re-pardon adds one; the latest is the reason shown.</summary>
public sealed record PardonReasonHistory
{
    public required SinId SinId { get; init; }
    public required ModerationReason Reason { get; init; }
    public required ModeratorId ModeratorId { get; init; }
    public required DateTimeOffset SetAt { get; init; }   // truncated to the microsecond: part of the key
    public Pardon? Pardon { get; init; }
}
```

- `Sin.Pardons` (a collection) becomes `Sin.Pardon` (`Pardon?`). `Pardon.GuildId` goes: the sin has the guild.
- The reason's moderator is required, unlike `SinReasonHistory.Actor`, because only `/Pardon` writes one, and it
  always has a moderator. The legacy copy takes it from the pardon, which `RequirePardonModerator`'s guard already
  requires.
- A reason row's key holds a time, so its `SetAt` is truncated to the microsecond, as 2.2's state rows are (the
  meaningful-keys rule). Two re-pardons of one sin in the same microsecond are refused by the key and written as
  nothing (`ON CONFLICT DO NOTHING`).
- `PardonReasonHistory`'s foreign key points at `Pardons."SinId"`, not at `Sins`, so a reason can't exist without its
  pardon. Deleting a sin cascades to its pardon and from there to its reasons.

## 4. Edge cases

| Case | What happens | Error case |
|---|---|---|
| A legacy pardon with an empty reason (24 of 38 on production) | A `Pardon` row and no reason row (OQ-1). `/SinLog` shows the pardon as today. `/Publish Unban` publishes an empty reason, as it does today | — |
| A legacy pardon with a reason | A `Pardon` row, plus one reason row at the pardon's date, by the pardon's moderator | — |
| A second `/Pardon` on a pardoned sin | The pardon's moderator and date stay. A new reason row. `/SinLog` still names the first moderator and date. `/Publish Unban` uses the new reason | — |
| Two moderators pardon the same sin at once | One pardon (the first insert wins). Two reason rows | — |
| `/Pardon` on a sin in another guild, or one that doesn't exist | "Could not find a sin with that ID.", as today | `NotFound` |
| `XpHistory."Type"` outside 0–3, or `MessageHistory."Action"` outside 0–2, at deploy | The migration stops with a message naming the count. Nothing is changed (the migration's transaction) | — |
| A snowflake at or above 2^63 at deploy | The `::bigint` cast fails ("bigint out of range") and the migration rolls back. Discord ids reach that around 2084 | — |
| A member whose XP total is 0 or less | Not in the view, so not on `/Leaderboard`. `/Leaderboard user:` for them replies "User not found on the leaderboard", as for a member with no XP | `NotFound` |
| Two members with the same total | The one with the lower `UserId` ranks first, on every refresh | — |
| A member with no display name or username row | The view's name is `null`; 3.15 falls back to a mention | — |
| A member whose latest display name row is `null` (nickname cleared) | `DisplayName` is `null`; 3.15 falls back to the username | — |
| A legacy table, after 2.3 | Still in the database with its rows and `numeric` columns. Settings `Initial` still reads it by raw SQL. EF no longer knows it | — |
| An empty database | Every step runs. The guards find nothing, the copies copy nothing, and the view is created empty | — |

## 6. SQL

### 6.1 Tables

```sql
CREATE TABLE "PardonReasonHistory" (
    "SinId"       bigint NOT NULL,
    "SetAt"       timestamptz NOT NULL,
    "Reason"      varchar(1000) NOT NULL,
    "ModeratorId" bigint NOT NULL,
    CONSTRAINT "PK_PardonReasonHistory" PRIMARY KEY ("SinId", "SetAt"),
    CONSTRAINT "FK_PardonReasonHistory_Pardons_SinId" FOREIGN KEY ("SinId")
        REFERENCES "Pardons" ("SinId") ON DELETE CASCADE
);
```

`Pardons` after 2.3: `SinId bigint` (primary key, `main`'s `PK_Pardons`, foreign key to `Sins` with cascade),
`ModeratorId bigint NOT NULL`, `SetAt timestamptz NOT NULL` (no default: the code always sets it). The primary keys
serve every read: a sin's pardon by `SinId`, and its latest reason by a backward scan of `(SinId, SetAt)`. That is
why `IX_Pardons_SinId_SetAt` and `IX_SinReasonHistory_SinId_SetAt` were redundant (Q6).

### 6.2 The `bigint` rewrite (in the new migration; hand-written, one statement per table)

EF would emit one `ALTER TABLE` per column, and Postgres rewrites a table once per statement. So the migration's
`Up` is raw SQL, with one statement per table. The generated operations serve as the checklist: a unit test compares
the columns the raw SQL converts with the ones EF's diff lists (section 8).

```sql
ALTER TABLE "XpHistory"
    ALTER COLUMN "GuildId"   TYPE bigint USING "GuildId"::bigint,
    ALTER COLUMN "UserId"    TYPE bigint USING "UserId"::bigint,
    ALTER COLUMN "AwarderId" TYPE bigint USING "AwarderId"::bigint,
    ALTER COLUMN "Type"      TYPE varchar(21) USING CASE "Type"
        WHEN 0 THEN 'Earned' WHEN 1 THEN 'Awarded' WHEN 2 THEN 'Reclaimed' WHEN 3 THEN 'Migrated' END;

ALTER TABLE "MessageHistory"
    DROP COLUMN "GuildId",
    ALTER COLUMN "Action" DROP DEFAULT,
    ALTER COLUMN "MessageId"   TYPE bigint USING "MessageId"::bigint,
    ALTER COLUMN "ModeratorId" TYPE bigint USING "ModeratorId"::bigint,
    ALTER COLUMN "Action"      TYPE varchar(34) USING CASE
        WHEN "Action" = 0 THEN 'Created'
        WHEN "Action" = 1 THEN 'Edited'
        WHEN "Action" = 2 AND "ModeratorId" IS NOT NULL THEN 'DeletedByModerator'
        WHEN "Action" = 2 THEN 'Deleted' END;
ALTER TABLE "MessageHistory" RENAME COLUMN "Action" TO "Discriminator";
```

The `CASE`s have no `ELSE` because step 1's guards have already refused anything else. The other 13 tables follow
the same pattern with their id columns only:

**Budget** (from 2.1's measurements; checked by section 8's copy run). The whole migration is now one rewrite of each
table, where today's chain has two of `XpHistory` and an `UPDATE` of `MessageHistory`. On 2.1's copy, C-2's `bigint`

Scaled as 2.1 does (× 1.56 × 15.9), the longest statement is **about 2 minutes** on production, under the 15-minute
line. The whole first deploy drops from about 6 minutes to **about 3**: one `XpHistory` rewrite and one build of
`IX_XpHistory_UserId_GuildId_Xp` are saved, and the pair index is never built.

### 6.3 The view (in the new migration, after the rewrite)

```sql
CREATE MATERIALIZED VIEW leaderboard_view AS
SELECT x."GuildId", x."UserId", x."TotalXp",
       ROW_NUMBER() OVER (PARTITION BY x."GuildId" ORDER BY x."TotalXp" DESC, x."UserId") AS "Rank",
       d."DisplayName", u."Username"
FROM (SELECT "GuildId", "UserId", sum("Xp") AS "TotalXp"
      FROM "XpHistory" GROUP BY "GuildId", "UserId" HAVING sum("Xp") > 0) x
LEFT JOIN LATERAL (SELECT h."DisplayName" FROM "ServerDisplayNameHistory" h
                   WHERE h."UserId" = x."UserId" AND h."GuildId" = x."GuildId"
                   ORDER BY h."Timestamp" DESC LIMIT 1) d ON true
LEFT JOIN LATERAL (SELECT h."Username" FROM "UsernameHistory" h
                   WHERE h."UserId" = x."UserId"
                   ORDER BY h."Timestamp" DESC LIMIT 1) u ON true;

CREATE UNIQUE INDEX idx_leaderboard_view_guild_user ON leaderboard_view ("GuildId", "UserId");
CREATE UNIQUE INDEX idx_leaderboard_view_guild_rank ON leaderboard_view ("GuildId", "Rank");
```

The first unique index is the one `REFRESH … CONCURRENTLY` needs, and it serves the count and the member lookup. The
second serves the page read (`Rank` between two values) and makes defect 23's fix a constraint: a refresh that
produced two equal ranks would fail (OQ-5). Each lateral join reads one row through its table's primary key
(`(UserId, GuildId, Timestamp)` and `(UserId, Timestamp)`), backwards. 2.1 measured this shape at 894 ms under
`EXPLAIN ANALYZE` on the copy, and estimated the refresh at about 3 s on production.

### 6.4 Pardon statements (interim, raw SQL through EF)

```sql
-- /Pardon: in one transaction. The first insert does nothing if the sin is already pardoned.
INSERT INTO "Pardons" ("SinId", "ModeratorId", "SetAt") VALUES (@SinId, @ModeratorId, @At)
ON CONFLICT ("SinId") DO NOTHING;
INSERT INTO "PardonReasonHistory" ("SinId", "SetAt", "Reason", "ModeratorId")
VALUES (@SinId, @At, @Reason, @ModeratorId)
ON CONFLICT DO NOTHING;

-- The legacy copy (step 3), before "Reason" is dropped.
INSERT INTO "PardonReasonHistory" ("SinId", "SetAt", "Reason", "ModeratorId")
SELECT "SinId", "PardonDate", "Reason", "ModeratorId"::bigint
FROM "Pardons"
WHERE trim("Reason") <> '';
```

The copy skips empty reasons the way `ModelRedesign`'s `SinReasonHistory` copy does. `/SinLog` and `/Publish Unban`
read through EF: `Sin.Pardon` for the moderator and date, and the latest `PardonReasonHistory` row for the reason.

**Tests for the SQL** (integration, `Database/`): the pardon statements, including a re-pardon (one pardon, two
reasons, the first moderator and date kept) and two concurrent first pardons (one pardon, two reasons). The view: the
tie-break, the 0-XP and negative exclusion, the latest name of each kind, `null` names, and a refresh after new XP.
The schema: no `numeric(20,0)` column outside the legacy tables, every legacy table still present, and no foreign key
between a live table and a legacy one.

## 7. Telemetry

None new. The pardon writes and the readers still go through EF until 3.6, and Npgsql's instrumentation (1.6) already
puts each statement in a span under the boundary's root span. The leaderboard refresh is already a worker tick with
its own span. No pardon reason or name goes into a span: the statements bind them as parameters, and parameter values
aren't recorded (defect 9).

## 10. Decisions (owner, 2026-11-19)

| # | Question | Decision (the suggested answer) |
|---|---|---|
| OQ-1 | **A pardon with no reason** (24 of 38 on production): no reason row, or a row with an empty reason? | **No row.** `ModerationReason` can't be empty, so a row with `''` would break the type's rule on read. `ModelRedesign` already skips empty sin reasons the same way. The pardon itself (who and when) is kept, so nothing is un-pardoned. |
| OQ-2 | **Where the work goes:** one new migration at the end of the chain, or edits spread through `ModelRedesign` and the migrations after it, as TD-9 assumed? | **One new migration at the end** for the pardon rework, the column drops, the rename, the `bigint` rewrite with the discriminators, and the view. Edit the existing migrations only to remove things (phase 2, the pairs, the discriminator `UPDATE`, the `LeaderboardView` and `DropRedundantIndexes` migrations). P-9 can't run before `DropOrphanedLegacyForeignKeys` (section 2.1), and putting the rest earlier would mean editing three migrations that name the old shapes. |
| OQ-3 | **The renamed column:** rename `Nickname` to `DisplayName` now, and keep it nullable? | **Yes to both.** The rename belongs with the table's, before the deploy. `null` keeps its legacy meaning (a cleared nickname); from 3.11 on a row always holds a name, because the display name falls back to the global name and then the username. 3.11 can add `NOT NULL` only if it backfills the legacy `null`s, which it may not be able to do. |
| OQ-4 | **Squash the post-`main` migrations?** 2.0 left this until after 2.3 (2.0's OQ-2). EF 10 runs each migration in its own transaction, so a failure partway leaves the earlier ones committed. | **No squash.** 2.3 has already removed the create-then-drop steps that made the chain wasteful, and the deploy runs about 3 minutes. A failure partway is recovered from the backup taken just before (2.4's runbook), which a squash wouldn't make unnecessary. The steps stay reviewable, and dev databases aren't rebuilt a second time. |
| OQ-5 | **A unique `(GuildId, Rank)` index on the view?** | **Yes.** It serves the page read, costs little on about 10,400 rows, and turns the tie-break into a guarantee: if a future edit of the view drops it, the refresh fails instead of letting ranks swap quietly. |

## 11. Results and differences from the spec

**Checks:**

- `has-pending-model-changes` reports nothing (the snapshot was generated with `GrimoireSchema`), and
  `MigrationModelTests` passes. The chain's order is unchanged: Settings `Initial` still runs straight after
  `ModelRedesign`.
- `GrimoireSchemaCopyTests` (new) runs the deploy path: it migrates a scratch database to `main`'s last migration,
  seeds `main`-shaped rows (with the legacy parents their keys need), runs the rest of the chain, and checks the
  rows. XP totals per member are unchanged and `Type 4` is gone. Each `MessageHistory` action gets its discriminator,
  and `GuildId` is gone. Pardons keep their moderator and date, and only the non-empty reason becomes history (OQ-1).
  The rename carries its rows. The view leaves out the member at 0, breaks the tie by `UserId`, and carries the
  latest names. Ids above 2^53 survive exactly. No live column is `numeric`, the legacy tables are still there, and
  no key joins the two. An unknown `Type` or `Action` stops the deploy with its message, before anything changes.
- **Pardons at runtime:** a re-pardon keeps the first moderator and date and adds a reason; `/SinLog` names the first
  moderator after a re-pardon by someone else (defect 7's case); `/Publish Unban` uses the latest reason with the
  first date, and publishes an empty reason for a pardon with none; two first pardons at once leave one pardon and
  two reasons.
- `GrimoireSchemaMigrationTests` (new, unit): the migration's hand-written column list is exactly the snowflake
  columns of `main`'s public tables, read from the model, and no column in either schema is `numeric`.
- **Mutation testing** of the new pure code (`PardonReasonHistory.Create`, the id converters and conventions,
  `ModerationActorConverter`): 33% at first, 90% after the fix. The survivors all came from EF's model cache: a built
  model is cached per context type for the whole test process, so a mutant in a convention never got a fresh model.
  The converter tests now build their models without service provider caching. The three left are equivalent: they
  remove a conversion for a type the model in question doesn't use (`MessageId` and `AttachmentId` in Settings, a
  plain `ulong` in the main model).
- **Not run: the copy run on a production restore** (section 8), nor 2.2's equivalence check, which needs the same
  restore. Both need the owner to restore a backup.

**Where the code differs from the text:**

- **The foreign keys are captured, not listed.** Step 2 saves the definition of every foreign key on or into a
  converted table, as the database has it, and step 7 re-adds them. That covers keys the spec's list of six would
  have missed, and a key that still pointed at a legacy table would fail loudly at step 7.
- **The column list is data in the migration** (`GrimoireSchema.BigintColumns`), from which the statements are built,
  so the unit test above can check it against the model.
- **Intermediate `Designer.cs` files are not regenerated** for the edited Grimoire migrations, as in 2.2. The new
  migration's Designer and the snapshot are generated.
- **One decided behaviour changed a pinned test.** LVL-71 (`Leaderboard_KeepsAMemberReclaimedToZero`) pinned a member
  at 0 XP on the board; Q12b leaves them off. The test and its manual row now say so.
- **`/Pardon` is one statement**, a CTE that inserts the pardon if missing and then the reason, instead of two
  statements in a transaction. The reason's foreign key is checked at the end of the statement, so it sees the pardon
  inserted alongside it.
