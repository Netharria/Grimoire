# Spec 2.2: Settings schema

Status: **implemented 2026-11-19, not committed.** Approved 2026-11-19: the owner took the suggested answer to all
four open questions (section 10), widened OQ-2 to every legacy mute, and chose meaningful keys over identity columns
(section 3.3). Tests: unit 846 (1 skipped), integration 1477 (39 skipped, unchanged), all passing. Mutation score of the new pure code: 100%. Build warnings: 133,
the same codes per project as before (134). The equivalence check on a production restore is still to run (section
11). Section 11 lists the results and where the code differs from this text.

Implements the plan's section 2.2: the `Settings` schema takes its final shape before the first deploy. That covers
guild settings as versioned JSON documents (TD-6), mutes and locks as one state row each (TD-1, TD-2), `bigint` ids
(P-9), and no create-then-drop index pairs (Q6). Settings `Initial`'s copy of the legacy data is rewritten to fill
the new shapes. Everything edits the undeployed Settings migrations in place (Q6, C9), inside 2.0's one chain (C12).

**One change to TD-6, from the owner (2026-11-18).** TD-6 put each module's on/off flag inside its own document
(`LevelingConfig { Enabled, … }`). This spec moves all six flags into one document of their own, `Modules`, and each
module's document holds only that module's settings. A check of "is this module on?", which every gated command and
nearly every event makes, then reads one small document. A disabled module's settings are never loaded or cached,
because callers check the module first and stop there. Section 3.1 explains the effect on 3.1's cache. The owner
recorded it as conflict C13 (OQ-1).

## 1. Scope

**In scope**

- **Guild settings as documents (TD-6, amended).** `Settings."GuildSettings"` changes from one row per key
  (`Type`, `State`, `Value` string) to one row per *document version*: `(GuildId, Document, Version)` with a `jsonb`
  value and who/when. There are six documents: `Modules`, `General`, `Leveling`, `MessageLog`, `Moderation` and
  `UserLog` (section 3.1). `GuildSettingType`, `GuildSettingDefault`, `GuildSettingDisabled` and
  `GuildSettingCustomValue` go.
- **Mutes, channel locks and thread locks as state rows (TD-1, TD-2).** Each item is one row with a `State` (`Pending`,
  `Active`, `Expired` or `Removed`) and the who/when (and why, for `Removed`) of each transition. `MuteRemoved`,
  `ChannelUnlocked`, `ThreadUnlocked`, the `EventType` discriminators and `ClosedAt` all go. Q31's partial index
  becomes `EndTime WHERE State IN ('Pending', 'Active')`.
- **`bigint` ids in `Settings` (P-9).** The tables are created post-`main`, so they are created with `bigint` from the
  start and nothing is rewritten at deploy. The `public` side stays on `numeric(20,0)` until 2.3.
- **Q6 index pairs.** `Initial` stops creating the seven indexes that duplicate a primary key, and Settings
  `DropRedundantIndexes` is deleted.
- **The legacy copy**, rewritten to build the documents and state rows from `main`'s tables. The mute copy now takes
  each mute's moderator and time from its sin, and the mute role from the guild's settings.
- **Every legacy mute, in force or overdue, is copied as `Active`** (OQ-2). On `main` a finished mute is deleted, so
  each row in `public."Mutes"` is one or the other. The 3 overdue ones on production (2.1) expire on the first poll.
- **Keeping the bot working (ground rule 2).** `SettingsModule` keeps its public API, so its 48 caller files don't
  change. Only its internals move to the new tables, still through EF Core (OQ-4). The mute and lock callers switch
  from `MuteAdded`/`ChannelLocked`/`ThreadLocked` to the new records (section 3.3); that change is mechanical.

**Decisions this implements:** TD-1, TD-2, TD-6 (amended by C13), P-9 (Settings half), Q6 (Settings pairs), Q31 (the
index), the plan's 2.2 item on the overdue mutes, and the guild-settings half of KI-103 (section 2.3).

**Out of scope**

- **The mute and lock processors** (TD-3, TD-4, MOD-6, KI-55's order). That is 3.4 and 3.5. They add the outbox's
  retry columns (attempts, next try, last failure) by editing `Initial` again, which stays possible until the deploy
  (C9). Until then nothing writes `Pending`: the commands still act first and record `Active`, as they do today.
- **3.1's settings service**: the Dapper port, the cache layout (SET-1, as amended by C13), the 1-hour expiry (Q19),
  fail-safe (SET-10) and KI-105.
- **The other Settings tables** (`Rewards`, `XpTrackedItems`, `MessageLogChannelOverrides`, `SpamFilterOverrides`,
  `DiagnosticsIgnoredItems`). They stay append-only, as Q5 decided. They change only to `bigint` and lose their
  redundant indexes.
- **Dropping the legacy `public` tables** (P-7), which comes in a later release.

## 2. Flow

### 2.1 The Settings chain, after 2.2

| Migration | Before | After |
|---|---|---|
| `20260524035623_Initial` | 8 tables, 15 indexes, the legacy copy into key/value rows and event rows | **Rewritten:** the final shapes (section 6), 8 indexes, the copy into documents and state rows |
| `20260919233857_AddDiagnosticsIgnoredItems` | one table | Kept, with `bigint` columns |
| `20260920001445_AddMuteRoleToMutes` | adds `MuteRoleId` | **Deleted:** `Initial` creates the column |
| `20261109022050_DropRedundantIndexes` (Settings) | drops 7 indexes | **Deleted:** `Initial` no longer creates them |
| `20261110232856_AddClosedAtToLocksAndMutes` | `ClosedAt`, its backfill, 3 partial indexes | **Deleted:** TD-1 replaces `ClosedAt` |

The ids that remain don't change, so 2.0's order holds: `Initial` still runs third, straight after `ModelRedesign`
(`StartupMigrationTests.SettingsInitial_RunsStraightAfterModelRedesign`). The `Designer.cs` file of each kept migration
is regenerated to match the model after its own step, and the snapshot is regenerated.

### 2.2 Reading a setting (interim, until 3.1)

1. A caller asks, for example, `IsModuleEnabled(Module.Leveling, guild)` (unchanged API).
2. `SettingsModule` reads the guild's `Modules` document from the cache (key `Settings_Modules_{guild}`). On a miss
   (effect: database) it reads the latest version, or nothing, and parses it (pure). A missing document or field means
   off.
3. It returns the module's flag (pure).

A module setting, such as `GetLevelingSettings(guild)`, reads the `Leveling` document the same way, under its own key.
Each document is one cache entry. A guild whose leveling is off never loads `Leveling`, because `GainUserXp` and the
leveling commands stop at step 3. `General` has no flag and is always on, as today.

### 2.3 Writing a setting (interim, until 3.1)

1. A command calls, for example, `SetLevelingSettings(guild, moderator, Amount, 10)` (unchanged API).
2. Validate the value (pure, unchanged: `XpGainAmount.Create`).
3. Read the latest version of the document, uncached (effect: database).
4. Apply the change to the parsed document (pure: `LevelingConfig → LevelingConfig`).
5. If the new document equals the current one, return `Write.Unchanged` and store nothing, as today.
6. Otherwise insert version `n + 1`, only if `n` is still the latest (effect: database, section 6.2). If another
   write got there first, the insert writes nothing. Repeat from step 3, up to 3 times; then fail as `Unavailable`.
7. Remove the document's cache key (effect), on both the `Saved` and the `Unchanged` path. Clearing it on `Unchanged`
   too fixes KI-103 for guild settings. The override tables keep KI-103's other half for 3.1.

### 2.4 Mutes and locks (interim, until 3.4 and 3.5)

Today's behaviour, stored the new way:

| Today | After 2.2 |
|---|---|
| `AddMute` closes the member's open `MuteAdded` and inserts a new one | Moves the member's in-force row to `Removed` (by the new mute's moderator, ended at the new mute's time), then inserts the new row as `Active`, in one transaction |
| `RemoveMute` inserts `MuteRemoved` and closes the `MuteAdded` | Moves the in-force row to `Removed`, with moderator and time |
| The expiry poll reads open `MuteAdded` rows past `EndTime`, removes the role, then calls `RemoveMute` | Reads `Active` rows past `EndTime` and, after removing the role, moves the row to `Expired` instead of `Removed` |
| `AddChannelLock` on a locked channel keeps the first lock's permissions | The same: the new row copies `PreviouslyAllowed`/`PreviouslyDenied` from the row it replaces |
| Thread locks | The same as channel locks, without permissions |

Each transition is an `UPDATE … WHERE "State" = <the state it moves from>`. If it updates no row, the item has
already moved on (a race with the expiry poll or another moderator), and the caller gets `NotFound`, as it does today
when no open row exists. The "only forward" rule (TD-1) therefore holds in the statement, and nothing catches a
constraint exception.

### 2.5 The legacy copy (in `Initial`)

All of it runs in `Initial`'s one transaction, against `main`'s tables, which `ModelRedesign` has left in place:

1. **Documents** (section 6.3): for each guild, one version-1 document per kind that has at least one non-default
   value. A value equal to today's default is left out, so it stays "default" and follows any future change of the
   default, as today's copy does.
2. **Mutes:** each `public."Mutes"` row becomes an `Active` row. Its `SetAt` and `SetBy` come from its sin (`SinOn`,
   `ModeratorId`), and its `MuteRoleId` from the guild's `GuildModerationSettings."MuteRole"`. Today's copy uses the
   sentinels `0001-01-01` and moderator 0, and no role.
3. **Channel locks:** each `public."Locks"` row becomes an `Active` row. The legacy table has no lock time, so the
   sentinel stays. Production has none (2.1).
4. Rewards, XP ignores and the two override tables are copied as today, with `::bigint` casts.

## 3. Types

### 3.1 Documents

One record per document, in `Grimoire.Settings/Domain/Documents/`. Every field is optional: a missing or `null` field
means the default, and System.Text.Json ignores unknown fields. A new setting is a new field, with no migration
(TD-6).

```csharp
public enum SettingsDocument { Modules, General, Leveling, MessageLog, Moderation, UserLog }

/// <summary>Which modules are on (C13). A missing flag is off. General has no flag: it is always on.</summary>
public sealed record ModuleStates(
    bool Leveling = false, bool UserLog = false, bool Moderation = false,
    bool MessageLog = false, bool Commands = false, bool AntiSpam = false)
{
    public bool IsEnabled(Module module);                 // General => true
    public ModuleStates With(Module module, bool enabled); // General => Invalid, as today
}

public sealed record GeneralConfig(ChannelId? ModerationLogChannel = null, ChannelId? UserCommandChannel = null);

public sealed record LevelingConfig(
    XpGainAmount? XpGainAmount = null, LevelScalingBase? LevelScalingBase = null,
    LevelScalingModifier? LevelScalingModifier = null, XpTimeoutPeriod? XpTimeout = null,
    ChannelId? LogChannel = null)
{
    public LevelingSettingEntry Resolve();   // defaults filled in: what GetLevelingSettings returns today
}

public sealed record MessageLogConfig(
    ChannelId? DeleteLogChannel = null, ChannelId? BulkDeleteLogChannel = null, ChannelId? EditLogChannel = null);

public sealed record ModerationConfig(
    ChannelId? PublicModerationLogChannel = null, TimeSpan? AutoPardonAfter = null, RoleId? MuteRole = null);

public sealed record UserLogConfig(
    ChannelId? JoinLogChannel = null, ChannelId? LeaveLogChannel = null, ChannelId? UsernameLogChannel = null,
    ChannelId? NicknameLogChannel = null, ChannelId? AvatarLogChannel = null);
```

`GuildModuleState` is replaced by `ModuleStates`. Its one public user, `/modules` (`ModuleCommands.View`), reads the
same six flags. `GuildLogType` gets two pure functions in place of `ToGuildSettingType`: one gets the log's channel
from its document, and one sets it. They are total over the eleven log types, and a unit test covers each one.

**JSON encoding** (one `JsonSerializerOptions`, `SettingsJson.Options`, shared by EF now and by 1.3's
`DapperTypeHandlers.RegisterDocument<T>` in 3.1):

| Value | In JSON | Why |
|---|---|---|
| Snowflake ids | a string, `"1234567890123456789"` | Discord's own API does the same: a JavaScript reader, such as pgAdmin's viewer, rounds numbers above 2^53 (OQ-3) |
| Durations | whole seconds, as a number, in a field named `…Seconds` (`XpTimeoutSeconds`, `AutoPardonAfterSeconds`) | Exact, and simple to write in the copy's SQL. Today's `"25:00:00"` workaround in `XpTimeoutPeriod.FromDatabase` goes |
| Level values | numbers | |
| Defaults and off | the field is left out (`WhenWritingNull`) | A missing field is the default, so a document holds only what a guild chose |

Value types are read through their `FromDatabase` factories, so a stored value outside today's limits keeps working
(S-1). Writes go through `Create`, as today.

**The effect on 3.1's cache.** SET-1 proposed one `GuildConfig` entry per guild, filled by one query. With C13, the
natural layout is one entry per document: `Modules` for every guild that uses the bot, plus one per document a running
module reads. This is a little more lookups than SET-1 for a guild with every module on (two entries for a module's
log instead of one). It gives these gains:

- The gate that runs on every gated command and every event is one small entry.
- A disabled module's document is never queried or cached.
- Turning a module on or off writes `Modules` only, so it doesn't add a version to the module's settings history,
  and it clears one key.
- `/modules` is one read, in place of `GetAllModuleState`'s six.

The documents are a few hundred bytes each, so memory is not where most of the gain is. The gain is in cold-cache
queries and in keeping each write's invalidation to one key. 3.1's spec makes the final call on the layout.

### 3.2 The stored document row (interim EF entity, internal)

```csharp
internal sealed record GuildSettingRow(
    GuildId GuildId, SettingsDocument Document, int Version, string Value, ModeratorId SetBy, DateTimeOffset SetAt);
```

`Value` is mapped as `jsonb` and parsed by `SettingsJson`. A document that doesn't parse is a defect (1.3's rule for
`jsonb`), never a default: reading a corrupt document as defaults would quietly turn modules off.

### 3.3 Mutes and locks

One state union, shared by the three tables, so "invalid state unrepresentable" holds in C# as the check constraints
make it hold in the database:

```csharp
public abstract record ItemState
{
    public sealed record Pending : ItemState;
    public sealed record Active(DateTimeOffset At) : ItemState;
    public sealed record Expired(DateTimeOffset At) : ItemState;
    public sealed record Removed(DateTimeOffset At, ModeratorId By, ModerationReason? Reason) : ItemState;
}

public sealed record Mute(
    GuildId GuildId, UserId UserId, SinId SinId, RoleId? MuteRoleId,
    ModeratorId SetBy, DateTimeOffset SetAt, DateTimeOffset EndTime, ItemState State)
{
    public bool InForce { get; }                                             // Pending or Active
    public Fin<Mute> Activate(DateTimeOffset at);                            // Pending → Active
    public Fin<Mute> Expire(DateTimeOffset at);                              // Pending or Active → Expired
    public Fin<Mute> Remove(ModeratorId by, ModerationReason? reason, DateTimeOffset at); // Pending or Active → Removed
}

public sealed record ChannelLock(
    GuildId GuildId, ChannelId ChannelId, ModerationReason? Reason, ModeratorId SetBy, DateTimeOffset SetAt,
    DateTimeOffset EndTime, PreviouslyAllowedPermissions PreviouslyAllowed,
    PreviouslyDeniedPermissions PreviouslyDenied, ItemState State);    // the same three transitions

public sealed record ThreadLock(
    GuildId GuildId, ChannelId ChannelId, ModerationReason? Reason, ModeratorId SetBy, DateTimeOffset SetAt,
    DateTimeOffset EndTime, ItemState State);                          // the same three transitions
```

- A transition from a state it doesn't allow (an `Expired` mute removed, for example) is `Invalid`. The SQL's
  `WHERE "State" = …` makes the same check against the stored row (section 2.4).
- **Keys mean something** (owner, 2026-11-19, replacing this spec's first draft of identity columns). A mute's key is
  its `SinId`: every mute comes from exactly one sin, and `main`'s legacy `Mutes` was keyed the same way. A lock's key
  is `(GuildId, ChannelId, SetAt)`. Because a set time is part of a key, `Create` truncates it to the microsecond
  (`ItemState.Stored`), so the value the code holds equals the stored one. .NET keeps 100 ns ticks, which Postgres
  would round away, so an update by key would otherwise match nothing.
- `Create` keeps today's parameters and checks: end after start, and no self-mute. Q31's factory, which takes
  `setAt` plus a `ModerationDuration` (a type that doesn't exist yet) and drops the "end before start" checks, belongs
  to 3.4 and 3.5. The schema has no end-after-start constraint, so it doesn't stand in their way, and a legacy row
  can't abort the deploy on it.
- EF maps an internal flat row per table (`MuteRow`, …), and the public records are built from it through internal
  `FromDatabase` factories. Dapper will read the same rows in 3.4.

**Errors:** no new cases. A missing item, or one that has moved on, is `NotFound`. A transition the state forbids is
`Invalid`. A lost write race on a document, after three tries, is `Unavailable`.

## 4. Edge cases

| Case | What happens | Error case |
|---|---|---|
| A guild with no `Modules` document | Every module is off, as with no rows today | — |
| A document with a field the code doesn't know (written by a newer build) | Ignored on read. A write by the older build drops it, which only matters if an older build runs against a newer database, and a rolled-back deploy restores the database too | — |
| A document that doesn't parse | A defect: the generic reply plus an alert. Settings are never read as defaults | defect |
| Two moderators change the same document at once | Both apply to the latest version. The loser re-reads and re-applies, so neither change is lost | — |
| The same change retried 3 times and lost each time | `Unavailable` and the generic reply. In practice this needs four writers at once | `Unavailable` |
| A write of the value already set | `Write.Unchanged`, no new version, the cache key is still cleared (KI-103) | — |
| Setting a channel to "none" | The field is removed from the document. The log is off, as `GuildSettingDisabled` is today | — |
| A module turned off and on again | Its document is untouched, so its settings come back as they were (today's behaviour) | — |
| Muting a member who is already muted | The in-force row → `Removed` by the new mute's moderator, then a new `Active` row, in one transaction | — |
| Unmuting while the expiry poll expires the same mute | One `UPDATE` wins. The other updates no row and gets `NotFound` ("No active mute found"). The role is removed either way | `NotFound` |
| A second in-force row for the same member or channel (a bug, or hand-written SQL) | The partial unique index refuses it | defect |
| An `Active` row with no `ActivatedAt`, or a `Removed` row with no moderator | The check constraint refuses it | defect |
| An overdue legacy mute (3 on production) | Copied as `Active`, like every legacy mute (OQ-2). The first expiry poll removes the role if the member still has it, then marks it `Expired` (OQ-2) | — |
| An overdue legacy mute whose member has left | The poll handles it as it handles any expired mute of an absent member today. 3.4 adds TD-4's retries | — |
| A legacy mute whose sin is missing | Copied with the sentinels (`0001-01-01`, moderator 0), as today's copy does for every mute | — |
| A legacy mute for a guild with no mute role set | `MuteRoleId` stays null, and the expiry falls back to the guild's role, as today | — |
| A legacy level setting outside today's limits | Copied as it is, and read through `FromDatabase` (S-1; 2.1 found none) | — |
| An empty database | The legacy tables exist (from `main`'s migrations) and are empty, so nothing is copied. The `IF EXISTS` guards stay, as cheap insurance | — |

## 5. UX suggestions

Nothing a user sees changes in 2.2. Two suggestions, for the sections that own the commands:

- **Suggested (3.18):** `/modules` shows who last changed the module states and when, read from the `Modules`
  document's latest version. That information doesn't exist today, because each flag is its own row.
- **Suggested (3.1):** a `/settings history <module>` view for moderators, listing a document's versions with who and
  when. The data is there from 2.2 on, so it only needs a command.

## 6. SQL

### 6.1 Tables (all in `Settings`; ids `bigint`)

```sql
CREATE TABLE "GuildSettings" (
    "GuildId"  bigint NOT NULL,
    "Document" varchar(32) NOT NULL,
    "Version"  integer NOT NULL,
    "Value"    jsonb NOT NULL,
    "SetBy"    bigint NOT NULL,
    "SetAt"    timestamptz NOT NULL,
    CONSTRAINT "PK_GuildSettings" PRIMARY KEY ("GuildId", "Document", "Version"),
    CONSTRAINT "CK_GuildSettings_Version" CHECK ("Version" >= 1),
    CONSTRAINT "CK_GuildSettings_Value" CHECK (jsonb_typeof("Value") = 'object')
);
```

The primary key serves both reads: the latest version of one document (a backward scan) and the latest of each of a
guild's documents (`DISTINCT ON`). There is no check on `Document`'s values on purpose: a new document kind then needs
no migration, and the code refuses unknown kinds.

```sql
CREATE TABLE "Mutes" (
    "GuildId"      bigint NOT NULL,
    "UserId"       bigint NOT NULL,
    "SinId"        bigint NOT NULL,
    "MuteRoleId"   bigint NULL,
    "SetBy"        bigint NOT NULL,
    "SetAt"        timestamptz NOT NULL,
    "EndTime"      timestamptz NOT NULL,
    "State"        varchar(16) NOT NULL,
    "ActivatedAt"  timestamptz NULL,
    "EndedAt"      timestamptz NULL,
    "RemovedBy"    bigint NULL,
    "RemoveReason" varchar(1000) NULL,
    CONSTRAINT "PK_Mutes" PRIMARY KEY ("SinId"),
    CONSTRAINT "CK_Mutes_State" CHECK (
           ("State" = 'Pending' AND "ActivatedAt" IS NULL AND "EndedAt" IS NULL AND "RemovedBy" IS NULL)
        OR ("State" = 'Active'  AND "ActivatedAt" IS NOT NULL AND "EndedAt" IS NULL AND "RemovedBy" IS NULL)
        OR ("State" = 'Expired' AND "EndedAt" IS NOT NULL AND "RemovedBy" IS NULL AND "RemoveReason" IS NULL)
        OR ("State" = 'Removed' AND "EndedAt" IS NOT NULL AND "RemovedBy" IS NOT NULL))
);
CREATE UNIQUE INDEX "IX_Mutes_InForce" ON "Mutes" ("GuildId", "UserId") WHERE "State" IN ('Pending', 'Active');
CREATE INDEX "IX_Mutes_EndTime" ON "Mutes" ("EndTime") WHERE "State" IN ('Pending', 'Active');
```

`Expired` allows a null `ActivatedAt`, because a `Pending` mute can expire before it is applied (TD-4). The sin is the
key because each mute comes from exactly one. `ChannelLocks` and `ThreadLocks` have the same shape, with the primary
key `(GuildId, ChannelId, SetAt)` and `(GuildId, ChannelId)` in their in-force index, with `Reason varchar(1000)` in place of `SinId`/`MuteRoleId`.
`ChannelLocks` adds `PreviouslyAllowed` and `PreviouslyDenied` as `bigint NOT NULL` (S-3: production has no lock
without them). The in-force index's `GuildId` prefix also serves `IsChannelLocked`'s per-guild set.

The other five tables keep their columns, with `bigint` ids. `Initial` stops creating the seven
`IX_…_ChannelId_GuildId_SetAt`-style indexes that repeat a primary key.

### 6.2 Statements (interim EF, as raw SQL through `ExecuteSql`, so the race is in the statement)

```sql
-- Latest document (read; cached)
SELECT "Value", "Version" FROM "Settings"."GuildSettings"
WHERE "GuildId" = @GuildId AND "Document" = @Document
ORDER BY "Version" DESC LIMIT 1;

-- New version, only if @Expected is still the latest (0 for no document yet). 0 rows: a lost race, re-read.
INSERT INTO "Settings"."GuildSettings" ("GuildId", "Document", "Version", "Value", "SetBy", "SetAt")
SELECT @GuildId, @Document, @Expected + 1, @Value, @SetBy, @SetAt
WHERE COALESCE((SELECT max("Version") FROM "Settings"."GuildSettings"
                WHERE "GuildId" = @GuildId AND "Document" = @Document), 0) = @Expected
ON CONFLICT DO NOTHING;

-- A transition, e.g. remove. 0 rows: nothing in force (NotFound).
UPDATE "Settings"."Mutes"
SET "State" = 'Removed', "EndedAt" = @At, "RemovedBy" = @By, "RemoveReason" = @Reason
WHERE "GuildId" = @GuildId AND "UserId" = @UserId AND "State" IN ('Pending', 'Active')
RETURNING *;

-- Expired, past due (the poll; IX_Mutes_EndTime)
SELECT * FROM "Settings"."Mutes" WHERE "State" = 'Active' AND "EndTime" <= @Now;
```

`ON CONFLICT DO NOTHING` covers the narrow case where two inserts both pass the `WHERE` before either commits. The
primary key then refuses the second one quietly.

### 6.3 The legacy copy (two of the six documents shown; the rest follow the same pattern)

```sql
-- Modules: one object per guild, only the flags that are on.
INSERT INTO "Settings"."GuildSettings" ("GuildId", "Document", "Version", "Value", "SetBy", "SetAt")
SELECT g."Id"::bigint, 'Modules', 1, d.doc, 0, '0001-01-01T00:00:00Z'
FROM public."Guilds" g
LEFT JOIN public."GuildLevelSettings"      l  ON l."GuildId"  = g."Id"
LEFT JOIN public."GuildUserLogSettings"    u  ON u."GuildId"  = g."Id"
LEFT JOIN public."GuildModerationSettings" mo ON mo."GuildId" = g."Id"
LEFT JOIN public."GuildMessageLogSettings" ml ON ml."GuildId" = g."Id"
LEFT JOIN public."GuildCommandsSettings"   c  ON c."GuildId"  = g."Id"
CROSS JOIN LATERAL (SELECT jsonb_strip_nulls(jsonb_build_object(
    'Leveling',   NULLIF(l."ModuleEnabled", false),  'UserLog',  NULLIF(u."ModuleEnabled", false),
    'Moderation', NULLIF(mo."ModuleEnabled", false), 'MessageLog', NULLIF(ml."ModuleEnabled", false),
    'Commands',   NULLIF(c."ModuleEnabled", false),  'AntiSpam', NULLIF(mo."AntiSpamEnabled", false))) AS doc) d
WHERE d.doc <> '{}'::jsonb;

-- Leveling: defaults left out, so they stay defaults.
INSERT INTO "Settings"."GuildSettings" ("GuildId", "Document", "Version", "Value", "SetBy", "SetAt")
SELECT "GuildId"::bigint, 'Leveling', 1, d.doc, 0, '0001-01-01T00:00:00Z'
FROM public."GuildLevelSettings"
CROSS JOIN LATERAL (SELECT jsonb_strip_nulls(jsonb_build_object(
    'XpTimeoutSeconds',     NULLIF(extract(epoch FROM "TextTime")::bigint, 180),
    'LevelScalingBase',     NULLIF("Base", 15),
    'LevelScalingModifier', NULLIF("Modifier", 50),
    'XpGainAmount',         NULLIF("Amount", 5),
    'LogChannel',           "LevelChannelLogId"::bigint::text)) AS doc) d
WHERE d.doc <> '{}'::jsonb;

-- Mutes: moderator and time from the sin, role from the guild's settings.
INSERT INTO "Settings"."Mutes"
    ("GuildId", "UserId", "SinId", "MuteRoleId", "SetBy", "SetAt", "EndTime", "State", "ActivatedAt")
SELECT m."GuildId"::bigint, m."UserId"::bigint, m."SinId", ms."MuteRole"::bigint,
       COALESCE(s."ModeratorId", 0)::bigint, COALESCE(s."SinOn", '0001-01-01T00:00:00Z'), m."EndTime",
       'Active', COALESCE(s."SinOn", '0001-01-01T00:00:00Z')
FROM public."Mutes" m
LEFT JOIN public."Sins" s ON s."Id" = m."SinId"
LEFT JOIN public."GuildModerationSettings" ms ON ms."GuildId" = m."GuildId";
```

Each block keeps today's `DO $$ … IF EXISTS … $$` guard. `AutoPardonAfterSeconds` is left out when it equals
10,950 days, as today.

**Tests for the SQL** (integration, `Database/`): each statement in 6.2 against Postgres, including a lost write race
(two connections, one wins, the other's insert affects 0 rows), a transition from the wrong state (0 rows), and each
check constraint and unique index refusing a bad row. The copy is tested in section 8.

## 10. Decisions (owner, 2026-11-19)

| # | Question | Decision (the suggested answer) |
|---|---|---|
| OQ-1 | **Record the separate `Modules` document as conflict C13**, amending TD-6 ("Disabled is `Enabled = false`")? | **Yes.** It is the owner's proposal. It keeps the gate read small, keeps disabled modules' documents out of the cache, and keeps toggles out of each module's settings history. A null channel still means "off" for a log, as TD-6 says. |
| OQ-2 | **The 3 overdue mutes on production:** copy them as `Active`, so the first poll removes the role and marks them `Expired`? Or close them as `Expired` in the migration? | **Copy as `Active`**, and the owner widened it: every legacy mute, in force or overdue, is recorded as `Active`. A mute that is still on the books but past its end most likely means the role was never removed. The poll then does what the mute promised, removing the role if the member still has it, and records the outcome. Closing them in the migration could leave three members with the role indefinitely. |
| OQ-3 | **Snowflakes in JSON as strings or numbers?** `jsonb` stores numbers exactly, so only outside readers are at risk. | **Strings**, as Discord's own API does. pgAdmin's JSON viewer and any JavaScript tool round numbers above 2^53, and a wrong channel id that looks right is a hard bug to see. |
| OQ-4 | **The interim runtime:** 2.2 moves `SettingsModule`'s internals to the new tables through EF, keeping its API, and 3.1 then ports it to Dapper. Or should 2.2 port the settings reads to Dapper now? | **EF in 2.2.** The Dapper runtime (`Db<RT>`, `Sql`) lives in `Grimoire`, which `Grimoire.Settings` can't reference. Porting means 3.1's restructuring. Keeping the API also lets the existing settings tests prove the new storage behaves as the old did. |

## 11. Results and differences from the spec

**Checks:**

- `has-pending-model-changes` reports nothing, and `MigrationModelTests` passes. The chain's order is unchanged:
  Settings `Initial` still runs straight after `ModelRedesign`.
- `SettingsCopyTests` (new) runs the real deploy path: it migrates a scratch database to `ModelRedesign`, seeds
  `main`'s legacy tables, runs the rest of the chain, and reads the result through `SettingsModule`'s public API.
  It covers every setting and log channel, a guild with only defaults (no documents), a channel id above 2^53, mutes
  in force and overdue (all `Active`, with their sin's moderator and time and the guild's mute role), a mute whose
  sin is missing (the sentinels), and a lock with its permissions.
- `SettingsSchemaTests` (new) covers the statements in section 6. Three concurrent writers to one document all land
  (versions 1 to 3). Each write is a version with who/when. A module toggle leaves the module's settings alone. Each
  check constraint and in-force index refuses a bad row. A mute or lock that has ended can't end again (`NotFound`).
- **Mutation testing** of the new pure code (`ItemState`, the documents, `SettingsJson`, the three `New…`
  factories): 73% at first (46 killed, 16 survived), then 100% after adding the tests the survivors pointed to. They
  check each factory's fields, the refusal messages, every log type against each document it doesn't belong to, a
  snowflake written as a JSON number, a `null` document, and the microsecond truncation. There was no score before:
  this code is new.
- **Not run: the equivalence check on a production restore** (section 8). The restore from 2.1 was dropped when 2.1
  finished, as its spec required. It needs the owner to restore a backup again. `SettingsCopyTests` covers each
  case on seeded data, but not production's own rows.

**Where the code differs from the text:**

- **Keys** (owner, 2026-11-19, already folded into sections 3.3 and 6.1). A mute is keyed by its `SinId`, a lock by
  `(GuildId, ChannelId, SetAt)`. `MuteId` and `LockId`, with their converters and Dapper handlers, were written and
  then removed. `Create` truncates a set time to the microsecond (`ItemState.Stored`), so an update by key matches.
- **Column names.** The state tables keep `ModeratorId`, as today, where section 6.1 said `SetBy`. The documents use
  `SetBy`, as the other Settings tables do.
- **Nine indexes, not eight.** Two per state table (in force, and `EndTime`), one per override table. The mute key
  needs no separate `SinId` index.
- **The legacy mute copy needs no duplicate handling.** `main`'s `IX_Mutes_UserId_GuildId` has been unique since
  `Init`, so a member has at most one legacy mute. The first version of `SettingsCopyTests` found this when it tried
  to seed two.
- **Disabling a module that was never turned on is now `Unchanged`.** Before, it stored a `Disabled` row, because
  that differed from "default". Now a missing flag is already off, so nothing is stored, and the reply is "The
  setting was already set to that value." GEN-173's test accepts either reply for a disable that runs first.
- **An expiry records no reason.** The expiry polls now move a mute or lock to `Expired`. Before, they wrote a removal
  event, by the bot, with a reason ("Channel lock expired.", "Channel no longer exists."), and the second reason is
  now lost. The log messages are unchanged. 3.5's failure column (TD-4) is where that reason returns; the plan's
  3.5 row says so.
- **A document that doesn't parse becomes `Unavailable` for now, not a defect.** The interim EF code still goes
  through `ExecuteSafelyAsync`, which turns every exception into `Unavailable`. The boundary renders both cases the
  same way (the generic reply plus an alert), and 3.1's Dapper port makes it a defect.
- **The write race uses raw SQL through EF** (`ExecuteSqlAsync`), and the mute and lock writes run in a transaction
  inside the retrying execution strategy, which refuses a transaction it doesn't own.
- **P-9 for Settings** is the `UseBigintIds` helper in the shared conventions, applied by `SettingsModel` to its own
  entities. 2.3 makes the `bigint` converters the convention and deletes the helper.
- **The value types read typed values.** `XpGainAmount`, `LevelScalingBase` and `LevelScalingModifier` read an `int`,
  and `XpTimeoutPeriod` reads seconds. The `"25:00:00"` workaround is gone.
- **The `/modules view` outage test** now empties the `Modules` cache entry first. With one document, its own setup
  warms the cache, and a warm cache answers through an outage, which SET-10 wants anyway.
- **A bug found on the way:** `UpdateDocument<T>` first compared documents with `==`. On a generic `T : class`,
  that compares references, so every write counted as a change. It now uses `EqualityComparer<T>.Default`. The
  redundant-write tests caught it.
- **Test helpers.** `SettingsRows` (integration project) seeds rows straight into the tables and reads documents
  back. Tests that break a table by entity name now name the row classes (`GuildSettingRow`, `MuteRow`).
