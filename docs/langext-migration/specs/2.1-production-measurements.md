# Spec 2.1: Production measurements

Status: **implemented 2026-11-19.** Approved 2026-11-18, with every open question answered (section 10). Results in
[`../measurements/2.1-results.md`](../measurements/2.1-results.md). Where the run differed from this text: the copy
prototype (6.3) covered both schemas and dropped and rebuilt the 11 foreign keys, which a `bigint`/`numeric` pair can't
keep; the production output is saved as `2.1-production-baseline.out`; and production's `live_rows` were stale, so the
scaling uses exact counts and sizes instead (results, introduction).

Implements the plan's section 2.1: Q7's "run the production size query first, to estimate how long the rewrite
takes", the rollup's part 6 measurement spike ("Production size and `EXPLAIN (ANALYZE, BUFFERS)`"), and the
production queries the branch review still lists as "needed before deploy" (its sections 2, 3 and 7). The result is a
time and disk budget for 2.3's rewrites, and the data facts 2.2 and 2.3 need before they edit the undeployed
migrations (Q6).

This section writes no production code, changes no schema and adds no tests. Its outputs are two SQL scripts and one
results document.

## 1. Scope

**In scope**

- **A read-only production script** (`docs/langext-migration/measurements/2.1-production.sql`), run once by the owner
  in pgAdmin's Query Tool against production. It is plain SQL (no `psql` meta-commands), runs inside
  `BEGIN READ ONLY`, so any write is refused, and reports every result as a `NOTICE` in the Messages tab. It replaces
  any 17-to-20-digit number with `<id>` before printing, so the output holds no ids, names or message content
  (defect 9's rule, applied to a committed document).
- **A copy script** (`docs/langext-migration/measurements/2.1-copy.sql`) and a short runbook, run against a restored
  copy of production on the dev machine. It times the current branch's migrations and a prototype of 2.3's `bigint`
  rewrite, which can't be measured on production itself.
- **A results document** (`docs/langext-migration/measurements/2.1-results.md`): the numbers, the budget worked out
  from them, and what each number decides (section 2, step 6).

**Decisions and findings this informs**

| ID | What the measurement decides |
|---|---|
| **Q7 / P-9** | The deploy cost of `bigint` ids: how long each table's rewrite takes, and whether any single statement comes near P-3's 30-minute command timeout. Q7 already decided to do it; this sets its budget, not whether. |
| **Q9** | The cost of `ModelRedesign`'s `MessageHistory` `UPDATE` and `XpHistory` rewrite, which 2.3 combines with P-9's. |
| **P-3** | Whether 30 minutes per statement is enough, and the total downtime of the first deploy. |
| **P-16** | Whether the XP ledger needs compaction (3.14), from rows per member and the refresh's cost. |
| **Q12, Q12b, defect 23, TD-9** | The refresh cost of the view as 2.3 recreates it (tie-break, 0 XP excluded, names from the database), against the 30-second default timeout the refresh still runs under. |
| **P-1, P-2, branch review section 2** | The legacy custom-command role rows, and the two rows-must-be-zero guards that abort a migration (`ModelRedesign`'s Awarded check, `RequirePardonModerator`). |
| **S-1, S-3** | Out-of-range level settings and locks with no captured permissions: inputs to 2.2's conversion into TD-6 documents and TD-1 state rows. |
| **TD-1, Q8, Q9** | Row counts the 2.2 and 2.3 data steps move: open mutes and locks (and any overdue ones), pardons, `MessageHistory` by `Action`, `XpHistory` by `Type`. |

**Out of scope, with reasons**

- **The leaderboard query filtered to the largest guild** (the rollup's addition, for LVL-2). Q12 declined LVL-2 and
  kept the view, so the number would decide nothing.
- **MOD-6's three expiry queries.** They read the append-only lock and mute tables, which TD-1 replaces with state
  rows. 3.4 and 3.5 design new expiry queries against the new tables.
- **The `COMMIT` round-trip spike** (HOT-2). It's an integration-test check, not a production one, and belongs to 3.9.
- **Rehearsing the final migrations** on a copy. That is 2.4, after 2.2 and 2.3 have edited them. 2.1 times today's
  migrations plus a prototype, as an upper bound.

## 2. Flow

Every step is either a read on production, a timed run on a disposable copy, or arithmetic. Nothing here touches the
running bot.

1. **Restore a copy** (owner). The owner restores their existing production backup, a few months old, into a local
   database, and gives Claude its local connection string. The copy holds user data, so nothing from it is committed
   except the measured numbers, and it is dropped when 2.1 is done.
2. **Write and dry-run the scripts** (Claude). The production script is first run against the copy, before the copy is
   migrated, so at `main`'s schema. Claude runs it with `psql -f`, which runs the same plain SQL and prints the same
   notices. That proves it runs end to end, is read-only, and prints no ids (section 8).
3. **Production run** (owner, read-only). At a quiet hour, the owner opens the script in pgAdmin's Query Tool on the
   production server and runs the whole file (F5). It sets `statement_timeout = '5min'` and `lock_timeout = '2s'` for
   its own transaction, so it can't hold up the bot for long. When it finishes, the owner copies the Messages tab into
   `2.1-production-baseline.out`. The owner also notes the database's disk size and usage from the DigitalOcean dashboard,
   which SQL can't read. The output goes into the results document as-is.
4. **Copy run** (Claude). On the copy:
   1. The dry run in step 2 already gives the copy's P-2 and P-4a, the reference for step 5.
   2. Generate both contexts' scripts from `main`'s last migration,
      `dotnet ef migrations script 20250705185227_SpamFilterOverrides --context GrimoireDbContext` and
      `dotnet ef migrations script 0 --context SettingsDbContext`, and run them with `psql` and `\timing on`, in the
      order startup runs them (Grimoire first). Each statement's time is recorded.
   3. Run the `bigint` prototype (section 6, C-2): one `ALTER TABLE … ALTER COLUMN … TYPE bigint` per table, covering
      every id column of that table, so each table is rewritten once. The view is dropped first and recreated after.
   4. Time `REFRESH MATERIALIZED VIEW CONCURRENTLY` on the current view shape, then `EXPLAIN (ANALYZE, BUFFERS)` of
      2.3's shape (section 6, C-3).
   5. Record the copy's database size before and after, and its peak during the run, for the disk budget.
5. **Work out the budget** (pure arithmetic, Claude). The copy is months older than production and runs on different
   hardware, so a copy time is scaled twice:
   - **For size**, by the table's rows on production over its rows on the copy (P-2's `live_rows` on both). This
     assumes a rewrite's time grows linearly with rows, which holds for a heap rewrite and roughly for an index build.
   - **For hardware**, by `k`, the full-table XP aggregate's time per row on production over its time per row on the
     copy (P-4a and P-2 on both).

   `k` is crude, since a rewrite is write-bound and the aggregate is read-bound. So the budget uses `max(k, 1) × 2` as
   its margin, and says so.
6. **Write the results document**: the tables, the budget, and one line per row of section 1's table saying what the
   number decided. Then update the docs (section 9). Any finding that changes a later section (a guard that isn't
   zero, a statement over the limit) goes to the owner before 2.2 starts.

## 4. Edge cases

| Case | What happens |
|---|---|
| Production's migration history doesn't end at `20250705185227_SpamFilterOverrides`, or a `Settings` schema already exists | Stop. C9's and Q6's premise ("nothing after `main` has run in production") is wrong, and editing migrations in place isn't safe. Back to the owner before anything else. |
| A guard query isn't zero (`XpHistory` Awarded with no `AwarderId`, `Pardons` with no `ModeratorId`) | The first deploy would abort and roll back. Record the count. The owner chooses: fix the rows on production before deploy, or 2.3 adds a data step. The migration's guard stays either way. |
| P-1's second query isn't zero (a restricted legacy command with no roles) | The open decision from review rank 30: nobody could use it on `main`, and everyone can after `ModelRedesign`. Record the count and put the question to the owner in 2.3's spec. |
| A statement's scaled estimate is over 15 minutes (half the 30-minute timeout) | 2.3 either raises `MigrationCommandTimeout` for the first deploy, or splits the work (for example a batched `UPDATE`). Recorded as a constraint on 2.3; the choice is in 2.3's spec. |
| Free disk is less than the peak extra space the copy run used, times 1.5 | Each migration runs in one transaction, so a table's old files are only released at its commit, and a rewrite needs room for a second copy of the table and its indexes. Grow the database's disk before the deploy, or 2.3 orders the rewrites so that no single migration rewrites everything. |
| The refresh (scaled) is over 10 s | The refresh still runs under Npgsql's 30-second default (P-3 covers migrations only). Recorded for 3.15: the refresh gets its own timeout, or the view's shape is reconsidered. |
| The heaviest member has more than 50,000 `XpHistory` rows, or the refresh is over 5 s | P-16's threshold ("tens of thousands of rows, or seconds"). 3.14 adds ledger compaction. Under it, P-16 is recorded as not needed. |
| A measurement hits the 5-minute statement timeout | Its block catches `query_canceled` and prints `[P-n] over 5 minutes`; the rest still run, because each block's handler is a savepoint. "Over 5 minutes" already answers the questions it serves. |
| A measurement fails for another reason (a column that isn't there) | Its block prints `[P-n] failed: <message>` and the rest still run. The dry run on the copy should have caught it; production's schema differing from the backup's is itself a finding (edge case 1). |
| The backup is months old (the expected case) | Copy times are scaled by each table's rows on production over the copy's (section 2, step 5). The data counts in P-5 to P-7 come from production, not the copy, so they are current. |
| A table grew much faster than the others since the backup (for example a new large guild) | The per-table scaling covers it. If one table is over 3× its copy size, the results flag that its estimate is the least certain. |

## 6. SQL

All queries target `main`'s schema, which is production's: `public`, `numeric(20,0)` ids, integer `Type` and `Action`,
and the singular `Reaction` table. Every statement is a read except section 6.3, which runs only on the copy.

### 6.1 Production script (`2.1-production.sql`, read-only)

pgAdmin's Query Tool shows only the last statement's result grid, and doesn't run `psql` meta-commands. So the script
is one explicit read-only transaction of `DO` blocks, one per measurement, and each block prints its rows as notices
in the Messages tab:

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '5min';   -- per statement, so per block (PostgreSQL 13 and later)
SET LOCAL lock_timeout = '2s';

-- The shape of every block. A query's rows print as JSON; an EXPLAIN prints its plan lines.
DO $$
DECLARE r record;
BEGIN
    FOR r IN <query> LOOP
        RAISE NOTICE '[P-2] %', regexp_replace(row_to_json(r)::text, '\d{17,20}', '<id>', 'g');
    END LOOP;
EXCEPTION
    WHEN query_canceled THEN RAISE NOTICE '[P-2] over 5 minutes';
    WHEN OTHERS THEN RAISE NOTICE '[P-2] failed: %', SQLERRM;
END $$;

-- ... one block per query below ...

ROLLBACK;
```

`WHEN OTHERS` doesn't catch a cancel, so both handlers are needed. Each handler makes its block a savepoint, so a
failed block leaves the transaction usable for the next one. The queries, each wrapped in that shape:

```sql

-- P-0 Premise (edge case 1): main's last migration, and no Settings schema yet.
SELECT "MigrationId" FROM "__EFMigrationsHistory" ORDER BY "MigrationId" DESC LIMIT 3;
SELECT to_regnamespace('"Settings"') IS NULL AS settings_schema_absent;

-- P-1 Environment.
SELECT version();
SELECT pg_size_pretty(pg_database_size(current_database())) AS database_size;
SELECT name, setting, unit FROM pg_settings
WHERE name IN ('shared_buffers', 'work_mem', 'maintenance_work_mem', 'max_wal_size', 'statement_timeout',
               'max_parallel_maintenance_workers', 'track_io_timing');

-- P-2 Every table: rows, heap, indexes, TOAST, total; and maintenance state.
SELECT c.relname,
       s.n_live_tup AS live_rows, s.n_dead_tup AS dead_rows,
       pg_size_pretty(pg_relation_size(c.oid)) AS heap,
       pg_size_pretty(pg_indexes_size(c.oid)) AS indexes,
       pg_size_pretty(coalesce(pg_total_relation_size(c.reltoastrelid), 0)) AS toast,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total,
       pg_total_relation_size(c.oid) AS total_bytes,
       greatest(s.last_vacuum, s.last_autovacuum)::date AS last_vacuum,
       greatest(s.last_analyze, s.last_autoanalyze)::date AS last_analyze
FROM pg_class c JOIN pg_stat_user_tables s ON s.relid = c.oid
WHERE c.relnamespace = 'public'::regnamespace
ORDER BY pg_total_relation_size(c.oid) DESC;

-- P-3 Every index on the five largest tables, which the rewrite rebuilds.
SELECT t.relname AS table_name, i.relname AS index_name, pg_size_pretty(pg_relation_size(i.oid)) AS size
FROM pg_index x JOIN pg_class i ON i.oid = x.indexrelid JOIN pg_class t ON t.oid = x.indrelid
WHERE t.relname IN (SELECT relname FROM pg_stat_user_tables WHERE schemaname = 'public'
                    ORDER BY pg_total_relation_size(relid) DESC LIMIT 5)
ORDER BY pg_total_relation_size(t.oid) DESC, pg_relation_size(i.oid) DESC;

-- P-4 XP ledger shape (P-16), without ids.
SELECT count(*) AS members, max(n) AS max_rows,
       percentile_disc(0.5) WITHIN GROUP (ORDER BY n) AS p50_rows,
       percentile_disc(0.99) WITHIN GROUP (ORDER BY n) AS p99_rows
FROM (SELECT count(*) AS n FROM "XpHistory" GROUP BY "GuildId", "UserId") m;
SELECT n FROM (SELECT count(*) AS n FROM "XpHistory" GROUP BY "GuildId", "UserId") m ORDER BY n DESC LIMIT 5;
SELECT count(*) AS guilds, max(n) AS largest_guild_rows, max(members) AS largest_guild_members
FROM (SELECT count(*) AS n, count(DISTINCT "UserId") AS members FROM "XpHistory" GROUP BY "GuildId") g;
SELECT count(*) AS members_with_zero_xp
FROM (SELECT 1 FROM "XpHistory" GROUP BY "GuildId", "UserId" HAVING sum("Xp") <= 0) z;

-- P-4a The whole-table aggregate (persistence section's query). Also the copy-to-production ratio k.
EXPLAIN (ANALYZE, BUFFERS) SELECT "GuildId", "UserId", sum("Xp") FROM "XpHistory" GROUP BY 1, 2;

-- P-4b The view's body as committed (branch review section 7): the refresh's query.
EXPLAIN (ANALYZE, BUFFERS)
SELECT "GuildId", "UserId", sum("Xp") AS "TotalXp",
       ROW_NUMBER() OVER (PARTITION BY "GuildId" ORDER BY sum("Xp") DESC) AS "Rank"
FROM "XpHistory" GROUP BY "GuildId", "UserId";

-- P-4c A member's total, as GainUserXp sums it on each gain, for the heaviest member (P-16's hot path).
-- main has no (UserId, GuildId, Xp) index, so this is an upper bound for the branch. Inside its DO block:
--   SELECT "GuildId", "UserId" INTO g, u FROM "XpHistory" GROUP BY 1, 2 ORDER BY count(*) DESC LIMIT 1;
--   FOR r IN EXECUTE format('EXPLAIN (ANALYZE, BUFFERS) SELECT sum("Xp") FROM "XpHistory"
--                            WHERE "UserId" = %s AND "GuildId" = %s', u, g) LOOP ...
-- The ids go in as literals, as the bot's query sends them; the plan prints them as <id>.

-- P-5 Rows the data steps move or delete.
SELECT "Type", count(*) FROM "XpHistory" GROUP BY 1 ORDER BY 1;      -- Q9 rewrite; Type 4 is deleted
SELECT "Action", ("DeletedByModeratorId" IS NOT NULL) AS by_moderator, count(*)
FROM "MessageHistory" GROUP BY 1, 2 ORDER BY 1, 2;                    -- Q9 UPDATE
SELECT count(*) AS proxied_rows_deleted FROM "ProxiedMessages" WHERE "SystemId" IS NULL OR "MemberId" IS NULL;
SELECT count(*) AS pardons, count(*) FILTER (WHERE "Reason" IS NULL OR "Reason" = '') AS without_reason
FROM "Pardons";                                                       -- Q8
SELECT count(*) AS mutes, count(*) FILTER (WHERE "EndTime" <= now()) AS overdue FROM "Mutes";   -- TD-1
SELECT count(*) AS locks, count(*) FILTER (WHERE "EndTime" <= now()) AS overdue FROM "Locks";   -- TD-1

-- P-6 Branch review section 2: P-1 (two), P-2, then the two guards that must be zero.
SELECT count(*) AS p1_roles_on_unrestricted FROM "CustomCommandsRole" r JOIN "CustomCommands" c
    ON c."Name" = r."CustomCommandName" AND c."GuildId" = r."GuildId" WHERE NOT c."RestrictedUse";
SELECT count(*) AS p1_restricted_without_roles FROM "CustomCommands" c WHERE c."RestrictedUse" AND NOT EXISTS
    (SELECT 1 FROM "CustomCommandsRole" r WHERE r."CustomCommandName" = c."Name" AND r."GuildId" = c."GuildId");
SELECT count(*) AS p2_reclaimed_with_moderator FROM "XpHistory" WHERE "Type" = 2 AND "AwarderId" IS NOT NULL;
SELECT count(*) AS guard_awarded_without_awarder FROM "XpHistory" WHERE "Type" = 1 AND "AwarderId" IS NULL;
SELECT count(*) AS guard_pardons_without_moderator FROM "Pardons" WHERE "ModeratorId" IS NULL;

-- P-7 Branch review section 3: S-1, then S-3's upper bound.
SELECT count(*) AS s1_level_settings_out_of_range FROM "GuildLevelSettings"
WHERE "Base" NOT BETWEEN 1 AND 500 OR "Modifier" NOT BETWEEN 1 AND 200 OR "Amount" NOT BETWEEN 1 AND 100
   OR "TextTime" < INTERVAL '1 minute' OR "TextTime" > INTERVAL '60 minutes';
SELECT count(*) AS s3_locks_without_permissions FROM "Locks"
WHERE "PreviouslyAllowed" = 0 AND "PreviouslyDenied" = 0;

```

An `EXPLAIN` runs through `EXECUTE` inside its block and prints its `"QUERY PLAN"` column, so its plan is in the
Messages tab too, with `Execution Time` as its last line.

### 6.3 Copy: the `bigint` prototype (C-2)

Run after C-1, so the tables have the branch's shape. For each of the five largest tables, one statement that covers
all of that table's `numeric(20,0)` columns, generated from the catalogue so no column is missed:

```sql
DROP MATERIALIZED VIEW leaderboard_view;
SELECT format('ALTER TABLE %I %s;', c.relname,
              string_agg(format('ALTER COLUMN %I TYPE bigint USING %I::bigint', a.attname, a.attname), ', '))
FROM pg_attribute a JOIN pg_class c ON c.oid = a.attrelid
WHERE c.relnamespace = 'public'::regnamespace AND c.relkind = 'r' AND NOT a.attisdropped
  AND format_type(a.atttypid, a.atttypmod) = 'numeric(20,0)'
GROUP BY c.relname \gexec
-- then the view and its unique index, as LeaderboardView creates them
```

The prototype runs on every table, not only the largest five, so its total is the whole Grimoire context. The
`Settings` context needs no prototype: 2.2 creates it with `bigint` from the start (rollup part 5(c), step 2).

### 6.4 Copy: the view (C-3)

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY leaderboard_view;   -- timed, current shape, bigint ids

-- 2.3's shape: tie-break (defect 23), 0 XP excluded (Q12b), names from the database (TD-9).
EXPLAIN (ANALYZE, BUFFERS)
SELECT x."GuildId", x."UserId", x."TotalXp",
       ROW_NUMBER() OVER (PARTITION BY x."GuildId" ORDER BY x."TotalXp" DESC, x."UserId") AS "Rank",
       n."Nickname" AS "DisplayName", u."Username"
FROM (SELECT "GuildId", "UserId", sum("Xp") AS "TotalXp" FROM "XpHistory"
      GROUP BY 1, 2 HAVING sum("Xp") > 0) x
LEFT JOIN LATERAL (SELECT "Nickname" FROM "NicknameHistory" h
                   WHERE h."UserId" = x."UserId" AND h."GuildId" = x."GuildId"
                   ORDER BY h."Timestamp" DESC LIMIT 1) n ON true
LEFT JOIN LATERAL (SELECT "Username" FROM "UsernameHistory" h
                   WHERE h."UserId" = x."UserId" ORDER BY h."Timestamp" DESC LIMIT 1) u ON true;
```

Column names follow the branch after C-1 and are checked against it when the script is written. This is a prototype
for its cost only; 2.3's spec owns the real view.

## 8. Tests

No automated tests: the section adds no code. The scripts are checked instead:

  prints at least one line and none prints `failed:`, `grep -E '[0-9]{17,20}'` over its output finds nothing, and

  confirms it prints `failed: cannot execute INSERT in a read-only transaction`.

  So the owner first runs it once against the local copy in pgAdmin and checks that the Messages tab shows the same
  lines as the dry run.

No old tests are replaced.

**Note on OQ-6.** Merging is possible only now, because nothing after `main` has run in production (C9). It means one
migrations-only `DbContext` that maps both schemas (`public` and `Settings`), one `__EFMigrationsHistory`, and the
post-`main` migrations of both contexts re-expressed as one ordered chain, so each data copy sits directly before the
drop or rewrite that needs it. Costs: it partly reverses Q6's "no squash" (the Settings migrations must be regenerated
in the merged context, whether or not the Grimoire ones are squashed), every dev and test database is rebuilt (2.4
already plans that), and the tests' two fixtures (`"Test collection"`, `"Settings collection"`) become one. Q10 already
keeps the legacy tables until P-7's later release, so the first deploy doesn't drop the tables the Settings copy
reads. A single chain makes that order a property of the chain instead of a rule people have to remember.
