# 2.1 results: production measurements

Spec: [`../specs/2.1-production-measurements.md`](../specs/2.1-production-measurements.md). Scripts:
[`2.1-production.sql`](2.1-production.sql) (read-only, pgAdmin) and [`2.1-copy.sql`](2.1-copy.sql) (copy only, psql).
Outputs: [`2.1-production-baseline.out`](2.1-production-baseline.out) (production, 2026-11-19, 48 s) and
[`2.1-copy-baseline.out`](2.1-copy-baseline.out) (the copy). Neither holds a 17-to-20-digit number.

Status: **done 2026-11-19.** Disk checked by the owner the same day: under 2 GB used of 10 GB.

The copy is the owner's production backup from a few months ago, restored locally (PostgreSQL 18.3), and cloned into a
throwaway `grimoire_21` for the runs that write. Production is PostgreSQL 18.7. The dry run on the copy ran every block
with no failures, and an added `INSERT` block was refused with `cannot execute INSERT in a read-only transaction`.

**Production's statistics are stale.** P-2's `live_rows` and `last_analyze` come from the cumulative statistics, which
were evidently reset (they are reset by a crash, a failover or a major upgrade). `XpHistory` shows 4,052 live rows and
has never been analyzed since, while its exact count (P-5) is 2,637,006. Autovacuum decides when to run from those same
counters, so it hasn't vacuumed or analyzed the large tables since the reset. So this document scales by exact counts
(P-5) and by size, never by `live_rows`. See section 6, "Statistics and bloat".

`XpHistory` holds 13% more rows in 56% more space: the heap is bloated (dead space autovacuum never reclaimed). The
message tables grew 3.2× in rows, over the spec's 3× line, so their estimates are the least certain. They are small
enough in absolute terms that it doesn't change anything.

`EXPLAIN`, so the overhead cancels out.

## 5. Budget

| | Formula | Value |
|---|---|---|
| Growth of `XpHistory` | by size (larger than by rows, 1.13×, because of the bloat) | **1.56×** |
| Growth of the message tables | `MessageHistory` rows | 3.16× |
| `k`, hardware per row | (production ms ÷ rows) ÷ (copy ms ÷ rows), P-4a and P-4b | 7.94 (P-4a) and 4.59 (P-4b); **7.94** used |
| Margin | max(k, 1) × 2 | 15.9 |
| Longest statement, estimated | 4.47 s × 1.56 × 15.9 | **about 1.8 minutes** |
| Whole migration, estimated | (13.1 s of `XpHistory` work × 1.56 + 0.9 s of the rest × 3.16) × 15.9 | **about 6 minutes** |
| Peak extra disk | the copy's +553 MB × (1,073 ÷ 547) | about 1.1 GB |
| Free disk needed | 1.5 × the peak extra | **about 1.6 GB** |
| Refresh, estimated (no margin: it isn't a deploy step) | 0.21 s × 1.56 × 7.94 | about 2.6 s now, about 3 s in 2.3's shape |

`k` is crude, as the spec says. Production's P-4a ran cold and against a bloated heap, and P-4b, run straight after it
on a warmer cache, gave 4.6. Using the larger figure and then doubling it keeps the estimate on the safe side. 2.0's
merged chain and 2.3's combined rewrites only lower these numbers.

## 6. What each number decides

| ID | Decision from the numbers |
|---|---|
| **Q7 / P-9** | Go, as decided. The whole `bigint` rewrite is estimated at about 1.5 minutes on production, almost all of it `XpHistory`. |
| **Q9** | The `XpHistory."Type"` rewrite is the longest statement. 2.3 should fold it into P-9's rewrite of the same table (one `ALTER TABLE` covering the type and the ids), which saves a full rewrite of the largest table, about 2 minutes estimated. |
| **P-3** | 30 minutes per statement is ample. `MigrationCommandTimeout` stays as it is. |
| **Q6 index pairs** | `IX_XpHistory_GuildId_Xp`, created and later dropped, costs 1.6 s on the copy (about 40 s estimated on production). Removing the pair (2.3) saves that too. |
| **P-16** | **Compaction is needed.** Three members have over 50,000 rows, and the heaviest one's total takes 1.0 s on production with `main`'s indexes. That runs on every XP gain for that member. The branch's `IX_XpHistory_UserId_GuildId_Xp` makes it an index-only scan, but only on pages the visibility map marks all-visible, which needs vacuum (next row). 3.14 adds the monthly compaction from P-16: fold each member's `Earned` rows older than N days into one `MigratedXp` row. |
| **Q12, Q12b, defect 23, TD-9** | The refresh is estimated at about 3 s in 2.3's shape, well under the 30-second default it runs with. The view stays (Q12). Neither 3.15 nor 2.3 needs a timeout change for it. Excluding 0 XP (Q12b) shrinks the view from 25,043 rows to about 10,400. |
| **P-1** | 0 and 0. Review rank 30's open question (a restricted legacy command with no roles) has nothing to apply to, so it closes. |
| **P-2** | 10 reclaimed rows keep their moderator through review rank 31's fix. |
| **Guards** | Both 0, so the first deploy won't abort today. The guards stay in the migrations, since rows can still change before the deploy. |
| **S-1, S-3** | Both 0. 2.2's settings conversion needs no repair step for out-of-range values or locks without captured permissions. |
| **TD-1 (2.2)** | 4 mutes, 3 of them overdue. On `main` a finished mute is deleted, so those 3 are stuck rows. 2.2's spec must decide whether they become `Active` and expire on the processor's first tick, which removes the role if the member still has it, or whether the migration closes them. No locks. |
| **Q8 (2.3)** | 38 pardons, 24 of them without a reason. Q8 makes each pardon one `Pardon` row plus its reason history, so 2.3's spec must decide whether a pardon with no reason gets no history row or a row with an empty reason. |
| **Statistics and bloat (2.4, new)** | Production's statistics were reset, and autovacuum hasn't caught up. `XpHistory` is about 1.6× its compact size. The rewrite removes that bloat at no extra cost. But a rewrite also leaves the rewritten columns without planner statistics, so **the deploy runbook (2.4) ends with `ANALYZE`**, and a `VACUUM` on `Messages` and `MessageHistory`, which aren't rewritten. 2.4 also checks that autovacuum is on for the database. |
| **Disk** | About 1.6 GB free is needed, and over 8 GB is free (under 2 GB used of 10 GB). No change to the database's size. |
